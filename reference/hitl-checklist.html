HITL 设计与审批清单

人是最贵的稀缺资源；每一次打断都要买来确定性。

首次建立 2026-11-14 配套 Lesson 0012 可打印

这张清单回答四个问题：什么时候该问人？问的时候给人看什么？ “批准”到底授权了什么？没人回答、进程崩溃、参数被换时怎么办？ 先记住三句话，再按分级、请求、绑定、超时、持久化与指标逐项检查。

01三句话心智模型

分级决定何时问 · 审批卡决定能不能判断 · 绑定决定授权范围
  1. HITL 不是给每个动作加一个 Approve 按钮。如果每个动作都要人批，人会开始橡皮图章；确定性的规则交给代码，判断留给人。
  2. 审批是一个有状态的后端系统。它有请求、身份、授权、有效期、消费、审计、并发控制与指标；不是一个布尔值。
  3. 审批不等于恰好一次执行。它保证“有人授权了这个动作”，不保证副作用只发生一次；后者要靠目标系统的幂等键或对账。
最容易犯的错

把风险等级绑定在工具名上。同一个 restart_service，在 dev 是 T1， 在 order-service 是 T2，在 payment-service 是 T3。按工具名分级，等于把参数绕过留给攻击者。

T0 / T1：不需要审批的动作

  • 只读、无外部副作用、可重复执行。
  • 非生产环境的可逆写操作；执行后通知值班即可。
  • 小规模、可自动回滚的容量调整。
  • 仍然要审计：谁、何时、对什么、做了什么。

T2 / T3：需要审批的动作

  • 影响生产流量，但可恢复（T2，一人）。
  • 不可逆、涉及资金、多服务或合规（T3，两人）。
  • four-eyes：不同的人、有授权、非发起人。
  • 审批人必须能看懂证据与后果，否则只是盖章。

T4：永不经过 Agent 的动作

  • 改防火墙、改 IAM、drop database 等超出授权范围的动作。
  • 没有安全回滚、无法对账的动作。
  • 未知工具、缺失参数、无法判定风险的动作。
  • 走独立变更流程；不要用“隐藏 flag”绕过。

多条规则叠加

  • 按参数分级：env、service、replicas、金额、目标范围。
  • 任务级预算：按 task_id 累计次数/金额/影响面。
  • 防多步规避：拆成 10 次小额不等于 10 次低风险。
  • 策略有版本、有测试、有变更审计；执行时重新评估。

03审批请求清单

坏审批卡 Agent requests approval Tool: restart_service [Approve] [Reject] 好审批卡 Action restart_service Target prod / order-service (3 replicas) Why now p99 8.2s; pool 49/50; runbook RB-12 step 4 Evidence health.json · logs 20:03–20:08 · RB-12 Effect rolling restart ~90s; traffic retried Rollback no data loss; previous image retained Risk T2 · production, reversible with effort Request agent/repomedic · INC-42 Expires 20:25 UTC (15 min) · timeout = reject Raw args {"service":"order-service","env":"prod"} [Approve] [Reject with reason] [Edit & re-approve]

必须显示

  • 精确工具 + 原始参数；不要只给模型摘要。
  • 目标服务、环境、副本数/资源范围。
  • 为什么现在做：证据链接、runbook、指标。
  • 后果预览：会发生什么、不会发生什么、持续多久。
  • 可逆性与回滚方式。
  • 风险等级与定级依据。
  • 发起人、任务/事故号。
  • 有效期与超时行为（默认拒绝）。

决定类型

  • Approve：按原始参数执行。
  • Reject：不执行，把原因写回 Agent。
  • Edit & re-approve：改参数后重新过策略、重新算 digest、重新绑定。
  • Ask for evidence：证据不足时先补，不急着批。
  • Escalate：转给更有权限或更熟悉的人。

安全边界

  • 审批卡只放做决定所需的最小信息。
  • 不要在通知/浏览器里暴露完整日志、连接串、隐私数据。
  • 浏览器审批只发送不透明 decision ID；完整状态留在服务端。
  • 不接受客户端传来的 state、参数或审批记录。
  • 审批人通过应用中间件认证与授权。

找人也是工具调用

  • request_human_input(question, context, options)。
  • options 包含 urgency、format、choices。
  • 追加 human_input_requested 事件，保存线程，跳出循环。
  • 人回复后用 thread_id 恢复，追加 response_from_human。
  • 适合“该查哪个方向”这类判断，不只是高风险写操作。

04绑定与授权清单

动作绑定

  • digest = 工具 + 规范化参数 + 发起人 + 任务号。
  • 规范化：键排序、统一空格、稳定数字格式。
  • 批准时存 digest；执行时重算并比较。
  • 参数被修改 → 拒绝，必要时重新发起审批。
  • digest 是动作指纹，不是密码学签名。

身份与职责分离

  • 审批人来自认证后的 session/token，不是自由文本。
  • 授权查询 IAM/on-call 组；不是“名字在列表里”。
  • 发起人不能批准自己的请求。
  • four-eyes 需要两位不同的、有授权的、非发起人。
  • 审批记录包含审批人、时间、备注、决定。

时效与重校验

  • 每个请求有 created_at 与 expires_at。
  • 执行前重新评估策略；收紧则阻断。
  • 执行前重新检查目标状态（TOCTOU）。
  • 过期 = 拒绝；需要时用新证据重新发起。
  • 长期挂起要带 agent/SDK 版本标记。

单次消费

  • 审批是一次性能力，不是可复用布尔值。
  • 执行前原子更新 approved → consumed。
  • 条件更新返回 0 行 → 不要执行。
  • 并发审批用 version 乐观锁，防止丢更新。
  • 重放命中幂等键 → 返回已有结果，不产生新副作用。

检查

TTL 是否服从事故 SLA？一个 15 分钟的审批窗口，放在 5 分钟的事故 SLA 里，实际等于“不允许 Agent 处理”。 等待是否不占线程/计算（interrupt、wait_condition）？ 超时后 Agent 是真的停止，还是偷偷继续循环？

06持久化执行清单

状态放在哪里

  • 审批状态在图里：简单，适合单编排器。
  • 审批状态在外部服务：适合多消费者、多人协作。
  • 用 request_id 关联两份状态。
  • 明确单一事实来源，避免“图里批准、系统里拒绝”。

崩溃窗口

  • 先写 effect 再消费审批：可能重复，靠幂等键去重。
  • 先消费审批再写 effect：可能丢动作，需要人工对账。
  • 按动作语义选择，不要一刀切。
  • 目标系统必须强制稳定幂等键，或提供事务/对账。

恢复语义

  • resume 会重跑未完成节点；已完成节点不重跑。
  • resume 会重放 interrupt 前的 stream 事件；前端按 event_id 去重。
  • 审批卡用 request_id 去重，避免恢复后弹第二张。
  • 不要自动重放结果不确定的动作。

审计

  • 每个请求：创建、决定、执行、消费、过期。
  • 每条事件：时间、actor、request_id、tool、digest、结果。
  • 高风险动作 100% 可追溯到审批人与参数。
  • 审计日志与业务日志分开保存。

07评测指标

指标回答的问题异常信号
Approval volume每位审批人每小时处理多少条？超过处理能力 → 疲劳
Time-to-decision p50/p95人花了多久决定？p50 < 5s → 橡皮图章
Approval rate批准比例是多少？≈100% → gate 装饰化；≈0% → 策略过严
Override / edit rate多少人改参数或拒绝？高 → 审批卡信息不足
Expiry / pending age多少过期？最老待办多久？高 → 审批成为瓶颈
Escaped-action rate批准的动作里多少事后不该做？抽样审计；真实漏检率
Replay / duplicate effects重试产生新副作用了吗？任何新重复副作用都是幂等失败
Audit completeness高风险动作证据齐全吗？缺失 → 无法复盘/合规

成对看指标：审批率下降本身不是目标；要的是 escaped-action rate 不上升的前提下，减少不必要的打断。
