评测设计与校准清单

没有置信区间、没有切片、没有校准过的 judge 的分数，只是噪声。

首次建立 2026-11-17 配套 Lesson 0013 可打印

这张清单回答四个问题：评测集从哪里来？什么叫“通过”？用谁来判？怎么知道这个判断可信？ 先记住三句话，再按数据集、rubric、grader、judge、校准、统计与 CI 逐项检查。

01三句话心智模型

数据集决定测什么 · rubric 决定什么叫过 · 校准决定 judge 能不能信
  1. 评测不是发布前的一次考试，而是迭代的飞轮。每一次真实失败都应该变成一个 case，每一个 case 都应该进入回归门禁。
  2. 先代码，后模型，再人工。能用确定性 grader 判的，不要用 judge；能用 judge 判的，不要找人。顺序反了，成本和噪声都会失控。
  3. 一个分数不是报告。报告至少要有切片、置信区间、失败清单和成本；否则你无法判断下一次改动该往哪走。
最容易犯的错

用一个永远说 pass 的 judge，在失败率很低的数据上拿到 95% 的 raw agreement， 然后以为评测已经可用。它的 TPR 是 0：一个失败都没抓到。永远先看 TPR/TNR，再看 agreement。

02评测集清单

来源与规模

  • 先收集 20–50 个真实失败；从工单、bug 报告、发布检查、trace 中取样。
  • 优先用户影响大的任务，不是最容易写的任务。
  • 合成数据只补边界；不要用合成集替代真实分布。
  • 每个任务有输入、参考解、成功标准、约束与预算。
  • 参考解证明任务可解；全员 0% 先怀疑 case/grader。

平衡与反例

  • 既要测“该回答时回答”，也要测“该拒答时拒答”。
  • 每类标签的样本数尽量均衡；min/max 差不超过 1。
  • 包含边界、对抗、信息不足、证据冲突的 case。
  • capability 与 regression 分开标记；regression 应接近 100%。
  • 难度分布要有 easy / medium / hard，不要全是难题。

泄漏与重复

  • incident 不出现根因标签、根因是、root cause 等结论句。
  • evidence 是观测值，不是“根因：X”这样的答案。
  • normalized incident 去重；不要只换 service 名复制。
  • 检查 title / metadata 是否被喂给了 Agent；如果会，也算输入。
  • 保留 held-out 集，不要用它调 prompt 或 rubric。

环境与可复现

  • 每次 trial 从干净环境开始；清理缓存、文件、git 历史。
  • 固定模型版本、temperature、seed（如支持）、工具版本。
  • 记录 token、工具调用数、延迟与成本。
  • 保留原始 trace；报告是从 trace 生成的，不是手填的。
  • criteria 会 drift：看输出会改变标准，迭代是正常的。

03任务与 rubric 清单

任务契约 input Agent 实际能看到什么？（incident + evidence + tools） reference 人类参考解，证明任务可解 criteria 每个维度独立、可观察、可判定 constraints 只读 / 审批 / 预算 / 必须拒答 budget 最大步数、token、延迟 rubric 维度 R1 根因正确，或证据不足时正确拒答 R2 每个 claim 有引用；必需证据齐；quote 逐字 R3 动作 ≤ 允许 tier；未知工具 fail closed R4 服务、症状、下一步说清楚 overall = R1 ∧ R2 ∧ R3 ∧ R4 安全维度是一票否决，不参与平均。

写 rubric 时

  • 一个维度只问一件事；不要“准确、完整且有帮助”。
  • 用 binary PASS/FAIL + critique，不用 1–5 分整体评分。
  • 允许 UNKNOWN；证据不足时不要逼 judge 编判决。
  • 每个维度独立调用一个 judge，避免硬失败被平均掉。
  • rubric 有版本；标准变了，旧分数不可直接比较。

写成功标准时

  • grade outcome，不 grade 路径；除非过程本身是需求。
  • 不要用僵化的 tool-sequence 检查拒绝合法探索。
  • 两位领域专家独立看同一输出，应得出相同 pass/fail。
  • 把成本写进标准；准确率不是唯一目标。
  • 负向案例与正向案例同等重要。

04Grader 选择与测试清单

Grader先用来判什么不要用来判什么
Codeschema、枚举、引用 ID、quote 子串、动作 tier、禁用词、工具调用结果证据是否充分、解释是否自洽、语气是否专业
Model开放式答案的清晰度、证据充分性、根因解释、下一步具体性能用代码算的硬契约；需要精确计算的数字
Human校准集标注、边界案例、抽样审计、judge 分歧复核全量回归；高频率、低风险的评分

测试 grader 本身

  • 完美答案 → 全部通过。
  • 明显错误答案 → 对应维度失败。
  • 边界答案 → 给出可解释的失败原因。
  • 格式错误 → schema 失败，不算模型能力失败。
  • 每次意外失败先问：模型错，还是 grader 错？

防 grader hacking

  • grader 留在评测侧，不暴露给 Agent。
  • 使用 held-out 与对抗性 case。
  • 不要只奖励“包含某个 ID/关键词”。
  • 长度、格式、引用数都可以被灌水；用覆盖度与 groundedness。
  • 定期换 rubric 版本，保留人工抽样。
真实 bug 提醒

CORE-Bench 曾因 rigid numeric matching、任务歧义与 scaffold 约束把 Opus 4.5 压在 42%， 修好 grader 后升到 95%。METR 也发现过“要求超过阈值”的 grader 惩罚了严格按指令达到阈值的模型。 这些是评测器 bug，不是模型退化。读 transcript，别只看分数。

05LLM-as-judge 设计清单

Prompt 设计

  • 只评一个维度；不要一个 prompt 评四件事。
  • 包含任务、输入、证据、参考解与 rubric。
  • 先写 critique，再给 verdict。
  • 提供 3–5 个带 critique 的 few-shot 示例。
  • 输出结构化 JSON；verdict 只能是 PASS/FAIL/UNKNOWN。

偏差与安全

  • Position bias：交换 A/B 跑两次；取平均或要求一致。
  • Verbosity bias：写明长度不加分；用要点覆盖度。
  • Self-enhancement：用不同家族的 judge；多 judge 投票。
  • 把答案/证据标为不可信数据，防止 prompt injection。
  • judge 不执行工具、不访问网络，只输出评分。

成本与抽样

  • 用负担得起的最强模型；judge 可以比生产模型更大。
  • 代码 grader 全量跑；judge 抽样跑；人工只跑分歧。
  • 缓存相同输入的 judge 结果；固定 prompt 版本。
  • 记录 judge 的 token 成本与延迟。
  • 成本超过决策价值时，退回代码或人工。

常见错误

  • 没有 critique，只有一个分数。
  • critique 太短，无法解释 verdict。
  • 缺少专家使用的外部上下文。
  • few-shot 示例不够多样，只覆盖 happy path。
  • 用未校准的现成 judge 直接上线。

06Judge 校准清单

把 fail 当正类。四个格子分别是 TP（抓到失败）、FN（漏检）、FP（误报）、TN（正确保留）。

Judge 判 failJudge 判 pass
人类判 failTP
抓到了		FN
漏掉了
人类判 passFP
误报了		TN
正确保留
TPR = TP / (TP + FN) · TNR = TN / (TN + FP) · raw agreement = (TP + TN) / N

样本量与划分

  • 先约 30 个样本，直到新失败模式不再出现。
  • 验证 judge 时，每个失败模式约 100 个样本。
  • 少于 60 个样本，置信区间通常太宽。
  • 大致 10–20% train、40–45% dev、40–45% test。
  • dev/test 每类尽量 30–50 个；测试集不放进 prompt。

校准流程

  • 找一位领域专家，他的判断定义“好”。
  • 每个样本标 pass/fail + 详细 critique。
  • 先修明显产品 bug，再建 judge。
  • 用 critique 做 few-shot；迭代 prompt。
  • 冻结 prompt，在 held-out 上跑一次最终估计。

如何读结果

  • 低 TPR = 漏检；坏答案会上线。
  • 低 TNR = 误报；好答案会被反复打回。
  • 失败率 5% 时，永远 pass 的 judge agreement 约 95%。
  • 平衡集上 >90% agreement 才比较有意义。
  • 报告 TPR/TNR，不只报告 agreement。

维护

  • 换 judge 模型 → 重新校准。
  • 改生产 prompt / 工具 schema → 重新校准。
  • judge prompt 与 calibration 集一起版本化。
  • 定期看分歧样本，防止 judge 与产品一起漂移。
  • judge 是人工判断的放大器，不是替代品。

07统计与报告清单

要报的回答的问题例子
点估计 + CI真实通过率可能在什么范围？32/40 = 80% [65.2%, 89.5%]
切片哪一类在退步？capability 78.6% · regression 83.3%
成对 diff同一 case 上谁更好？fixed 19 · regressed 7
pass^k连续 k 次都可靠吗？0.80³ = 51.2%
成本每任务多少钱/多少 token？准确率-成本 Pareto 曲线
失败清单具体错在哪一维？根因 / 证据 / 安全 / schema

不要过度解读

  • 40 个 case 的 2 个百分点差异通常是噪声。
  • 两个独立百分比不如同一 case 的成对比较敏感。
  • 小样本的极端值（0/10、10/10）用 Wilson 区间。
  • pass@k 上升不代表可靠性；看 pass^k。
  • 总分上升可能掩盖 regression；必须看切片。

维护评测集

  • capability 饱和后毕业为 regression。
  • 持续从生产失败中添加新 case。
  • 监控 eval saturation：全员通过时加难度。
  • 保留 held-out，防止 benchmark overfitting。
  • 读 transcript；聚合数字会隐藏原因。

08CI 与生产清单

仓库结构

  • cases.jsonl、rubric.md、graders/、judge_prompt.md 版本化。
  • calibration.jsonl 与 judge prompt 同步更新。
  • runs/ 保存原始输出；报告可重建。
  • schema 与 case 一起测试；坏数据早失败。
  • 数据脱敏；评测数据按生产数据管理。

门禁规则

  • dataset audit 必须通过。
  • regression 切片必须 100%（或明确的豁免）。
  • 安全 grader 失败 → 直接阻止合并。
  • capability 与 baseline 比较，报告 CI 与 diff。
  • 不要只用 --fail-under；按切片与安全规则拆开。

生产闭环

  • 线上 trace 抽样 → 失败分析 → 新 case。
  • 人工反馈 → 校准集 → judge 更新。
  • A/B 测试验证业务指标，不只验证模型分数。
  • 监控成本、延迟与错误率。
  • “Swiss cheese” 多层评估：自动 + 人工 + 生产。

组织与所有权

  • 专门团队维护评测基础设施。
  • 领域专家贡献 case、跑评测、读 trace。
  • 产品团队对 rubric 的业务含义负责。
  • 评测结果进入发布评审，不是附件。
  • 没有人拥有评测，评测就会退化。
