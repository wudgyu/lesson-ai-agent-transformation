服务化、流式与可靠性清单

请求会断，进程会死；run 必须活得比它们久。

首次建立 2026-11-27 配套 Lesson 0017 可打印

这张清单把“把 Agent 部署成服务”拆成六件事：run 的生命周期、入口准入、 超时与取消、重试预算、SSE 流式、关停与恢复。先记住三句话，再逐项检查。 配套 lab：labs/0017-serving；课时页： Lesson 0017。

01三句话心智模型

请求 ≠ run · 流是视图，结果才是真相 · 重试要花预算
  1. HTTP 请求是短命的，run 是长命的。入口返回 202 + run id；执行、事件、结果、checkpoint 都挂在 run 上。客户端断开不等于任务取消。
  2. SSE 只是通知通道。事件可能丢、可能被环形缓冲区淘汰、可能 overflow；最终结果必须能从 GET /runs/{id} 取回，并且先写结果再发 done。
  3. 重试、限流、排队保护的都是共享资源。重试花的是下游容量；并发限制保护的是 worker、内存和模型配额；队列必须有界，满了就 503，而不是无限堆积。
最容易犯的错

用 BackgroundTasks 跑 Agent。它和 web 进程同生共死、没有持久队列、 没有重试、没有可见性；进程收到 SIGTERM 就一起没了。FastAPI 官方文档明确把它定位为 “响应之后的小任务”，重活要用外部 job queue。

02Run 的解剖

POST /v1/runs │ ├─ 认证：tenant / subject / scopes ← 不能信 X-Tenant 头 ├─ 幂等：Idempotency-Key + payload hash ├─ 配额：tenant token bucket → 429 + Retry-After ├─ 容量：bounded queue + worker slots → 503 queue_full └─ 202 {run_id, events_url} │ ▼ queued ──worker──> running ──成功──> succeeded │ │ │ ├─ deadline / non-retryable ──> failed │ ├─ caller cancel ─────────────> cancelled │ └─ shutdown ──────────────────> queued (resumable) └─ caller cancel ────────────────────────────────> cancelled 每个 run 持有： run_id · tenant · status · created_at · started_at · finished_at event log (seq, type, data, ts) · last_seq checkpoint (phase_index, findings) · result / error attempts · resumable · cancel_requested

状态机必须写死

  • terminal 只有三种：succeeded / failed / cancelled。
  • terminal 之后不再接受 cancel、不再改结果。
  • done 事件永远是最后一个事件。
  • 结果先落 store，再发 done。
  • queued 的 run 在重启后必须能被重新拾起。

Run 记录必须包含

  • 租户与调用者身份（审计用）。
  • 输入 payload 的 fingerprint。
  • 当前 phase / checkpoint，而不是只存“running”。
  • attempts 与最后一次错误类型。
  • 结果版本与生成时间（客户端可能拿到旧结果）。

端点状态码语义
POST /v1/runs202接受新 run；返回 run_id、Location、events URL。
POST /v1/runs200同 key 同 payload，run 已完成；返回原 run，不新建。
POST /v1/runs400缺 Idempotency-Key。
POST /v1/runs409同 key 的 run 仍在进行中；返回 Location 让客户端 attach。
POST /v1/runs422同 key 但 payload 不同；不要返回原结果。

GET /v1/runs/{id}/events200SSE；支持 Last-Event-ID。

GET /readyz200 / 503readiness：能接新流量吗？关停一开始就 503。
202 的含义

“我已接收，但还没完成。”客户端应保存 run id，通过 SSE 或轮询获取进度； 不要在一次 HTTP 请求里等完整 Agent 跑完。长连接 + 无进度 = 最容易被网关超时切断的形态。

04入口准入清单

身份与授权

  • tenant 来自认证主体，不来自客户端 header。
  • 每个 run 记录 subject 与 scopes，供审计。
  • 工具权限按 run 的任务能力投影，不按全局角色。
  • 写操作与高风险工具仍走审批，不因“服务化”绕过。

配额与限流

  • tenant token bucket：capacity 允许突发，refill 控制均值。
  • 429 必须带 Retry-After（RFC 6585）。
  • 限流键至少是 tenant；需要时可加 endpoint / model。
  • 正常重试不重复扣配额：先查幂等，再扣 token。
  • 限流器故障默认 fail open，但要有 kill switch 与指标。

并发与排队

  • 并发限制保护 worker、连接池、内存和模型配额。
  • 队列必须有界；满了返回 503，不无限堆积。
  • queue full 时退还刚扣的配额 token。
  • 区分 429（租户问题）与 503（系统问题）。
  • critical 流量可预留容量；普通流量先被 shed。

自适应与降级

  • 过载时按 max(0, (requests − K×accepts)/(requests+1)) 本地拒绝。
  • K 通常取 2；K < 1 会把健康后端也 shed 掉。
  • 拒绝只针对非关键任务；关键任务保留通道。
  • 恢复要慢，避免在过载与空闲之间抖动。

依据：Stripe 的 request rate limiter / concurrent requests limiter / load shedder； Google SRE 的 client-side adaptive throttling；RFC 6585 的 429 与 Retry-After。

05超时、取消与重试

deadline = 客户端总预算 · step timeout = remaining budget 每一层只拿剩余预算，不要每层重新起算。
client deadline 30s └─ server run deadline 25s └─ step deadline 10s └─ tool timeout 8s └─ retry delay 从 remaining 里扣 full jitter: delay = uniform(0, min(max_delay, base × 2^retry_index)) retry 放大: 3 attempts × 5 layers = 3^5 = 243 次下游调用

超时

  • 每个远程调用都必须有 deadline，覆盖 DNS/TLS/连接/读取。
  • 超时值来自下游延迟分布，不是拍脑袋。
  • 超时要能取消底层工作，不能只是客户端放弃等待。
  • 运行级 deadline 触发后标记 failed + partial evidence。

取消

  • 任务只在 await 点能被取消；每步要有 yield point。
  • phase 边界检查 should_stop()，不要在副作用中间取消。
  • 取消是协作式的；HTTP 断开不应自动取消昂贵 run。
  • 取消后仍要写 terminal 状态与 done 事件。

重试

  • 只重试 timeout / 429 / 503 / 连接重置。
  • 不重试 400 / 401 / 403 / 404 / 422 / 策略拒绝。
  • 指数退避 + full jitter；设置最大尝试次数与最大延迟。
  • 只让一层拥有重试权；多层重试会指数放大。
  • 重试从 token bucket 预算扣；成功可回补。

幂等

  • POST 创建 run 必须带 Idempotency-Key。
  • key 绑定 payload fingerprint；不同 payload → 422。
  • 进行中重复 → 409 + Location；已完成 → 原结果。
  • key TTL 要覆盖客户端最长重试窗口。
  • 副作用账本按 (run_id, phase) 去重，不靠“应该不会重跑”。

06SSE 线格式与恢复

Content-Type: text/event-stream Cache-Control: no-cache X-Accel-Buffering: no retry: 2000 id: 7 event: phase_started data: {"phase":"retrieve_logs","index":1} : ping id: 8 event: done data: {"status":"succeeded"}

线格式

  • UTF-8 文本；事件之间用空行分隔。
  • data: 多行会拼接；JSON 保持单行最简单。
  • id: 单调递增；浏览器重连时回传 Last-Event-ID。
  • retry: 毫秒整数，设置重连等待。
  • : 开头是注释，可用作 keep-alive ping。

恢复语义

  • 事件日志是环形缓冲区；必须处理“请求的 id 已被淘汰”。
  • gap 时先发 snapshot（状态 + 结果 + last id），再发保留事件。
  • snapshot 的 id 设为第一个保留事件之前，保证单调。
  • terminal run 重放完直接关闭，不发多余 ping。
  • 客户端收到 done 后仍 GET 一次结果。

背压

  • SSE 没有应用层流控；不能给慢消费者无限缓冲。
  • 每个订阅者有有界队列；满了丢弃最旧事件并断开。
  • overflow 事件携带“最后真正送达的 id”，不是 run 的 last id。
  • 让客户端用 Last-Event-ID 重连补齐，而不是服务端阻塞。

代理与部署

  • Nginx 要关 buffering：X-Accel-Buffering: no。
  • FastAPI 0.135+ 的 EventSourceResponse 自动设头并每 15s ping。
  • HTTP/1.1 每浏览器每域约 6 条连接；HTTP/2 多路复用。
  • 多 worker 时事件日志与订阅广播必须外置。
错误发生在 200 之后

SSE 一旦开始发送，HTTP 状态码已经锁定为 200。运行中失败必须发 event: error，再发 event: done；客户端要同时处理 “流内错误”和“连接断开”两种失败，不能只检查 HTTP 状态。

07关停与恢复顺序

1. 收到 SIGTERM / 删除事件 2. readiness → false（负载均衡器停止导流） 3. 拒绝新 run：503 draining 4. 在 grace period 内等待在飞 run 完成 5. 超时：取消 worker，在最后完成的 phase 写 checkpoint · 先写 effect，再写 checkpoint · effect ledger 按 (run_id, phase) 去重 6. 进程退出（SIGKILL 之前） 7. 新进程启动： · 扫描 status=queued 的 run · 从 checkpoint.phase_index 继续 · 已产生的 effect 跳过，不重复发评论/开 PR
边界错误做法正确做法
readiness关停时仍返回 200立即 503；liveness 保持 200 直到退出
新请求继续接受，最后被 SIGKILLdraining 阶段直接 503
在飞 run等所有 run 跑完（可能几小时）等 grace period，超时 checkpoint
副作用checkpoint 先写、effect 后写effect 先落盘，ledger 去重，再 checkpoint

10一手来源

  • FastAPI — Concurrency and async / await：def 走线程池、async def 直接 await；阻塞调用不要放进事件循环。
  • FastAPI — Server-Sent Events：EventSourceResponse / ServerSentEvent、自动 keep-alive、Last-Event-ID。
  • WHATWG HTML — Server-sent events：last event ID、重连、Last-Event-ID、UTF-8 与解析规则。
  • MDN — Using server-sent events：单向、事件格式、HTTP/1.1 连接上限。
  • Python asyncio — Task cancellation：任务只在 await 点响应取消；清理要 shield 关键步骤。
  • AWS Builders' Library — Timeouts, retries, and backoff with jitter：timeout 取 p99.9、retry 是自私的、full jitter、retry token bucket、5 层 × 3 次 = 243。
  • Google SRE Book — Handling Overload：client-side adaptive throttling 公式与 K 的取值。
  • Stripe — Scaling your API with rate limiters：request rate limiter、concurrent requests limiter、load shedder。
  • RFC 6585 §4 — 429 Too Many Requests：429 语义与 Retry-After。
  • IETF — Idempotency-Key HTTP Header Field：key 唯一性、fingerprint、409 / 422 语义（Active Internet-Draft）。
  • FastAPI — Background Tasks：同进程、小任务；重活要用外部 job queue。
  • Kubernetes — Pod termination：SIGTERM、terminationGracePeriodSeconds、preStop、endpoint 摘除与 SIGKILL。
  • Uvicorn — Deployment：workers、spawn、代理头 --forwarded-allow-ips、滚动重启。
