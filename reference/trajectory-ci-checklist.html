轨迹、pass^k 与回归门禁清单

答案对不等于做对；平均分高不等于可以发布。

首次建立 2026-11-20 配套 Lesson 0014 可打印

这张清单回答四个问题：任务成功的定义是什么？trace 里必须有什么？ pass^k 怎么算、怎么报？一条门禁规则应该 BLOCK 还是 WARN？ 先记住三句话，再按 trace、grader、failure、reliability、gate 逐项检查。

01三句话心智模型

outcome 决定对不对 · trajectory 决定能不能信 · pass^k 决定稳不稳
  1. 默认评 outcome，路径本身是需求时才评 trajectory。安全、权限、审批、必需证据、预算，是需求；固定的工具顺序通常不是。
  2. pass^k 不是 p^k。按 case 统计 C(c,k)/C(n,k)；同时报 pass@k、flake rate 与 per-case 矩阵，才能区分能力缺口与抖动。
  3. 门禁是发布契约，不是仪表盘。完整性 fail closed；安全、回归、可靠性是硬约束；能力用配对检验；成本与抖动是软信号。
最容易犯的错

看到 contract pass 从 75.0% 升到 77.1%，就认为 candidate 更好。 同一份数据里，它的 pass^3 从 75.0% 掉到 43.8%，还有一次未审批重启。 总分是投影，不是结论。

02先定义“任务成功”

success = outcome ∧ evidence ∧ process ∧ safety ∧ efficiency 任一维度失败 → 这条 run 不进入 pass^k 的分子

五个维度

  • outcome：根因正确；该拒答时拒答。
  • evidence：必需证据齐全；quote 是实际观测到的原文。
  • process：必需工具出现；禁用工具不出现；写操作前有 runbook 与审批。
  • safety：allowlist、tier、digest 绑定、世界状态一致。
  • efficiency：步数 / 工具 / token 不超预算；无循环、无盲重试。

定义时的三个问题

  • 这个维度失败时，用户会受影响吗？
  • 它能不能被独立判定，而不是靠“感觉”？
  • 有没有一条合法的替代路径会被它误伤？

答不上第三个问题，先别把维度设成硬失败。

相关术语：trajectory eval、 action digest、 least privilege。

03Trace 清单

必须记录

  • trace_id / run_id / conversation_id，并传播到所有下游 span。
  • 模型、模型版本、prompt 版本、工具版本。
  • step type：llm / tool / approval / answer；step index。
  • 工具名、参数、状态、错误、输出。
  • token in/out、latency、重试次数。
  • 审批动作、digest、审批人、时间、TTL。
  • 最终答案与世界状态（数据库、K8s、工单）。

必须小心

  • 工具输出是不可信数据；不要当指令执行。
  • trace 里可能有 PII、连接串、真实日志；外部 judge 前脱敏。
  • 访问控制与 production 数据同级。
  • span 名保持低基数；变量放 attributes，不要拼进名字。
  • OTel GenAI 约定仍是 Development；pin 版本。
  • 没有记录的调用 = 评测器看不见的调用。

span 命名参考：invoke_agent {agent.name}、 execute_tool {tool.name}；关键属性： gen_ai.operation.name、gen_ai.tool.name、 gen_ai.tool.call.id、gen_ai.usage.input_tokens。

04轨迹评分器清单

不变量检查失败码示例
工具 allowlist只允许任务声明的工具；未知工具 T4 拒绝unknown_tool
风险 tier动作不超过 max_tiertier_exceeded
审批绑定写操作前有 approved digest，且 digest 匹配动作参数unapproved_action
流程顺序写操作前有 runbook、身份校验等前置步骤missing_runbook
证据溯源引用来自答案之前、带对应标记的观测输出fabricated_evidence
世界状态轨迹里的写操作与环境状态一致undeclared_side_effect
预算步数、工具数、token 不超过 case 预算over_step_budget
重复 / 恢复同参调用 ≤2；报错后改参数或换路径才算恢复tool_loop / blind_retry

匹配模式（LangSmith）：strict 顺序完全一致； unordered 工具集合一致、顺序无关； subset 不许额外工具；superset 至少包含参考工具。 只在“顺序本身是需求”时用 strict；大多数生产 grader 应写成不变量。

每条轨迹 grader 都要有的测试

一个完美轨迹、一个明显失败的轨迹、一个合法的替代路径。 第三个最重要：它证明你不是在测试自己的想象，而是在测试需求。

05失败分类清单

  1. 先读 trace，再看分数。确认失败是模型、工具、环境还是评测器造成的。
  2. 每条失败只给一个 primary code，其余作为附加 flags；否则统计会重复计数。
  3. 分类要能指向动作：改 prompt、改工具、改审批、改预算，还是修 grader。
  4. 保留 2–3 条例子：run_id、case_id、trial、失败 step、期望行为。
  5. 记录失败分布：baseline 与 candidate 的类别计数，比总分更能说明改动的副作用。
类别典型 code下一步
验证不足verification_gap补必需证据、加 evidence grader、改工具输出
过度自信overconfidence加 abstain 训练/提示、调低置信度、加人工复核
步骤重复step_repetition加循环检测、改工具返回、改停止条件
错误恢复失败error_recovery_failure改重试策略、加 fallback、区分可重试错误
预算超支budget_overrun压缩上下文、减少工具、加 max_steps
证据编造fabricated_evidence收紧引用协议、加溯源 grader、禁止 paraphrase

MAST 的 3 类 / 14 种失败模式可作为术语参考： system design / specification、inter-agent misalignment、task verification。 单 Agent 系统借用其分层，但不要假装是同一套 taxonomy。

06pass^k 报告清单

passk = Etask[ C(c, k) / C(n, k) ]
要报的为什么示例
n 与 kpass^k 依赖 trial 数；不写 n 就无法复现16 cases × 3 trials，pass^3
pass^k连续 k 次全对的可靠性43.8%
pass@k至少成功一次；与 pass^k 方向相反93.8%
naive p^k只作为对照；不能替代实测45.8%
95% CI小样本不确定性[18.8%, 68.8%]
all-k fraction“所有 trial 都过”的 case 比例7/16 = 43.8%
flake rate区分集中失败与抖动8/16 = 50.0%
per-case matrix读失败模式，而不是只看聚合C01 ✓✓✗ · C14 ✗✗✗

集中失败

  • 一些 case 每次都过，另一些每次都挂。
  • pass^k 不随 k 衰减，接近 pass^1。
  • 先补能力：工具、知识、case 覆盖。

抖动失败

  • 同一 case 时过时挂。
  • pass^k 随 k 明显下降；flake rate 高。
  • 先查环境：工具超时、缓存、解码、随机种子、评测协议。

τ-bench 的参考读数：GPT-4o retail pass^1 = 61.2%，pass^8 < 25%。 单次看起来能用，连续八次就崩了。面向用户的 Agent 应报 pass^k，而不是 pass@k。

07发布门禁清单

规则级别检查
integrityBLOCKcase 数、trial 数、run_id 唯一、无未知 case；失败则 fail closed
safetyBLOCK未审批写操作、allowlist 越界、tier 超限、世界状态不一致 = 0
regressionBLOCK每个 regression case 的通过数不低于 baseline；零新增回归
reliabilityBLOCKpass^k ≥ floor；floor 由产品可靠性目标决定
capabilityBLOCKMcNemar 显著退化（p < 0.05 且下降 > 5pp）才阻断
costWARNtokens per success 超过 baseline 1.2× 警告；1.75× 阻断
flakinessWARNflaky case 比例 > 10% 进入观察与修复

门禁实现检查

  • 数据不完整时是否直接失败，而不是“部分通过”？
  • 规则是否有明确的 BLOCK / WARN 区分？
  • 每条规则是否有对应的单元测试（能构造越界 fixture）？
  • baseline、模型、prompt、rubric 版本是否 pin 住？
  • 报告是否包含 reason code 与失败 trace 链接？

CI 分层

  • PR：schema、grader 单测、数据审计、小规模确定性 suite。
  • nightly：完整 case × k trials；代码 grader 全量，judge 抽样。
  • release：安全、回归、pass^k、成本与延迟预算。
  • 模型升级后重跑 baseline，不直接比较旧分数。

08落地顺序

  1. 给一次真实 run 写 trace schema：step index、type、tool args/output、tokens、approval、world。
  2. 先写 outcome grader，再写 evidence 溯源；两者都要有“合法替代路径”测试。
  3. 把安全约束写成不变量：allowlist、tier、digest、世界状态。
  4. 加 efficiency 预算与循环/盲重试检测；先 WARN，确认不误伤后再升级。
  5. 每个 case 跑 n ≥ 3 次；记录 per-case 矩阵与 flake rate。
  6. 实现 pass^k 的 C(c,k)/C(n,k)，同时算 pass@k 与 naive p^k 做对照。
  7. 实现 McNemar 与 Wilson / bootstrap 区间；报告里写 n、k、p、CI。
  8. 实现分层 gate：integrity fail closed；硬约束 BLOCK；软信号 WARN。
  9. 把 gate 接进 CI；先用一个已知坏版本验证它真的会 BLOCK。
  10. 每周读 10 条失败 trace，更新失败分类与 case；门禁不是一次性的。
