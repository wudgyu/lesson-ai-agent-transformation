01你的起点与设计逻辑

背景
资深 Java 后端；状态机、幂等、可观测性是你的母语
已有
做过 RAG / Agent Demo，但不成体系
投入
4 周全职，30+ 小时/周
目标
系统理解 + 一个真实项目，而不是刷面试题

四条设计原则

  1. 第一性原理先行。先用手写 150 行代码理解 Agent 循环，再学 LangGraph。框架是放大器，不是地基。
  2. 每周一个可运行交付物。不做“只读文章”的周。每个概念都必须落到一个能跑、能测的 lab。
  3. 评测从第一天开始。第 1 周就建 10 例评测集，第 3 周扩到 40 例；没有评测的 Agent 只能叫 demo。
  4. 用 Java 工程经验做杠杆。StateGraph 对应状态机，tool idempotency 对应接口幂等，tracing 对应链路追踪，tool schema 对应接口契约。
为什么不是先学 LangGraph

框架会替你隐藏消息协议、循环控制和状态变更。先学框架，你会在遇到“工具没被调用”“循环停不下来”“状态被覆盖”时无从下手。 第 1 周手写循环，第 2 周再用 LangGraph 重建同一个 Agent——这时你看到的是“它替我做了什么”，而不是“魔法”。

03最终项目：RepoMedic

一句话：面向 Java 微服务的排障 Agent。输入一条告警或故障描述，它自动收集代码、日志、指标、提交历史等证据， 给出带引用的根因假设与修复建议；任何高风险动作必须经过人工批准。

为什么是这个项目

  • 你的领域优势。Java 微服务、连接池、N+1、配置漂移、依赖冲突——这些判断力是你多年积累的护城河，Agent 只是把它放大。
  • 天然覆盖全部课程能力。RAG（代码/文档）、工具（日志/指标/git）、记忆（事故上下文）、HITL（重启/回滚）、评测（根因准确率）、可观测性（trace）。
  • 数据可得。用 Spring PetClinic 之类的开源 Java 项目，加上可控的故障注入与合成日志，就能构造 20–40 个可重复的评测场景。
  • 可讲、可展示。“Agent 帮我定位了一次连接池耗尽”比“我跑通了一个 LangGraph demo”有说服力得多。

05如何评估你真的学会了

每周日做三件事，检验的是 storage strength（长期留存），不是当场听懂的 fluency：

  1. 不看笔记讲 10 分钟。向一个假想的 Java 同事解释本周架构：为什么这样拆、哪个选择会被推翻、失败时怎么定位。
  2. 跑评测并解释失败。不只看通过率；挑 2 个失败轨迹，说明是模型、工具、上下文还是任务定义的问题。
  3. 做一次迁移。把本周的模式用到一个小变体上（换工具、换数据、换约束），确认不是背答案。

每周末我会把关键洞察、被纠正的误解、你展现出的能力写进 learning-records/，作为下一阶段“最近发展区”的依据。课程节奏会根据你的实际表现调整，而不是死按路线图。

06不做什么

  • 不训练/微调模型。只讲到能判断“该不该微调”的程度；重点是应用层工程。
  • 不推 Transformer 数学。理解 attention 的直觉与 context 的成本即可。
  • 不做多模态/语音 Agent。先用文本把核心循环打透。
  • 不美化前端。演示界面最小可用，把时间留给评测与可靠性。
  • 不追新框架。以 LangGraph + OpenAI Agents SDK 为主，理解原理后迁移成本很低。

07现在开始

第一课不装框架、不讲概念史。我们直接拆开 Agent 的循环，用 150 行 Python 写出一个能调用工具、 能看到每一步 trace、能自己停下来的 Agent。跑通它，你就拥有了理解后面所有框架的“源码级”参照物。
