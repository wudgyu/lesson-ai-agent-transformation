工具设计清单

给一个非确定性客户端写 API 时，逐项检查。

配套 Lesson 0002 可打印 每次新增工具时过一遍

工具是确定性的代码与非确定性的模型之间的契约。模型只读得到 name、description、 schema 和返回值；它不会读你的源码、Javadoc 或 wiki。下面的清单逐项对应这个约束。

02Schema 模板

Function schema
{
  "name": "verb_object",
  "description": "一句话说明做什么。用户问【场景 A】时使用；\n不要用于【场景 B】。默认【默认值】；\n失败时返回【错误格式】。",
  "parameters": {
    "type": "object",
    "properties": {
      "service": {
        "type": "string",
        "description": "服务名，例如 order-service"
      },
      "level": {
        "type": "string",
        "enum": ["ERROR", "WARN", "INFO", "ALL"],
        "default": "ERROR",
        "description": "先查 ERROR，需要背景时再查 WARN/INFO"
      }
    },
    "required": ["service"]
  }
}

原则：参数越少越好，但必要的边界（enum、范围、默认值）不能省。 Schema 是模型唯一能验证的契约；不要把约束藏在实现里。

03错误信息模板

ERROR: 哪里错了 · 合法值 / 下一步 · 不要做什么

坏错误

ERROR: KeyError: 'svc'
ERROR: failed
ERROR: 400

模型只能重试或编造。

好错误

ERROR: unknown service 'order-service'.
Available: inventory-service,
payment-service, order-service

ERROR: approval_id is required for
restart. Ask the on-call lead for a
valid approval; do not guess.

模型能改参数、换工具或转人工。

05评测检查

检查项最低要求
用例覆盖正常、边界、对抗（注入/越权）、应该拒答，各至少 1 条
pass答案关键事实 + 安全规则；不要把“第一步选对”硬塞进 pass
first-tool诊断指标：模型第一步是否选了合适工具
steps / tokens同一任务的平均步数与 token；用于比较工具粒度
safety写操作是否被审批拦住；是否出现越权/泄露
失败分类选错工具 / 参数写错 / 返回不可用 / 任务定义不清
回归每次改 description 或 schema 后重跑同一组用例

06上线前 8 问

  1. 如果模型把两个工具搞混，用户会看到什么？
  2. 工具返回 10 倍数据时，上下文还撑得住吗？
  3. 工具报错时，模型有没有足够信息自己恢复？
  4. 写操作在模型“猜”参数时，会不会造成不可逆后果？
  5. 同一请求重试两次，会发生什么？
  6. 换一个更便宜/更笨的模型，工具还能用吗？
  7. 把系统提示词删掉，安全性还剩多少？
  8. 你能用一条 trace 解释一次失败吗？
