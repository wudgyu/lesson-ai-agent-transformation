多 Agent 决策清单

先证明单 Agent 不够，再拆；拆的是上下文，不是组织架构。

首次建立 2026-11-10 配套 Lesson 0010 Supervisor · Handoff · Sub-agent 可打印

这张清单只回答一个问题：什么时候值得把一个 Agent 拆成多个，拆完以后靠什么保证它不比单 Agent 更糟？ 先记住三句话，再按拓扑、委派契约、预算、失败模式与评测逐项检查。

01三句话心智模型

supervisor 保持控制 · handoff 转移控制 · sub-agent 隔离上下文
  1. 多 Agent 不减少总 token，只把 token 移出主上下文。Anthropic 的工程复盘显示，多 Agent 系统约消耗聊天场景的 15 倍 token；收益是主线程更小、可并行、权限可隔离，不是“更便宜”。
  2. 只有子任务能独立决策时，拆分才安全。Cognition 的反方观点：动作携带隐含决策；两个子 Agent 看不到彼此的动作，就会产生互相冲突的假设。拆分的前提是委派契约足够完整，且子任务之间不需要共享中间决策。
  3. 先从单 Agent 开始，用评测证明某个指标不够，再增加一个 specialist。OpenAI 的指南也是同一句话：只在能力/策略隔离、prompt 清晰度或 trace 可读性有可测收益时才拆。
最容易犯的错

按“组织架构”拆 Agent：planner、researcher、writer、reviewer 各一个。 这不是架构，是角色扮演。拆分的依据必须是上下文边界、工具/权限边界、并行收益， 而不是人类团队的岗位名称。

02三种拓扑：控制权在哪

拓扑控制权上下文适合主要风险
Supervisor
orchestrator-worker / agents-as-tools		 留在 lead；worker 是受控调用，结果返回 lead 每个 worker 新上下文；只把摘要与证据带回主线程 可独立并行的子任务、工具很多、信息超过一个窗口、需要权限隔离 委派开销、重复/遗漏、lead 被摘要淹没、worker 看不到彼此的隐含决策
Handoff 转移给 specialist；specialist 可以直接面对用户或继续转交 共享会话状态；需要显式过滤/摘要消息 有状态的多轮对话、顺序阶段、每个阶段有不同指令/工具/策略 上下文污染、工具调用与 ToolMessage 配对错误、控制流复杂
Sub-agent 被 lead 调用；通常作为工具 全新窗口；只返回精简结论 一次深挖、保护主上下文、隔离大量原始材料 丢掉父级约束、重复父级已做的工作、结论不可核查

拓扑不是互斥的：一个 handoff 的 specialist 内部可以再调用 sub-agent； 一个 supervisor 的 worker 也可以是一个小图。关键是控制权和上下文边界， 不是节点数量。

2026 框架现状

LangGraph 官方的 langgraph-supervisor 包已不再积极维护，文档建议改用 “把 subagent 包成 tool” 或 handoff 的 Command 写法； 本课的 lab 直接用 StateGraph + 子图实现，不依赖该包。 OpenAI Agents SDK 则提供 Agent.as_tool()（manager 模式）与 handoffs=[...]（控制转移）两种原语。

03决策树：先问四个问题

Q0. 你有没有单 Agent 的基线评测？

没有 → 先建 20 例评测集，跑单 Agent。没有基线，“多 Agent 更好”只是感觉。
有 → 进入 Q1。

Q1. 失败是否来自“主上下文太满/工具太多/权限太宽”？

否 → 先修工具、上下文工程或单 Agent 循环，不要拆。
是 → 进入 Q2。

Q2. 子任务能否独立完成，并且能用 schema 验收？

否 → 用单 Agent，或 handoff 共享上下文；不要用 supervisor 硬拆。
是 → 进入 Q3。

Q3. specialist 需要直接和用户多轮对话吗？

是 → Handoff：按阶段转移控制，显式过滤历史。
否 → Supervisor / sub-agent：worker 返回摘要，lead 汇总并回答。

典型的“值得拆”信号

  • 上下文超限：单个子任务就要读 50–200 个文件或上万行日志，且只需返回几条结论。
  • 工具选择困难：单 Agent 有 15+ 工具，评测显示经常选错；按领域拆成 3–5 个工具集更窄的 worker。
  • 权限/策略隔离：读代码与执行重启需要不同审批、不同沙箱、不同模型。
  • 可并行：日志、代码、runbook 三条调查线互不依赖，能同时跑。

典型的“不该拆”信号

  • 任务强耦合：后一步必须看到前一步的全部动作与中间决策（大多数编码任务）。
  • 只是“角色听起来更专业”：planner / researcher / writer / reviewer。
  • 子任务很小，委派契约比任务本身还长。
  • 没有评测，只是想让架构图看起来更高级。

04委派契约：sub-agent 的接口

supervisor 与 worker 之间不是“喊一句话”，而是一份可验收的接口契约。 契约缺失时，最常见的结果是重复劳动、遗漏和“看起来完成了”。

objective: 一句话说明这次调查要回答什么 inputs: 允许读取的数据、文件、日志窗口、事故 ID must_consider: 父级已确认的约束与决策（不要重新推翻） tools: 只给完成这件事所需的最小工具集 output_schema: {finding, evidence[], confidence, open_questions[]} budget: max_steps / max_tokens / deadline stop: 什么条件下必须停下并返回 partial

坏委派

查一下 order-service 的日志。

  • 没有时间窗口与服务水平
  • 没有输出格式，worker 只能自由发挥
  • 父级已知的“先别重启”约束丢失
  • 无法判断返回是否完整

好委派

在 20:00–20:10 的 order-service 日志中，找出连接池耗尽的直接证据；只返回 3 条带时间戳的日志与错误码。不要提出修复动作；父级已决定暂不重启。

  • 范围、输出、边界、已知决策齐全
  • 返回可被 schema 校验
  • 父级可以据此审计证据
Cognition 的第二条原则

“Actions carry implicit decisions.” 如果 worker 必须知道另一个 worker 已经改了什么、查了什么， 那么在委派契约里显式写进去；写不进去，就说明这两个任务不该拆。 只传任务描述、不传已做决策，是冲突假设的温床。

05预算、去重与停止条件

预算

  • agent 数上限：从 3–5 开始，不超过任务需要的领域数
  • 每个 worker 有 max_steps / max_tokens
  • 整个 run 有总 token 与 deadline
  • handoff 次数有上限，防止来回踢皮球

去重

  • 委派任务带稳定 key：agent:query_hash
  • 已执行 key 写入 run state，避免重复调查
  • worker 返回 open_questions，由 lead 决定是否再派
  • 并行 worker 之间不要写同一个外部资源

停止

  • 所有计划领域都有 finding，或预算耗尽
  • 剩余 open question 无法在预算内回答 → partial
  • worker 连续失败两次 → 降级，不再重试
  • 答案必须标注证据覆盖与未解决项

可观测

  • 每次委派一个 span：parent_run_id + worker_run_id
  • 记录契约、返回、token、工具调用、耗时
  • trace 里能区分“委派错”与“worker 做错”
  • handoff 记录 from / to / reason / 过滤后的历史

06失败模式：MAST 三类 + 工程对策

“Why Do Multi-Agent LLM Systems Fail?”（MAST）标注了 1,600+ 条轨迹、7 个框架， 归纳出 14 种失败模式，分属三类：system design、 inter-agent misalignment、task verification。 下面是最常撞上的六种，以及可直接落地的对策。

失败模式表现对策
委派含糊两个 worker 查同一件事，另一条线没人查委派契约 + 稳定 task key + 计划清单
上下文缺失worker 不知道父级已排除的方案，提出冲突建议把已确认约束写进 must_consider；强耦合任务改 handoff/单 Agent
过度拆分简单问题起 10 个 agent，token 与延迟爆炸单 Agent 基线 + “一个 specialist 一条可测收益”
无限往返agent 之间 handoff 不停，或 supervisor 反复重试handoff/max_steps/重试上限；失败两次即降级
验证缺口lead 直接相信 worker 的结论，没有证据worker 必须返回 evidence + confidence；lead 做引用检查
历史损坏handoff 后消息角色/ tool_call 配对错乱显式过滤历史；保留触发 handoff 的 AIMessage + ToolMessage
Anthropic 的真实翻车记录

早期多 Agent 研究系统曾为简单查询创建 50 个 subagent、为不存在的来源无限搜索、 subagent 之间互相重复工作；还有 subagent 偏好 SEO 内容农场而不是高信任来源。 这些都不是模型“笨”，而是委派、工具描述与验证设计的问题。

07评测：和单 Agent 基线比什么

指标问题怎么测
Task success最终答案是否正确、完整？20 例起；rubric 或 LLM judge + 人工抽检
Evidence coverage该找的证据是否都找到了？期望证据清单 / 实际引用；按 agent 分域统计
Token / cost多花的 token 买到了什么？按 run 记账：lead + worker + 重试 + 汇总
Tool efficiency有没有重复调用、无效调用？tool_calls / task；重复 key 比例
Latency并行是否真的降低了墙钟时间？p50 / p95；区分串行与并行
Coordination委派是否准确？handoff 是否必要？轨迹规则：agent 选择、handoff 次数、遗漏任务
Safety权限是否越界？高风险动作是否审批？注入/越权测试集；工具白名单断言

评测单位不是“最终答案”，而是轨迹：哪个 agent 被派出、拿到什么上下文、 调了什么工具、返回了什么证据、lead 如何汇总。没有轨迹，你无法区分 “架构不对”和“某个 worker 的 prompt 不对”。

08最小代码骨架

Supervisor 的核心不是某个包，而是把 subagent 包成一个有 schema 的工具， 由 lead 决定调用谁、传什么、如何汇总。下面是最小形态： 

from langchain.agents import create_agent
from langchain.tools import tool

worker = create_agent(model="...", tools=[query_logs, check_health])

@tool("investigate_logs", description="在给定时间窗内查日志，返回 3 条证据")
def investigate_logs(query: str) -> dict:
    result = worker.invoke({"messages": [{"role": "user", "content": query}]})
    return {
        "finding": result["messages"][-1].content,
        "evidence": [],          # worker 必须回传证据
        "confidence": "medium",
        "open_questions": [],
    }

lead = create_agent(model="...", tools=[investigate_logs, investigate_code])

Handoff 的核心是用状态决定下一个节点：specialist 返回 Command(goto=..., update={"active_agent": ...})，把控制权交给下一段。 关键是显式决定哪些消息随控制权一起过去： 

from langgraph.types import Command

def transfer_to_code(state):
    return Command(
        goto="code_agent",
        update={
            "active_agent": "code",
            # 只传 handoff 触发消息与 ToolMessage，不传整个内部轨迹
            "messages": filter_handoff_messages(state["messages"]),
        },
    )
不要用框架包代替设计

langgraph-supervisor 之类的封装能省几十行代码，但不会替你想清楚委派契约、 上下文过滤、去重与预算。先把这些写进 state 和测试，再决定要不要用封装。 本课 lab 用 StateGraph 直接实现，就是为了让每个决策可见。
