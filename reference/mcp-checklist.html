MCP 设计与接入清单

协议统一接口，host 决定信任；发现工具不等于把工具交给模型。

首次建立 2026-11-12 配套 Lesson 0011 MCP 2026-07-28 可打印

这张清单回答两个问题：作为 server，怎样把能力暴露得让任何客户端都能用？ 作为 host/client，怎样在不信任 server 的前提下安全地使用它？ 先记住三句话，再按原语、协议、传输、客户端策略与安全逐项检查。

01三句话心智模型

MCP 是接口 · server 暴露能力 · host 决定信任
  1. MCP 不是 Agent 框架。它不决定循环、不决定何时停止、不做规划。它只规定“能力如何被发现、调用、返回”。Agent 的控制流仍然是你的代码或图。
  2. MCP 不是 function calling 的替代品。Function calling 是模型输出“我要调用某工具”的格式；MCP 是工具提供方与消费方之间的协议。两者可以串联：MCP 发现工具 → 投影成 function schema → 模型选择 → client 执行 MCP 调用。
  3. MCP 不提供信任。server 是外部代码；它的工具描述、schema、结果都是不可信输入。host 必须自己做 allowlist、审批、超时、审计与输出隔离。
最容易犯的错

把 MCP 当成“插件市场”：装上 server，把 `tools/list` 原样塞进模型上下文。 工具越多，schema 越贵、选择越难、攻击面越大。正确顺序是： 发现 → 筛选/投影 → 授权 → 调用 → 审计。

03Server 端清单

工具契约

  • 名字短、动词开头、全局唯一；多 server 聚合时加前缀（repomedic.query_logs）。
  • description 当 prompt 写：做什么、何时用、返回什么、不要做什么。
  • inputSchema 用类型、枚举、范围、默认值；不要靠描述约束参数。
  • 有结构化返回就声明 outputSchema，并返回 structuredContent。
  • 预期错误用 ToolError 返回可自纠正的消息；协议错误只用于请求本身有问题。
  • 工具列表保持确定性顺序，利于缓存与 prompt cache。

资源与提示

  • 资源 URI 稳定、可读、不可猜；模板参数与函数参数一一对应。
  • 声明 mimeType；文本返回 text，二进制返回 blob。
  • 资源不存在返回 -32602（Invalid Params）；不要返回空 contents。
  • prompt 参数是字符串；缺必填参数返回 -32602。
  • prompt 内容由 server 定义，但是否使用由用户决定。

安全与运行

  • 校验所有输入；对外部调用设超时、限流、重试上限。
  • 工具输出可能包含注入文本；不要假设客户端会消毒。
  • 敏感资源做访问控制；文件路径做穿越检查。
  • 远程部署用 OAuth 2.1；校验 token 的 audience，禁止 token passthrough。
  • 不要依赖协议级 session；跨调用状态用显式 handle。
  • stdio server 以客户端权限运行；安装前审查启动命令。

注解（只是提示）

  • readOnlyHint：不改变外部状态。
  • destructiveHint：可能造成破坏性变更。
  • idempotentHint：重复调用效果相同。
  • openWorldHint：会与外部世界交互。
  • 注解来自 server，默认不可信；host 必须用策略强制，而不是相信注解。

04Host / Client 端清单

发现与投影

  • 维护可信 server 注册表；不要自动连接任意 URL。
  • 先 server/discover 读版本与 capabilities，再决定用哪些方法。
  • 按任务投影工具：只把当前需要的 3–5 个放进模型上下文。
  • 统计 schema token；工具越多，选择越难、成本越高。
  • 聚合多个 server 时给工具名加前缀，处理重名。

调用与授权

  • allowlist 之外的工具直接拒绝，不询问模型。
  • 写操作默认拒绝；人工审批后放行，并记录审批人。
  • 写操作带稳定 idempotency key；重复调用返回同一结果。
  • 每次调用设超时、最大输出、重试上限。
  • 审计：工具名、参数摘要、结果状态、审批、耗时、server 身份。

输出与上下文

  • 把工具输出标记为不可信数据（来源、工具名、截断）。
  • 不要把原始输出直接拼进 system prompt。
  • 结构化输出优先用 structuredContent，文本块只作兼容。
  • 大输出先截断/摘要；保留证据 URI 供追问。
  • 区分“工具返回的数据”和“模型自己的结论”。

失败与兼容

  • isError=true 是工具执行错误，可反馈给模型重试。
  • JSON-RPC error 是协议/请求错误，通常不该让模型反复重试。
  • 老 server 没有 server/discover：探测后回退到 initialize。
  • 2026-07-28 断流不重放；用新 request id 重发，并保证幂等。
  • server 不可用时降级为“证据不足”，不要伪造结果。

052026-07-28 协议要点

变化工程含义
无状态核心没有 initialize/initialized、没有 Mcp-Session-Id。每个请求在 _meta 携带 protocolVersion、clientInfo、clientCapabilities；可以放在轮询负载均衡后面。
server/discoverserver 必须实现，返回支持的版本、capabilities、身份。client 可先探测再选版本；老 server 用它做兼容探测。
每次请求自带能力capabilities 不再“连接时协商一次”，而是每个请求的输入。server 必须按请求鉴权，不能按连接记忆。
列表不随连接变化tools/list、resources/list、prompts/list 可随授权变化，但不得因连接或其它请求的副作用变化。
subscriptions/listen取代 HTTP GET 流与 resources/subscribe；一个长连接流承载显式订阅的变更通知。
MRTRserver 需要额外输入时返回 InputRequiredResult；client 带 inputResponses 重试原请求。取代 server-initiated sampling/elicitation/roots。
无 SSE 重放断流即丢请求；client 用新 request id 重发。幂等键比“断线重连”更重要。
Tasks 是扩展长任务从核心移到 io.modelcontextprotocol/tasks 扩展；按需支持，不要假设所有 server 都有。
弃用Roots、Sampling、Logging、HTTP+SSE、DCR 进入弃用/替代路径；新实现不要采用。
版本兼容

2025-11-25 及更早的 server 仍使用 initialize 握手与 session。 客户端应使用 SDK 的 mode="auto"（或等价探测）先试 2026-07-28，再回退。 不要在代码里硬编码“所有 server 都是最新版”。

06传输选择

stdioStreamable HTTP
形态client 启动 server 子进程；JSON-RPC 走 stdin/stdoutHTTP POST + 可选流式响应；默认 /mcp
适合本地工具、IDE 插件、单用户桌面远程服务、多用户、水平扩展
身份继承本地用户权限；靠进程隔离OAuth 2.1 / CIMD；token audience 校验
注意安装即执行代码；审查启动命令，沙箱化Mcp-Method/Mcp-Name 头；无 session；SSRF 防护

HTTP+SSE 是旧传输，已弃用。新实现只用 Streamable HTTP；不要为一个新 server 选 SSE。

08接入评测：别只看“能连上”

指标回答的问题怎么测
Discovery correctness该发现的工具/资源都发现了吗？名字与 schema 对吗？对 server 契约做快照测试；检查确定性顺序
Schema cost把所有工具塞进上下文要多少 token？投影后省多少？序列化 function schema，按 tokenizer 计数；对比全量与任务级
Tool-selection accuracy模型是否选中了正确工具与参数？20 例任务 → 期望工具；混淆矩阵
Policy enforcement未授权/未审批的调用是否 100% 被拦截？负向测试：allowlist 外、无审批、重复幂等键
Error recovery工具失败后模型能否自纠正？注入 4xx/超时/空结果；看轨迹是否重试或降级
Latency overheadMCP 比进程内函数多多少延迟？p50/p95；区分 stdio 与 HTTP；含冷启动

RepoMedic lab 的参考值：4 个工具的 schema 约 1419 token；triage 只投影 3 个后约 992 token， 省下约 30%。这不是“模型更聪明”，而是把上下文预算花在当前任务上。
