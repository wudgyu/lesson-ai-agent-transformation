Tracing、成本与延迟预算清单

trace 是一等数据；账单不是 token 总数；延迟看 active 与 critical path。

首次建立 2026-11-21 配套 Lesson 0015 可打印

这张清单回答四个问题：一次 run 的 trace 里必须有什么？token 账单怎么算才不重复？ 延迟预算该按 wall 还是 active？哪些异常必须阻断发布？先记住三句话，再按 trace、账本、延迟、面板、采样逐项检查。

01三句话心智模型

trace 是一等数据 · 账单按叶子 inference 计 · 延迟看 active 与 critical path
  1. 先有树，再有指标。没有父子关系、起止时间与 operation 归属，token 与耗时都无法归因；日志再多也只是文本。
  2. agent span 的 usage 是汇总，不是账单行。只从叶子 inference span 计费；对所有带 usage 的 span 求和会把同一批 token 算两遍。
  3. wall ≠ active ≠ critical path。wall 含审批等待；active 扣掉审批；critical path 是决定结束时间的依赖链，并行工具不能相加。
最容易犯的错

看到 agent span 上有 gen_ai.usage.input_tokens，又看到每个 LLM 子 span 上也有， 就把它们全部加起来。结果是成本翻倍，还找不到原因。先问：这个 usage 是“汇总”还是“本次调用”？

02Trace 清单

每个 span 必须有

  • trace_id：贯穿一次 run。
  • span_id / parent_id：能重建树。
  • name：低基数、可聚合；不要把用户输入塞进名字。
  • kind：agent / llm / tool / approval / retrieval / guardrail。
  • start_ms / end_ms：同一时钟源；子区间落在父区间内。
  • status：ok / error；错误要有 error.type。
  • operation.name：invoke_agent / chat / execute_tool / retrieval。

一次 agent run 还必须有

  • run / conversation / tenant / case 的关联 ID。
  • model、prompt 版本、agent 版本、工具版本。
  • 工具名、调用 ID、参数摘要、状态、错误。
  • usage：input / output / cache_read / cache_write / reasoning。
  • 审批：动作、digest、审批人、决定、等待时长。
  • 最终答案与世界状态（数据库、K8s、工单）。
隐私默认值

不要把完整 prompt / completion / 工具参数默认写进 span。OTel 把 gen_ai.input.messages、gen_ai.output.messages、 gen_ai.system_instructions、gen_ai.tool.definitions 定义为 opt-in。默认只记元数据；需要采样内容时先脱敏，再单独授权。

03OpenTelemetry GenAI 属性速查

2026-11 核验：GenAI 约定仍在独立仓库 semantic-conventions-genai， 状态为 Development。实现时要 pin 版本；属性名会变。

属性级别用途 / 注意
gen_ai.operation.nameRequiredchat / text_completion / embeddings / invoke_agent / execute_tool / retrieval。汇总 token 时先按它过滤。
gen_ai.provider.nameRequired替代旧的 gen_ai.system；例：openai、anthropic、aws.bedrock。
gen_ai.request.modelConditional请求的模型名；价格表按它匹配。
gen_ai.response.modelRecommended实际响应的模型名；可能因路由/别名不同。
gen_ai.usage.input_tokensRecommended包含 cache read / cache write / 各模态；不是“未缓存输入”。
gen_ai.usage.output_tokensRecommended包含 reasoning 与各模态输出。
gen_ai.usage.cache_read.input_tokensRecommendedinput 的子集；按 cache 价计费。
gen_ai.usage.cache_write.input_tokensRecommendedinput 的子集；部分供应商收写入溢价。
gen_ai.usage.reasoning.output_tokensRecommendedoutput 的子集；通常按 output 价计费，不要额外再加一次。
gen_ai.agent.nameConditional低基数；不要用 StateGraph 这类框架类型名。
gen_ai.tool.nameConditional工具名；与 gen_ai.tool.call.id 一起定位一次调用。
gen_ai.tool.call.idConditional把 tool span 与消息里的 tool_call 对上。
指标 vs span

总量、成本、SLO 用 metrics（gen_ai.client.inference.usage.* 计数器与 gen_ai.client.operation.duration 直方图）；单次为什么贵、为什么慢用 trace。 metrics 不受 trace sampling 影响，span 会。不要拿“采样后的 trace 总和”当账单。

04Token 账本

billed_input = input_tokens = uncached_input + cache_read + cache_write uncached_input = input_tokens - cache_read - cache_write input_cost = uncached_input × input_rate + cache_read × cache_read_rate + cache_write × cache_write_rate output_cost = output_tokens × output_rate total = input_cost + output_cost

只对叶子 inference span 求和。agent span 的 usage 是它下面所有 LLM 调用的汇总；subagent、gateway、framework 层也可能重复上报。 OTel 明确提醒：不要在所有 span 上直接 sum(gen_ai.usage.*)， 要先按 gen_ai.operation.name 过滤，否则同一批 token 会被多层重复计算。

计费前的五个检查

  • 这个 span 是叶子 inference 吗？
  • usage 是 provider 报的，还是 tokenizer 估的？
  • cache_read / cache_write 是 input 的子集吗？
  • 失败调用有没有 usage？失败也要计费。
  • 用的价格是 run 发生当天生效的版本吗？

成本口径

  • cost per run：含失败 run，回答“跑一次要多少钱”。
  • cost per success：分母只放成功 run，回答“做成一件要多少钱”。
  • retry cost：失败调用 + 第 2 次及以后尝试。
  • cache savings：相对“全部按 input 价”省下的钱；写入溢价可能抵消。
  • context growth：每轮重发的历史会被反复计费，累计输入可能接近 O(T²)。
缺失 usage 时

不要用 tokenizer 估一个数填进去。显示 unknown，把成本标成下界， 并让面板 BLOCK。估算会把 instrumentation 的 bug 变成“看起来合理的账单”。 Langfuse 2026-11 已明确停止自动 tokenization，原因正是估算在 reasoning / cache 定价下会算错。

05延迟预算

wall_ms = root span 的 end - start blocked_ms = approval span 区间的并集 active_ms = wall_ms - blocked_ms critical path = DAG 最长路径 - 节点权重：exclusive = duration - union(直接子 span) - 边：parent → child；顺序执行的兄弟：前一个子树的叶子 → 后一个 - 并行兄弟之间没有边，所以不会相加

必须分开报

  • wall：用户实际等待。
  • blocked：等人审批 / 等外部系统。
  • active：模型 + 工具 + 编排的活跃时间。
  • TTFT：首 token 时间；流式体验的关键。
  • p50 / p95 / p99：不要只报平均。

预算怎么写

  • SLO 写成“百分比 × 阈值”，例如“95% 的 active run < 15s”。
  • 每个 stage 一条预算：llm、tool、approval、TTFT。
  • 单 run 上限与全局 p95 分开；长尾会被平均值藏住。
  • 审批等待单独设预算；不要混进模型延迟。
  • 预算超了先看 critical path，不要先怪模型。
尾延迟会被 fan-out 放大

单个叶子慢的概率是 p，并行 n 个叶子时， 至少一个慢的概率是 1 − (1 − p)n。 p=1%、n=100 时是 63.4%。所以“每个工具 p99 都达标” 不等于“端到端 p99 达标”；要按 trace 的 critical path 看，而不是按单个 span 看。

06面板与门禁

检查默认级别依据
trace 树 / schema 不完整BLOCK无法归因；完整性 fail closed。
inference span 缺 usageBLOCK成本不可解释；估算会掩盖 bug。
agent 汇总 ≠ 子调用之和BLOCK账本口径冲突；先修数据。
model 无价格 / 价格未生效BLOCK无法计价。
active p95 / 单 run active 超预算BLOCK延迟是发布契约（按产品定）。
cost per success 超预算WARN成本是重要信号，但不单独阻断。
cache hit rate 低WARN先确认负载是否可缓存，再优化。
retry share 高WARN查失败原因；可能同时是可靠性问题。
trace sampling 开启但用于账单BLOCK采样后的总和不是总成本；用 metrics。

面板至少四个视图

  • trace 树：一次 run 的 waterfall 与 critical path。
  • 成本：by run / by arm / by model / by step；cost per success。
  • 延迟：active p50/p95/p99；stage 分解；TTFT。
  • 可靠性：错误率、retry share、missing usage、reconcile 失败。

告警不要只看日总额

  • 用量突增可能是业务增长，也可能是 retry storm。
  • 按成功任务成本告警，比按总花费告警更接近价值。
  • 预算按“烧钱速率”与“剩余预算”双窗口看。
  • 每次价格表更新都记录生效日期，不回溯历史。

07采样、隐私与缺失数据

08七个常见坑

  1. 把所有带 usage 的 span 相加。agent + subagent + gateway + LLM 多层重复；只算叶子 inference。
  2. 把 cache_read 当额外 token。它是 input 的子集；公式是 uncached = input − cache_read − cache_write。
  3. 把 reasoning token 再加一次。它通常已包含在 output 里；先看供应商口径。
  4. 用估算补缺失 usage。估算在 reasoning / cache 定价下会错，而且会掩盖 instrumentation bug。
  5. 把并行工具时长相加。两个 7 秒并行不是 14 秒；看 union 与 critical path。
  6. 把审批等待算进模型延迟。wall 95 秒、active 7 秒时，优化模型没有意义。
  7. 用今天的价格重算历史账单。价格会变；按 trace 发生日期选择生效版本。

09和 Java 后端对照

本课概念Java 后端对应

token 账本计费/成本中心；按 tenant、endpoint、model 分摊

dashboard gate发布门禁；完整性 fail closed，SLO 硬约束，成本软信号
sampling链路采样；指标不能采样后再当总量
