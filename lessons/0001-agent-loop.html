01先拆掉一个幻觉¶

很多人对 Agent 的想象是：一个更聪明的模型，自己会思考、会搜索、会写代码。 但如果你把任何 Agent 框架的源码翻到最底层，看到的都是一个非常朴素的结构：

Agent = LLM + Tools + Loop + Stop condition

模型负责“下一步做什么”的判断；工具负责“真正做事”；循环让判断可以基于新事实反复发生； 停止条件保证它不会永远转下去。四者缺一，要么只是聊天机器人，要么只是工作流，要么是一场事故。

Anthropic 在《Building Effective Agents》里给了一个更精确的划分：

Workflow vs Agent

Workflow 是 LLM 与工具通过预先写好的代码路径编排的系统； Agent 是 LLM 动态决定自己的流程与工具使用、并掌控如何完成任务的系统。

原文：Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents are systems where LLMs dynamically direct their own processes and tool usage. 来源

维度WorkflowAgent
控制流由谁决定代码，提前写死模型，每一步动态决定
可预测性高，路径固定低，步数与路径不定
成本低且稳定随步数增长，可能失控
适合的任务步骤明确、可枚举开放式、需要随机应变
调试方式常规日志与断点必须看完整 trajectory

这不是“Agent 更高级”的等级制。Anthropic 的建议恰恰相反：先用最简单的方案， 只有当任务真的需要模型自己决定路径时，才引入 Agent 的复杂度与成本。 第 3 周的项目里，你会看到很多子任务其实应该做成 workflow，而不是 Agent。

02Agent 的最小定义¶

把公式拆开，每个零件只问一个问题：

零件它回答的问题没有它会怎样
LLM下一步做什么？调用哪个工具？什么时候停？没有决策者，只能执行固定脚本
Tools如何读取外部世界、执行动作？只能基于训练数据空谈，无法接触真实系统
Loop拿到观察后，如何继续决策？一次工具调用就结束，无法多步任务
Stop condition什么时候必须停？无限循环、成本失控、重复副作用

这里有一个容易被忽略、但极其重要的事实：

模型不执行任何工具

模型只会输出一段结构化的请求：“我想调用 read_file，参数是 {"path": "notes.txt"}”。 真正打开文件的是你的代码。所以权限、沙箱、审计、幂等，都必须做在工具层——模型无法替你把关。

这也是为什么“给 Agent 一个 shell”是高风险操作：你给的不是模型权限，而是你自己的进程权限。

一个“增强型 LLM”（augmented LLM）就是在这个最小结构上，加上检索、工具与记忆。 它既是 workflow 的积木，也是 agent 的积木。第 1 周剩下的内容，基本都在把这个结构做得更可靠： 工具怎么设计、RAG 怎么接、错误怎么恢复、预算怎么设。

03ReAct：边想边做¶

最早把这套循环讲清楚的是 2022 年的 ReAct 论文：让模型交替产生 Thought（我打算做什么）、 Action（调用哪个工具）、Observation（工具返回了什么），再把观察喂回下一轮。 关键不是“想”，而是想完之后必须接触真实世界，再根据结果修正。

为什么必须有 Observation？因为模型在生成下一步时，只能依据它“看到”的内容。 如果没有把工具的真实返回放回上下文，它就只能凭记忆猜——这正是很多“Agent 看起来很忙但结论是编的”的根源。 Observation 把下一步从猜测拉回事实。

现代 function calling 的实现里，模型的“Thought”经常是不可见的（或者被合并进 tool call 前的文本）， 但循环没有变：决策 → 调用 → 观察 → 再决策。你后面学的 LangGraph、OpenAI Agents SDK， 只是把这个循环画成了图、加上了状态与持久化。

04消息协议：模型如何“调用”工具¶

工具调用的本质是三次消息往返。假设用户问：“notes.txt 里的端口是多少？” 你的程序先把工具清单发给模型：

① 工具 schema（你的代码 → 模型）

{
  "type": "function",
  "function": {
    "name": "read_file",
    "description": "读取 sandbox 内某个文本文件的内容。path 必须是相对路径。",
    "parameters": {
      "type": "object",
      "properties": {
        "path": { "type": "string", "description": "例如 notes.txt" }
      },
      "required": ["path"]
    }
  }
}

模型不会“执行”它，而是返回一个调用请求。你的代码解析后执行工具：

② 模型返回 tool_calls（模型 → 你的代码）

{
  "role": "assistant",
  "content": "我需要先读取文件。",
  "tool_calls": [{
    "id": "call_abc123",
    "type": "function",
    "function": {
      "name": "read_file",
      "arguments": "{\"path\": \"notes.txt\"}"
    }
  }]
}

执行结果必须带着同一个 id 写回历史，否则下一轮 API 调用会直接报 400：

③ 工具结果（你的代码 → 模型）

{
  "role": "tool",
  "tool_call_id": "call_abc123",
  "content": "# 部署笔记 · order-service\n- 端口: 8081\n..."
}

tool_call_id 的配对是协议里最容易踩的坑。 模型可能一次返回多个 tool call，你的代码必须逐个执行、逐个用对应的 id 写回； 顺序错了、id 丢了、或者只写回一部分，都会让下一轮请求失败。 这也是为什么第 2 周的框架会把“工具执行”封装成一个节点——它在替你维护这个配对。

工程类比

tool schema 就是接口契约，tool_calls 是请求报文，tool_call_id 是链路 ID， role: tool 是响应报文。你熟悉的 API 设计原则，在这里几乎原样适用。

05停止条件：没有它就没有 Agent¶

循环是 Agent 的力量来源，也是它最危险的地方：模型可能反复调用同一个工具、在错误方向上打转、 或者被工具返回的内容带偏。生产系统至少要有一组“刹车”：

刹车防的是什么典型做法
最大步数无限循环、反复试错max_steps=8，超限抛出可观测的错误
Token / 成本预算单次任务烧掉不可接受的费用累计 usage，超过阈值降级或转人工
墙钟超时工具卡死、外部 API 不响应每步超时 + 总超时，工具层也要有 timeout
连续错误上限模型在坏工具上死磕连续 N 次 ERROR 后停止并上报
人工接管高风险动作、不可逆副作用写操作前 interrupt，等待批准

注意：“模型说完成了”不是停止条件，而是循环的正常出口。 两者要分开设计——正常出口负责交付答案，刹车负责兜底。只依赖前者，迟早会遇到停不下来的运行。

07Lab：跑通并改动它¶

代码在 labs/0001-mini-agent/。先不要打开编辑器通读， 按下面的顺序做——每一步都有一个可观察的结果。

Step 1 · 离线跑通（2 分钟）

cd labs/0001-mini-agent
python3 agent.py --demo

不需要 API key。你会看到 3 个 step：列文件 → 读文件 → 给出答案。 注意第 3 步的 model → final：模型没有请求工具，循环自然结束。

Step 2 · 对照 trace 读循环（5 分钟）

打开 agent.py，只看 run_agent 函数。 找到这五件事分别在哪一行：

  1. 把工具清单传给模型（registry.schemas()）；
  2. 判断模型有没有请求工具（tool_calls）；
  3. 执行工具（registry.execute(...)）；
  4. 把工具结果写回消息历史（role: tool + tool_call_id）；
  5. 没有工具调用时返回最终答案。

Step 3 · 跑测试（1 分钟）

python3 -m unittest -v

7 个测试全部离线。特别看 test_max_steps_guard 和 test_path_traversal_is_blocked：前者验证刹车，后者验证工具边界。

Step 4 · 接一个真实模型（10 分钟，可选）

cp .env.example .env
# 编辑 .env：填入 LLM_API_KEY / LLM_BASE_URL / LLM_MODEL
python3 agent.py "sandbox/notes.txt 里记录的连接池上限是多少？"

任何 OpenAI-compatible 端点都可以：DeepSeek、Qwen、GLM、OpenAI、Ollama、vLLM。 如果没有 key，跳过这一步不影响本课目标——你已经看到了完整协议。

Step 5 · 加一个工具（8 分钟）

按 README 的练习 1 实现 search_files， 注册 schema，加一个测试。重点不是写函数，而是想清楚三件事： 模型什么时候该用它？参数怎么描述？返回什么格式最利于模型引用？ 这三件事就是第 2 课的主题：工具设计（ACI）。

Step 6 · 亲手触发一次停止条件（2 分钟）

python3 agent.py --demo --max-steps 1

观察 AgentLoopError。然后问自己：如果这是生产环境，除了步数，还应该加哪些预算？

08你刚写的，在框架里叫什么¶

第 2 周你会用 LangGraph 重建这个 Agent。先建立映射，届时你看到的是“它替我做了什么”， 而不是一堆新概念：

你手写的LangGraphOpenAI Agents SDK
run_agent 循环agent 节点 + 条件边Runner 的 agent loop
messages 列表State（messages + reducer）Session / conversation
registry.schemas()节点绑定的 tools@function_tool
registry.execute()ToolNode工具执行器
max_stepsrecursion_limitmax_turns
trace 列表checkpointer + LangSmithTracing

框架真正给你的，不是这个循环，而是循环周围的工程能力：持久化、恢复、人工中断、流式输出、 多 Agent 编排、可观测性。循环本身，你已经有源码级的理解了。
