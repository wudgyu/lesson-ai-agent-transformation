上下文不是记忆

把状态、记忆与上下文分开，Agent 才能在长任务里保持连贯。

01三个容易混为一谈的东西¶

“记忆”这个词在 Agent 讨论里被用得很松。先把三个层次分开：

ContextStateMemory
生命周期这一次模型调用这次任务 / 会话跨会话、跨任务
存储位置上下文窗口内存对象 + checkpoint外部 store / 文件 / 数据库
谁读写模型看见的内容Agent 代码显式维护写入策略 + 检索策略
典型内容系统提示、任务、记忆、最近消息、工具结果事实、决策、未解决问题、副作用记录用户偏好、事故经验、流程规则
失败模式溢出、context rot、污染丢事实、重复副作用、状态不一致过期、错误、隐私泄露、检索错
contextt = select(statet, memory, taskt)

模型永远只看到 context。State 和 memory 是你在模型外面维护的结构； 你的工作是把其中最相关的那一小部分“投影”进 context。 Anthropic 把上下文称为有限的注意力预算：每多一个 token，都在消耗模型分配注意力的能力。 Effective Context Engineering

Java 后端对照

Context ≈ 一次请求的 DTO；State ≈ 会话/任务对象（可持久化）；Memory ≈ 数据库或缓存。 你不会把整个数据库塞进一个请求，也不该把整个会话历史塞进一次模型调用。

02上下文预算与四种污染¶

上下文越长，模型对其中信息的利用越差——这叫 context rot。 Anthropic 的观察是：所有模型都会出现不同程度的退化，只是斜率不同。 所以“窗口够大”不是解决方案；窗口越大，你越需要决定什么不该进去。

LangChain 把长上下文带来的问题分成四类，值得当作排错清单：

污染类型发生了什么RepoMedic 例子
Context Poisoning错误信息进入上下文，并被后续推理沿用一个错误的根因假设被反复引用
Context Distraction上下文太长，模型被训练分布外的内容带偏塞入 50 条日志，模型忘了任务
Context Confusion无关内容影响了回答支付服务的复盘被当成订单服务的根因
Context Clash上下文中的信息互相矛盾旧 runbook 说 40，新配置说 50

LangChain 把应对策略归纳成四个动作：write（写到上下文外）、 select（检索回来）、compress（摘要/裁剪）、 isolate（子 Agent 隔离）。这一课主要做前三个，第四个留到多 Agent 课。 Context Engineering for Agents

03State：把会话变成可恢复的对象¶

不要用“把消息列表 append 起来”当状态。消息列表只记录说过什么，不记录已经确认了什么、 还缺什么、哪些动作已经执行过。一个可恢复的 state 至少要有： 

{
  "messages": [...],
  "facts": {
    "db_pool_max": {
      "value": "50",
      "source": "tool:get_service_health",
      "confidence": 0.9,
      "status": "active"
    }
  },
  "decisions": ["不要只重启；先修 N+1 或回滚"],
  "open_questions": ["是否已经回滚或恢复批量查询？"],
  "side_effects": ["restart:order-service:APR-1"],
  "phase": "investigating"
}

三个设计决定最关键：

  • 事实带 provenance 与 confidence：没有来源的事实，无法在冲突时判断该信谁。
  • 冲突显式 supersede：旧值不删除，标记为 superseded；这既是审计，也是调试。
  • 副作用单独记录：写操作不能只存在于消息里，否则 resume 后模型会重复执行。

State 的更新应该像 reducer：消息 append、事实按键合并、问题去重、决策保留。 这和你熟悉的 event sourcing 很像：消息/工具结果是事件，state 是由事件归约出的当前视图； checkpoint 是快照。LangGraph 的 StateGraph 与 checkpointer 就是把这个模式产品化。 LangGraph — Memory

If it isn't in state, it didn't happen

进程崩溃后，模型看不到任何“它以为发生过”的事。只有落进 state / checkpoint 的事实、决策、 未解决问题和副作用记录，才能在 resume 后继续。消息列表不是状态的全部。

04Compaction：状态转移，不是摘要¶

Compaction 是在上下文接近上限时，把历史压缩成一段更短的状态，重新开始一个上下文窗口。 Anthropic 的描述很具体：保留架构决策、未解决的 bug、实现细节，丢掉冗余的工具输出和消息； Claude Code 会保留最近访问的 5 个文件。调参时先最大化 recall，再优化 precision。 Effective Context Engineering

最容易上手的压缩不是“让模型写一段摘要”，而是清掉旧的工具结果。 一个工具结果在调用后的几轮里可能有用，之后通常只剩一句结论有价值。 Anthropic 把 tool result clearing 称为最轻、最安全的 compaction。

本 lab 的压缩策略

Lab 的 compaction.py 不调用模型，而是把 state 里的结构化信息写成固定格式： 

# Compacted session state

## Confirmed facts
- db_pool_max = 50 (source: tool:get_service_health, confidence: 0.90)
- root_cause = N+1 in OrderQueryService.findRecentOrders (source: tool:search_runbooks, ...)

## Decisions / constraints
- 不要重启；先查根因

## Open questions
- 是否已经回滚或恢复批量查询？

## Recent tool evidence
- search_runbooks: source=incidents/2026-10-24-order-pool.md; ...

然后保留 system 消息、第一条 user 消息和最近 4 条消息，把中间历史替换成这条摘要。 这样做的好处是：事实、决策、未解决问题不依赖模型“记得写”，而是从 state 里直接生成。

实测：压缩保住了什么，代价是什么

18 轮排障，预算 800 tokens，阈值 0.70，keep_recent=4。离线实测，2026-10-27。

模式任务成功最初约束保留峰值 tokens压缩次数丢弃消息
none（硬截断）是否84208
compaction是是67380

两种模式都能答对最终问题，但硬截断把最初的用户约束（“先查日志，不要重启”）丢掉了。 压缩保住了它，峰值也低了约 170 tokens。代价是压缩了 8 次——压缩本身也有成本。

把阈值调高、只保留最近 2 条消息，压缩次数会降到 2 次，峰值升到约 741，最终 tokens 反而更低： 

python3 eval.py --scenario long --threshold 0.9 --keep-recent 2
Compaction thrash

每次压缩都要调用模型、重写状态、重新建立上下文。如果阈值为 0.7、保留 4 条， 你可能会在每一轮都压缩一次。把 compactions 当成指标看： 它太高，说明阈值太低或 keep_recent 太大。

Structured notes：压缩之外的另一条路

Anthropic 还推荐 structured note-taking：让 Agent 把进展写到上下文外的笔记里， 下次需要时再读回来。Claude Code 的 to-do list、项目里的 NOTES.md 都是这个模式。 它特别适合“有清晰里程碑、需要跨很多步”的任务；compaction 更适合连续的对话流。

05Long-term memory：写入与读取¶

State 是线程/会话作用域的；长期记忆跨会话，需要自己的写入策略与读取策略。 LangGraph 把长期记忆按认知科学分成三类，这个分类在工程上很好用：

类型存什么RepoMedic 例子典型读法
Semantic事实、偏好、概念“这个用户希望先看 runbook”检索后注入 system/context
Episodic过去的事件、动作序列“上次 order-service 连接池事故怎么处理的”few-shot / 历史案例
Procedural规则、流程、怎么做事“回滚必须 on-call 负责人审批”更新 system prompt / 工具策略

CoALA 把这些记忆组件放进一个统一的认知架构：工作记忆、情景记忆、语义记忆、程序记忆， 再加上结构化的动作空间与决策过程。CoALA MemGPT 则从操作系统借来“虚拟上下文管理”：把主上下文当成 RAM，把外部存储当成磁盘， 通过分页/换入换出制造“更大的记忆”的假象。MemGPT

写入策略：不是所有对话都值得记

  • 显式 vs 隐式：用户说“记住”时写入最可靠；隐式提取需要置信度与去重。
  • 热路径 vs 后台：LangGraph 明确区分在 Agent 运行中写（实时、可解释、增加延迟）与后台任务写（不阻塞、需要调度）。
  • 去重与 TTL：同一偏好反复说，不应该产生十条记忆；临时信息要过期。
  • provenance 与 confidence：记忆来自用户、事故复盘还是模型推断？冲突时按来源与置信度裁决。
  • 隐私与权限：记忆是跨会话的数据资产，写入前就要想清楚保留多久、谁能读。

读取策略：相关性、时近性、重要性

Generative Agents 的 memory stream 用三个信号检索：recency（越近越重要）、 importance（事件本身多重要）、relevance（与当前 query 多相关）。 Lab 用了一个简化版：0.6 × 词面重合 + 0.2 × 时近性 + 0.2 × 置信度。 Generative Agents

Lab 里有两个直接可见的效果：

场景没有长期记忆有长期记忆
跨会话偏好第一个工具是 get_service_health第一个工具是 search_runbooks
旧记忆冲突旧值 40 不会被记录；新值 50 生效旧值 40 被标记 superseded，最终答案使用 50
Memory is not ground truth

记忆可能是错的、过期的、被注入的。它应该和检索结果一样带来源与置信度， 在冲突时让新证据覆盖旧记忆，而不是相反。不要把“长期记忆”当成“永远正确”。

06Checkpoint 与 resume¶

Checkpoint 是把 state 持久化成快照；resume 是从快照恢复，继续未完成的任务。 这和 compaction 是两件事：

CheckpointCompaction
目的崩溃/暂停后恢复控制上下文预算
是否损失信息不损失（完整 state）有损（摘要/裁剪）
存储数据库/文件新的上下文窗口
关键风险重复副作用、状态过期丢事实、压缩抖动

Lab 的 SessionAgent 在每一步之后写 checkpoint。Resume 后，state 里有事实、 未解决问题和 side_effects；再次调用 restart_service 时， 工具用 service + approval_id 作为幂等键，第二次返回 noop。 实测 duplicate_side_effects = 0。

Resume is not replay

恢复不是把历史消息重新执行一遍。只读工具可以重放，有副作用的工具必须幂等或跳过。 这就是第 4 课的 tool idempotency，在状态层的体现。

07怎么评测记忆¶

“问模型记不记得”不是评测。模型可能说“记得”，但行为没有使用记忆；也可能说“不记得”， 但答案其实用到了上下文。评测要看行为与状态：

指标回答的问题
Task success最终答案是否包含期望事实
Prompt / fact retention压缩/恢复后，任务约束与关键事实是否还在
Peak / final tokens上下文预算是否受控
Compaction count压缩是否抖动
Memory hit跨会话偏好是否被检索到并改变行为
Stale handling旧记忆是否被新证据正确覆盖
Resume success崩溃恢复后事实与未解决问题是否还在
Duplicate side effects恢复后是否重复执行写操作

评测要分片：短会话 / 长会话、同会话 / 跨会话、无冲突 / 有冲突、正常结束 / 崩溃恢复。 平均分会掩盖“长会话里 Prompt 丢了”这种局部失败。

本 lab 的评测方式

4 个场景：long_incident、preference、stale_memory、 resume。每个场景用脚本化策略跑固定轮次，比较不同模式。 完整命令与指标见 labs/0007-state-memory/。

最大的认知转变是：Agent 的可靠性不取决于模型“记得”，而取决于你有没有把该记的写进结构化状态。 Prompt 是易失的，state 是可恢复的，memory 是有策略的。把这三层分开，长任务才可控。
