01先分清三种失败¶

第 5 课把“找得到”拆成了可测量的指标。但一个 RAG 答案要可信，还要穿过三道关：

P(可信答案) ≈ P(retrieve) × P(rerank / select) × P(generate grounded)
失败层症状该看什么指标怎么修
Retrieval正确证据根本没进候选集Recall@candidate_k改 chunk、tokenizer、混合检索、embedding
Rerank / selection候选里有，但没进 top-k 或被上下文挤掉MRR、nDCG、Precision@k重排、调整 k、parent-child、去重
Generation / citation证据在上下文里，模型仍答错、漏答或乱引Correctness、Faithfulness、Citation precision/recall引用协议、校验、拒答、更强模型

这三层是乘法关系。检索 recall 只有 0.6，重排和生成再完美，端到端上限也只有 0.6。 反过来，检索完美但模型把 [S2] 的结论安到 [S1] 上，用户看到的仍然是一个不可信的答案。

错误的引用比“不知道”更糟

RepoMedic 的输出会被用于重启、回滚、改配置。一个带错误出处的自信结论， 比一句“证据不足，需要人工确认”危险得多。引用不是装饰，它是审计接口。

这一课按这三层依次处理：先重排（第 2 节），再引用与校验（第 3–4 节）， 最后用七个失败点与答案级评测把整条链路串起来（第 5–6 节）。

02Rerank：宽召回，精排序¶

第一阶段检索是双塔（bi-encoder）：query 和 document 分别编码成向量， 靠向量距离找候选。它快，因为文档向量可以离线算好；但它必须把文档的所有可能含义 压进一个向量，而且编码文档时还不知道 query 是什么。信息损失是结构性的。

重排是交叉编码器（cross-encoder）：把 query 和 document 拼在一起过模型， 直接输出相关性分数。它看得见两者的交互，精度更高，但必须在线逐对计算，所以更慢。 Pinecone 的总结很直白：“rerankers are slow, and retrievers are fast.” Rerankers and Two-Stage Retrieval

Bi-encoder（第一阶段）Cross-encoder（重排）
输入query 与 document 分开编码query + document 联合编码
预计算文档向量可离线建索引必须在线逐对打分
速度快，适合百万级候选慢，适合几十到几百个候选
精度近似，容易丢细节更高，能看到词与词的关系
典型位置召回 top-50 ~ top-200精排到 top-5 ~ top-20

为什么需要两阶段？Pinecone 指出了一个容易被忽略的事实： recall 不考虑返回了多少文档，所以你可以靠“把整个库都返回”把 recall 刷到 1.0。 真正要优化的是“用尽量少的上下文，拿到尽量多的相关证据”。重排就是这个交易的执行者。

重排能修什么，不能修什么

情况重排能救吗为什么
正确 chunk 在候选集，但排第 8能交叉编码器可以直接把它提到前面
正确 chunk 不在候选集不能候选集是重排的输入；没有输入就没有输出
语料里根本没有答案不能这是 Missing Content，需要拒答或补数据
query 本身有歧义有限重排只能按给定 query 排序，不能替你澄清意图

所以评价重排时，必须同时看两个数：candidate_k 的 recall ceiling 和 rerank 后的 recall@top_k。如果 ceiling 只有 0.6，重排做到 0.6 就到顶了； 继续调重排权重没有意义，应该回去修召回。

本 lab 的实测

第 5 课的 20 个检索用例，BM25 候选集 k=15，重排到 top-5。离线实测，2026-10-25。

配置Recall@5Full@5MRR@5PrecisionContext chars
first-5（不重排）0.6250.5500.5520.2501033
rerank-5（启发式）0.7250.7000.6270.2701174
ceiling@150.8750.8500.5760.1562598

重排把 recall@5 从 0.625 提到 0.725，代价是上下文从 1033 字增加到 1174 字。 但它离 0.875 的候选集上限还有一段距离——剩下的失败主要是语义召回问题， 不是排序问题。这就是为什么第 5 课一直强调：先修召回，再修排序。

生产里用什么重排

常见选择：Cohere Rerank、Voyage rerank、本地 bge-reranker，或者用 LLM 直接给候选打分。 API 重排通常增加 100–200ms 延迟；要准备好超时与降级到第一阶段结果的路径。 Cohere Rerank · Voyage Reranker

重排之后还有一个容易忽略的问题：顺序。即使 top-5 都相关， 把最关键的一段放在中间也可能被模型忽略（lost in the middle）。 实践上把最强证据放在开头或结尾，并在 prompt 里明确标出“这是关键证据”。 Lost in the Middle

03引用：让每个结论有出处¶

引用有三个作用：让用户验证结论、让工程师调试失败、 让系统在合规场景里可审计。它不是给答案加一行 source 链接，而是改变模型的行为： 模型必须先在证据里找到支持，再组织语言。

引用粒度

粒度例子优点缺点
文档级incidents/2026-10-24.md最容易实现用户仍要自己找段落；无法验证具体结论
Chunk 级[S1] → chunk_id + heading可定位、可实现chunk 内可能有多段，仍不够精确
Span 级quote + start/end 字符偏移可精确高亮、可自动校验实现成本最高；模型可能改写 quote

Anthropic 的 Citations API 走的是结构化路线：把来源文档切成句子， 返回 cited_text、document_index，以及按文档类型的位置索引 （纯文本是字符区间，PDF 是页码区间，custom content 是块索引）。 官方称内置引用比多数自定义实现最多高 15% 的 recall accuracy； cited_text 也不计入输出 token。 Anthropic Citations · 发布说明

如果你用的不是 Anthropic，或者需要跨供应商，可以用一套通用引用协议： 

你是 RepoMedic 的排障助手。只能依据下面提供的来源回答。

要求：
1. 每个事实性结论后面标注来源编号，例如 [S1]。
2. 只能引用下面出现过的编号；不要编造来源。
3. citations 里为每个编号给出支持该结论的原文 quote；quote 必须是来源中的原句。
4. 来源不足时，answer 写“证据不足：...”并说明缺什么，citations 为空。
5. 只输出 JSON。

{"answer": "...", "citations": [{"source_id": "S1", "quote": "..."}]}

来源：
[S1] doc=incidents/2026-10-24-order-pool.md heading=... lines=...
...

这条 prompt 的关键不是“请引用”，而是三件事： 来源编号是封闭集合、quote 必须是原文、 允许并鼓励说证据不足。没有第三条，模型会在证据不足时编一个答案； 没有第二条，引用就无法自动校验。

引用改变的是生成行为

要求 quote 原文，会把“凭记忆总结”变成“先在来源里定位再复述”。 这个约束会降低流畅度，但会显著提高可验证性。对排障、法务、医疗这类场景， 这笔交易通常值得。

04引用校验：引用 ≠ 支持¶

“模型给出了引用”和“引用支持结论”是两件事。校验要分四层，成本从低到高：

层级检查成本能抓住什么
1. ID 有效性引用的 [S#] 是否在提供的来源里极低，纯规则编造来源编号
2. Quote 包含quote 是否是来源中的原句/子串低，纯规则改写给错、引用错段落
3. 结论蕴含quote 是否真的推出答案中的 claim高，NLI / LLM judge引用存在但不支持、过度推断
4. 人工审计高风险场景抽样复核最高细微语义偏差、业务判断错误

Lab 实现了前两层，并对第三层留了边界：quote containment 是必要条件，不是充分条件。 第 4 层的判断仍然需要人。下面这张表就是 lab 里故意写坏的 5 个输出：

用例写坏的方式被哪一层抓住
A02引用 ID 有效，但 quote 不在来源里第 2 层：quote_not_found
A03答案里写了不存在的 [S9]第 1 层：invalid_ids
A04第二句结论没有引用Coverage：uncited_claims
A06多来源问题只引了一个来源Citation recall：missing source
A09引用真实存在，但结论与 quote 相反第 2 层抓不住；需要第 3 层
Quote containment 的盲区

A09 的答案是“order-service 使用的是 MySQL”，引用的是架构文档里写着 “PostgreSQL” 的那一段。 quote 确实存在，ID 也有效，确定性检查会放行；但结论与证据相反。 这类失败只能靠 NLI / LLM judge / 人工审计。不要因为“引用校验通过”就认为答案正确。

ALCE 基准把引用质量拆成 fluency、correctness、citation quality 三个维度， 并用 NLI 判断引用是否支持结论。它的结论很清醒：即使最好的模型， 在 ELI5 上也有约 50% 的情况拿不出完整引用支持。 Enabling LLMs to Generate Text with Citations

05七个失败点¶

Barnett 等人的经验报告把 RAG 的失败点整理成七类。它比“检索/生成”二分更细， 因为它把“检索到了但没进上下文”“在上下文里但没被抽取”这些中间状态也单独列了出来。 Seven Failure Points When Engineering a RAG System

#失败点RepoMedic 里的例子对策
FP1Missing Content语料里没有 Spring Boot 版本，系统却编了一个拒答、补数据、明确能力边界
FP2Missed Top Ranked正确复盘在候选集，但没进 top-5重排、调 k、混合检索
FP3Not in Context召回了 15 个 chunk，组装 prompt 时被截掉上下文预算、去重、排序
FP4Not Extracted证据在 context 里，模型被噪音带偏更强模型、更明确的引用协议
FP5Wrong Format要求 JSON，模型输出了 Markdown结构化输出、解析容错、重试
FP6Incorrect Specificity问“哪个类”，答“某个服务”输出契约、事实检查
FP7Incomplete答了根因，漏了需要审批的动作检查清单、覆盖度指标

论文的两个结论比列表更重要：RAG 的验证只有在运行中才可行， 以及鲁棒性是演化出来的，不是一开始设计出来的。 这意味着你需要 trace、评测集和失败分类，而不是指望一套 prompt 解决所有问题。

把失败点映射到你的指标

FP1 → abstention accuracy；FP2 → recall / MRR；FP3 → context precision / context chars； FP4–FP7 → answer correctness、faithfulness、citation coverage、format compliance。 没有指标，失败点就只是故事。

06答案级评测¶

第 5 课评的是检索层；这一课要评答案层。Lab 用 11 个用例： 9 个可回答（含单源、多源、反例、配置读取），2 个应拒答。

指标回答的问题怎么算
Answer accuracy期望事实是否出现、禁止表述是否没出现可回答用例中事实全中的比例
Grounded rate引用 ID 有效、quote 可验证、结论有引用通过引用校验的可回答用例比例
Citation precision给出的 citation 里有多少真的可验证有效 citation / 全部 citation
Citation recall该引的来源有没有引全有效引用的期望来源 / 期望来源总数
Abstention accuracy该拒答时有没有拒答不可回答用例中正确拒答的比例
Pass rate事实 + 引用 + 来源召回是否全过全部用例中 pass 的比例

Lab 的 --backend fixtures 使用脚本化输出，其中 5 个故意写坏。 这是 checker 的演示，不是模型评测；真实结论要跑 --backend llm。

指标本 lab 的 fixture 结果
Answer accuracy0.889（8/9）
Grounded rate0.667（6/9）
Citation precision0.889
Citation recall0.833
Abstention accuracy1.000（2/2）
Pass rate0.545（6/11）
Avg context chars1407

这组数字故意不是满分。它演示的是：答案事实对了（0.889），不代表引用可信（0.667）； 引用 precision 高（0.889），也不代表来源引全了（0.833）。 如果只盯最终答案，你会漏掉这几类引用问题。

评测栈：确定性 → LLM judge → 人工

  1. 确定性检查：ID 是否存在、quote 是否包含、每个 claim 是否有引用、期望来源是否出现。便宜、可复现、适合 CI。
  2. LLM judge：判断 claim 是否被 quote 蕴含、答案是否覆盖期望事实、是否过度推断。需要校准，避免自我偏好。
  3. 人工审计：高风险场景抽样；把分歧样本写回评测集。

Ragas 的 Faithfulness 提供了一个可操作的起点：把答案拆成 claims， 逐条检查是否能由 retrieved context 推出，分数 = 被支持的 claim 数 / 总 claim 数。 Ragas — Faithfulness

平均分是谎言，答案层也一样

按“可回答 / 不可回答 / 单源 / 多源”切片。多源问题的 citation recall 往往最先崩； 不可回答问题的 abstention 往往被平均分掩盖。先修最差的那一片。

09和 Java 后端对照¶

这一课几乎就是搜索系统与审计系统的工程直觉，换了一个“客户端”。

RAG 概念Java 后端对应
两阶段检索 + rerank粗排 + 精排 / 搜索引擎的多阶段查询
bi-encoder vs cross-encoder倒排召回 vs 精排模型
citation IDtrace ID / 请求 ID / 审计日志编号
quote containment审计日志与原始事件的字段校验
groundedness数据血缘 / 可追溯性
abstention服务降级、返回空结果、拒绝越权请求
fixtures契约测试 / golden files
citation precision / recall告警准确率 / 召回率
七类 failure points故障树 / FMEA

最大的认知转变是：“答案正确”不是一个布尔值，而是一组可分解的检查。 事实、引用、来源覆盖、拒答、格式，各自有独立的失败模式。 你要做的不是写一个更长的 prompt，而是把每个检查变成可重复的评测。
