01先算一笔上下文账¶

先别谈模型。算一笔账：一个中型 Java 代码库有 800 个文件，平均 200 行， 每行约 10 个 token，就是 160 万 token。再叠加三年的 runbook、事故复盘、配置和工单， 数字只会更大。即使某个模型的上下文窗口“够大”，你也不会想为每次提问都付这笔钱。

更麻烦的是，塞进去不等于看得见。上下文越长，模型对中间信息的利用率越差—— 这就是 context rot 与 “lost in the middle” 现象。 Anthropic 在上下文工程指南里把上下文称为预算：每一段材料都在和系统提示词、 对话历史、其他工具结果争夺模型的注意力。 Effective Context Engineering · Lost in the Middle (arXiv:2307.03172)

RAG（Retrieval-Augmented Generation）的原始论文把它描述为“参数化记忆 + 非参数化记忆”的组合： 模型负责语言与推理，外部索引负责事实与出处。 Lewis et al., 2020 今天的 RAG 管线复杂得多，但核心没变：

RAG = Retrieve(q, D) → Augment(q, chunks) → Generate(q, chunks)

生成模型只能基于它看到的内容回答。所以有一条残酷但重要的上限：

检索决定上限

如果正确片段没有进入 top-k，后面的模型再强也只能猜。检索失败不是“答案不够好”， 而是答案所需的事实根本没到场。先修检索，再谈 prompt。

检索有两个失败方向：漏召回（该找到的没找到）和噪音（找到了很多不相关的）。 漏召回是致命的；噪音浪费 token、稀释注意力，但模型有时能自己过滤。 这也是为什么本课先把 recall 放在第一位，同时记录上下文成本。

02RAG 的两条流水线¶

RAG 不是一个函数，而是两条生命周期完全不同的流水线。把它们混在一起，是很多“demo 能跑、 上线就崩”的根源。

两条流水线之间有一份数据契约：每个 chunk 至少要带 chunk_id、doc_id、heading、text 和行号范围。 没有稳定 ID，你就无法引用出处、无法做增量更新、也无法把评测标签绑定到具体证据。 

{
  "chunk_id": "runbooks/db-pool.md#诊断",
  "doc_id":   "runbooks/db-pool.md",
  "heading":  "Runbook: 数据库连接池耗尽 > 诊断",
  "start_line": 12,
  "end_line": 19,
  "text": "..."
}

索引是派生数据，不是真相源。源文档改了，索引必须重建；embedding 模型换了， 整个向量索引作废。生产里最常见的 RAG 事故之一，就是“文档更新了，索引还是三个月前的”。 这和你熟悉的缓存失效、物化视图刷新是同一类问题。

Java 后端对照

离线流水线 ≈ ETL / 批处理；在线查询 ≈ serving；chunk_id ≈ 稳定主键； 索引 ≈ 物化视图；embedding 模型版本 ≈ schema 版本。把这些元数据写进索引，才谈得上可复现。

03Embedding：语义坐标，不是魔法¶

Embedding 把文本映射成一个固定长度的向量。 语义相近的文本，在向量空间里距离更近；检索时用余弦相似度找最近的邻居。 它擅长的是换一种说法：用户问“数据库连接被占满了”，文档写“连接池耗尽”， 两者没有共同的关键词，但语义相近。

但它是一种有损压缩。压缩会保留“大意”，丢掉“细节”。下面这些，向量往往不可靠：

输入类型向量的表现后果
TS-999 vs TS-998字面与语义都很近可能召回错误的错误码，处置完全不同
类名 / 方法名 / 配置键camelCase、缩写、版本号容易被平滑精确匹配失败，代码检索不可用
数字与单位48/50 与 50/48 可能很近指标判断反转
否定与条件“不是连接池问题”可能仍靠近“连接池问题”把排除项当成根因
同义改写 / 跨语言通常表现好这是它真正的价值所在

所以 embedding 的正确用法不是“替代关键词”，而是“补上关键词抓不到的语义召回”。 这也是下一节 hybrid 检索的动机。

选模型时看什么

  • 先在自己的语料上测，不要只看 MTEB 排行榜。排行榜是起点，不是结论；你的语料分布、语言、代码占比都可能不同。
  • 维度与成本：维度越高，存储与计算越贵；对 20–50 个 chunk 的小库，差异可以忽略，对百万级索引就不是。
  • query / document 是否分开编码：一些模型（如 Voyage）要求查询与文档使用不同的输入类型或前缀，用错会显著掉点。Voyage Embeddings
  • 版本锁定：模型升级意味着全量重算。把模型名与维度写进索引元数据，否则你无法解释分数变化。

归一化之后，余弦相似度就是点积。实现只有几行： 

def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = math.sqrt(sum(x * x for x in a))
    nb = math.sqrt(sum(y * y for y in b))
    return dot / (na * nb) if na and nb else 0.0
向量不是语义真值

它只是某个模型在某个训练分布上学到的压缩表示。相似不等于相关，更不等于可处置。 对代码、错误码、配置键这类“精确标识符”密集的语料，永远保留一条关键词通道。

04Chunking：检索的最小单位¶

Chunk 同时是检索、embedding、引用和上下文预算的单位。 切得好，模型拿到的是“一段能独立看懂的话”；切得差，它拿到的是“半句话 + 一个孤立的代词”。

Chunk 过小Chunk 过大
语义不完整，指代丢失多个主题被平均进一个向量
答案被拆到多个 chunk，召回不全检索精度下降，噪音变多
引用很精确，但上下文不够每次查询消耗大量 token，延迟与成本上升

经验起点：事实查找用 200–500 tokens，需要推理的段落用 512–1024 tokens， 重叠 10–20%。但这些只是起点，不是答案。Pinecone 的建议很直接： 选一组候选尺寸（例如 128/256 与 512/1024），在你的查询集上实测。 Chunking Strategies

优先级更高的不是“多大”，而是“在哪里切”。结构感知的切法会沿 Markdown 标题、段落、Java 类/方法边界走， 并把标题路径带进 chunk。Lab 为了把语料压到 14 篇，代码文件整文件作为一个 chunk； 真实代码库应该按类/方法切：

标题路径 + 完整句子；chunk_id 可稳定指向这一段。

更进阶的一步是 contextual retrieval：在把 chunk 送去 embedding / BM25 之前， 先用一个便宜模型为它写 50–100 token 的“情境说明”，比如“这段来自 2026-10-24 order-service 的连接池事故复盘，讨论根因”。Anthropic 报告称，在 top-20 检索失败率上： contextual embeddings −35%，加上 contextual BM25 后 −49%， 再加 rerank 后 −67%（5.7% → 1.9%）。配合 prompt caching，成本约为 $1.02 / 百万文档 token。 Contextual Retrieval

Lab 里的 structure chunker 对 Markdown 做的是它的“穷人版”：把文档标题前缀到每个 chunk。 这不需要模型调用，但已经能让 chunk 不再完全失去上下文。你可以把它理解为 deterministic context header。

Small-to-big / parent-child

如果检索单位要小、但生成需要大，可以“检索小子块，返回父段落”。 这能同时拿到精确召回与足够上下文。Lab 里你会先看到反例：k=5 时答案被拆在两个 chunk 里， 把 k 调到 10 才把两块都捞回来——这就是 chunk 边界问题的具体形状。

05Hybrid：关键词 + 向量¶

Hybrid search 同时跑两路召回： 关键词检索（BM25）与向量检索，再把两份排名融合。它不是“更高级”，而是“两种错误模式互补”。

BM25 在做什么

BM25 建立在 TF-IDF 上：一个词越罕见（IDF 高），命中它越值钱；一个词在文档里重复太多次， 收益会饱和（k1）；文档越长，越要打折（b）。典型参数是 k1=1.5、b=0.75。你不需要背公式，但要理解它的偏好： 精确、罕见、可枚举的词。

score(q,d) = Σ IDF(qi) · f(qi,d) · (k1+1) / ( f(qi,d) + k1(1−b+b·|d|/avgdl) )

因为 BM25 只看词面，tokenizer 的质量直接决定召回。对代码与中文语料，至少要做三件事：

  • 拆标识符：findRecentOrders → find / recent / orders；db_pool.used → db / pool / used。
  • 保留整串：同时保留 findrecentorders 与 db_pool.used，精确查询才有强信号。
  • 中文 bigram：没有分词词典时，数据库连接池 切成 数据/据库/库连/连接/接池，比按空格切可靠得多。

两路怎么选

查询类型更可能赢例子
精确标识符BM25TS-999、findRecentOrders、maximum-pool-size
口语化改写向量“数据库连接被占满了” → “连接池耗尽”
指标 + 因果两者“p99 2400ms、连接池 48/50，最可能是什么原因？”
跨文档多跳两者 + 更大 k“v2.14.1 改了什么，和哪个类有关？”

融合：RRF

BM25 的分数和 cosine 的分数尺度不同，直接相加没有意义。 Reciprocal Rank Fusion（RRF）只看排名：

score(chunk) = Σ 1 / (k + ranki)，常用 k = 60

两路都排在前面的 chunk 会得到更高分；只在单路出现的 chunk 也有机会。 这是“共识优先”的融合。Weaviate 的 alpha 则是另一条路： alpha=1 纯向量，alpha=0 纯关键词，中间值按权重混合。 Weaviate — Hybrid Search

实现细节：每路先召回 50 个候选，融合后再取 top-5 或 top-10。 如果只融合每路的 top-5，你会丢掉“单路排第 8、另一路排第 3”的好候选。

Hybrid 不是免费午餐

两套索引、两倍写入、两倍的失败模式，在线还要多一次查询与融合。对代码、错误码、配置键密集的语料， 它通常值得；对纯自然语言、语料很小的场景，先用好一路，再决定要不要加。

06用 Recall@k 证明你找得到¶

“感觉检索变好了”不是证据。你需要一组带标签的查询，以及一组能分开诊断的指标。 Lab 的 20 个用例分四类：keyword（精确标识符）、semantic（口语改写）、 mixed（指标 + 因果）、multi-hop（跨文档）。

指标回答的问题怎么算
Recall@k该找到的证据，有多少进了 top-k？命中证据数 / 证据总数，按用例平均
Full@k所有证据都进 top-k 的用例比例？多证据全部命中的用例 / 总用例
MRR@k第一条命中证据排第几？1 / 首次命中的排名，按用例平均
Precisiontop-k 里有多少 chunk 真有用？命中 chunk 数 / top-k 长度
Context chars每次查询塞进多少上下文？top-k chunk 的字符数之和，按用例平均

Ragas 把检索质量拆成 context recall 与 context precision 等指标，并用 LLM 判断“参考事实是否被检索到”。 Lab 用的是更便宜、更确定的证据标签：每条查询绑定 doc + contains 短语。 它没有 LLM judge 那么灵活，但可复现、可在 CI 里跑；标签的正确性由你负责。 Ragas — Available Metrics

不要只看平均分：Recall 与上下文成本

配置Recall@kContext chars你付出的代价
structure · k=50.6251033上下文最省，但多跳/跨节证据容易漏

这组数字想说明的不是“naive 更好”。naive 在 k=5 时靠更大的块把 recall 刷到 0.800， 但 structure 把 k 调到 10 后反超到 0.825，上下文还更少。公平的比较要在相近预算下做， 并且同时看 precision 与 context chars。这也是为什么第 6 课的 rerank 有价值： 先宽召回，再用更贵的模型精排，把噪音压下去。

平均分是谎言

本 lab 的 hybrid 在 keyword 切片上 recall=1.000，在 semantic 切片上只有 0.429。 平均 0.650 会把这条裂缝藏起来。永远按查询类型切片，先修最差的那一类。

失败归因：先分类，再调参

症状可能原因下一步
top-k 里完全没有正确文档检索器/分词/embedding 不匹配看 tokenizer；对精确查询加 BM25；换 embedding 前先做小实验
正确文档在，但正确段落不在chunk 边界 / 粒度调 k、改 chunker、parent-child / small-to-big
正确段落排在第 6–10 名融合权重 / 候选不足加大 candidate_k、调 RRF、上 rerank
标签里的短语在文档中不存在评测集腐烂改标签；把 validate 放进 CI

Lab 里的 Q14 是一个典型：查询同时包含 p99 指标和“最可能原因”。指标在“证据”段， 原因 N+1 在“根因”段；structure chunker 把它们切成两块，k=5 时只捞到指标。 BM25 要到 k=10 才把根因捞回来；hybrid 在 k=7 就够——RRF 把单路排名靠后的根因块拉了进来。 这不是模型不聪明，是证据跨 chunk。解决办法是更大的 k、parent-child，或者让检索器返回相邻块。

08Lab：给 RepoMedic 建检索层¶

代码在 labs/0005-rag-retrieval/。 语料是 14 篇 RepoMedic 文档：runbook、事故复盘、Java 代码、配置、错误码。 评测集是 20 个查询，每个都绑定“文档 + 证据短语”。

Step 1 · 离线校验（5 分钟）

cd labs/0005-rag-retrieval
python3 -m unittest -v
python3 eval.py --validate

29 个测试覆盖 tokenizer、BM25、chunking、RRF、指标与索引往返。 --validate 检查 20 个用例的证据文档是否存在、证据短语是否还在原文里。 这一步不需要 API key。

Step 2 · 构建索引，跑三种检索器（10 分钟）

python3 index.py --chunker structure --out index/structure.json
python3 eval.py --index index/structure.json --retriever all

重点看三件事：keyword 切片是否接近满分；semantic 切片是否明显更低； hybrid 是否在两者之间取得更好的整体 recall。然后看失败列表： 每条失败都缺了哪条证据？top-k 里又是什么？

Step 3 · structure vs naive：比较召回与上下文成本（10 分钟）

python3 index.py --chunker naive --size 600 --overlap 80 --out index/naive-600.json
python3 eval.py --index index/naive-600.json --retriever bm25
python3 eval.py --index index/structure.json --retriever bm25 --k 10

在 k=5 时，naive-600 的 recall 更高，但 ctx_chars 也接近翻倍。structure 把 k 调到 10 后， 整体 recall 反超（0.825），成本仍低于 naive。回答：如果上下文预算固定，你会选哪个？为什么？

Step 4 · 定位一个“跨 chunk”失败（8 分钟）

python3 eval.py --index index/structure.json --retriever bm25 --k 5 --case Q14
python3 eval.py --index index/structure.json --retriever bm25 --k 10 --case Q14
python3 eval.py --index index/structure.json --retriever hybrid --k 7 --case Q14

Q14 同时包含 p99 指标和“最可能原因”。指标在“证据”段，原因 N+1 在“根因”段。 BM25 要 k=10 才把根因捞回来；hybrid 在 k=7 就够，因为 RRF 把单路排名靠后的根因块拉了进来。 然后回答：这是 chunk 边界、tokenizer、检索器，还是标签的问题？

Step 5 · 可选：接真实 embedding（10 分钟）

cp .env.example .env
# 填写 EMBEDDING_API_KEY / EMBEDDING_BASE_URL / EMBEDDING_MODEL

python3 index.py --chunker structure --embed-api --out index/structure-embedded.json
python3 eval.py --index index/structure-embedded.json --retriever all

观察 semantic 切片是否上升，以及 hybrid(dense:...) 是否比单路更稳。 如果供应商不提供 embedding，跳过这一步；不要用 vector(lexical) 的结果冒充语义检索。

Step 6 · 回答三个问题

  1. 为什么 keyword 切片接近满分，而 semantic 切片明显更低？这是 tokenizer、embedding 还是语料的问题？
  2. naive-600 的 recall 更高，为什么它不一定更好？请用 ctx_chars 和 prec 解释。
  3. 如果 Q14 这类“指标 + 根因”查询占你线上流量的一半，你会改 chunk、改 k，还是加 rerank？为什么？

09和 Java 后端对照¶

这一课几乎是后端工程经验的直译。变化只有一个：检索的“客户端”是模型，不是程序。

RAG 概念Java 后端对应
embedding model搜索引擎的 analyzer / 语义索引
BM25倒排索引 + TF-IDF 排序
RRF多路有序结果归并（merge sorted lists）
chunk_id稳定主键 / 文档版本号
索引重建物化视图刷新 / 缓存失效
Recall@kSLI + 回归测试通过率
黄金集契约测试 + 集成测试
chunk metadatatrace tag / 日志上下文

最大的认知转变是：检索质量是一个分布问题，不是一次调用问题。 你不能靠“这次答案看起来不错”判断系统可靠；你需要一组查询、一组标签、一组按类型切片的指标， 然后在每次改 chunk、改模型、改融合参数后重跑。第 3 周我们会把这套东西扩展成完整的评测体系。
