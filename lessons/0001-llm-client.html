你写过 Java 服务，也调用过 LLM API。但很多“Agent 不听话”的问题， 其实发生在一次模型调用里：上下文塞得太满、输出没有契约、temperature 太高、 把 tool_calls 当成已经执行。这一课把这次调用拆开。

先测一下直觉：3 个判断题
  1. 模型会自己执行工具吗？
  2. temperature=0 能保证每次输出完全一致吗？
  3. 上下文窗口是“输入 + 输出”共享的预算吗？

对答案：不会，执行的是你的代码；不能，它只降低随机性；是，输入与输出共用同一个窗口。

如果三题都答对，这一课会给你一套可复用的 client 与 schema 契约；如果有一题犹豫，正好补上。

01模型在做什么¶

LLM 的本质是下一个 token 的概率分布： 给定上下文，它输出词表上每个 token 的分数，采样出一个 token，再把它接回上下文，重复。

P(next token | context) = softmax(logits / temperature)

这句话有三个工程后果：

  • 它不执行任何东西。模型不会打开文件、不会发 HTTP 请求、不会写数据库；它只会输出“我想调用某个工具”的结构化请求。执行的是你的代码。
  • 它没有记忆。每次调用看到的只有你传进去的 context；上一次调用发生过什么，除非你写进 context，否则不存在。
  • 它是概率性的。同一个输入可能得到不同输出；这既是能力，也是工程风险的来源。
模型不执行工具

Function calling / tool calling 只是模型输出一段结构化请求： “我要调用 query_logs，参数是……”。真正执行的是你的工具层。 权限、沙箱、审计、幂等，都必须做在工具层。

所以 Agent 的第一性原理不是“更聪明的模型”，而是： 模型做决策，代码做执行，循环把两者接起来。 这一课先把“决策”这一次调用讲清楚；第 3 课再把循环接上。

02Token 与上下文预算¶

Token 是模型处理文本的最小单位，不等于字符，也不等于单词。 同一个句子，中文、英文、代码的 token 数可能差很多；计费、延迟、上下文长度都以它为单位。 Anthropic 的 token counting 文档与 OpenAI 的 tokenizer cookbook 都提供了具体工具， 但工程上更重要的是：把 token 当预算，而不是当事后账单。 Anthropic — Token counting · OpenAI — tiktoken

上下文窗口是输入 + 输出共享的上限。 一次调用里，预算大致被这些部分吃掉：

预算项典型内容工程问题
System prompt角色、约束、输出契约太长会挤占证据；太短会缺约束
对话历史user / assistant / tool 消息随轮次增长；需要压缩或截断
检索/工具结果RAG chunks、日志、指标最容易失控；要过滤、截断、去重
输出答案、JSON、tool_callsmax_tokens 太小会截断；太大会浪费

这也是为什么第 5、6 课要讲检索与重排：不是所有材料都值得进上下文。 Anthropic 把上下文称为“注意力预算”：token 越多，模型对其中信息的利用反而可能越差。 Effective Context Engineering 

context budget example
  system prompt        ~ 300 tokens
  conversation         ~ 1,800 tokens
  retrieved chunks     ~ 2,400 tokens
  tool results         ~ 900 tokens
  reserved for output  ~ 1,000 tokens
  ---------------------------------
  total                ~ 6,400 tokens

  if the window is 8k, you have ~1.6k headroom.
  if the next turn adds 2k of logs, you will overflow.
Java 对照

Token 预算 ≈ 请求体大小 + 响应体大小的硬上限；max_tokens ≈ 响应缓冲区上限； 超出预算不是“慢一点”，而是直接失败或被截断。

03采样：temperature / top_p¶

采样决定“从概率分布里怎么选下一个 token”。 两个最常用的旋钮：

  • temperature：缩放 logits。越低越接近“选最高概率”，越高分布越平、越随机。
  • top_p（nucleus sampling）：只保留累计概率最高的一部分 token，再在其中采样。
任务建议原因
工具调用 / 结构化抽取低温度（0–0.3）减少格式漂移与参数幻觉
排障结论 / 事实问答低到中（0.1–0.4）稳定、可复现优先
头脑风暴 / 文案中到高（0.7–1.0）需要多样性
需要严格确定性的场景不要只靠 temperature=0供应商实现、并行、版本都可能带来差异

temperature=0 通常让模型选最高概率 token，但不保证跨请求完全一致： 浮点运算、批处理、模型版本、供应商实现都可能影响结果。把“确定性”当成工程目标时， 应该用 schema 校验、缓存、幂等和评测，而不是只设一个参数。

不要同时盲调 temperature 和 top_p

两个参数都会改变分布形状，同时调很难归因。先固定一个，用同一组评测样本测另一个； 没有评测的“调参”只是感觉。

04结构化输出¶

结构化输出是把“自然语言回答”变成“可被程序消费的契约”。 最可靠的做法不是让模型“尽量返回 JSON”，而是：

  1. 给 schema：字段、类型、枚举、必填、是否允许额外字段。
  2. 让模型按 schema 输出：JSON mode / structured outputs / function calling。
  3. 在代码里校验：不要 json.loads 之后直接用。
  4. 失败时修复：把校验错误反馈给模型，重试有限次数；仍失败就降级或转人工。
{
  "type": "object",
  "properties": {
    "category": {"type": "string", "enum": ["billing", "technical", "account", "other"]},
    "priority": {"type": "string", "enum": ["P0", "P1", "P2"]},
    "summary": {"type": "string"},
    "needs_human": {"type": "boolean"}
  },
  "required": ["category", "priority", "summary", "needs_human"],
  "additionalProperties": false
}

这个 schema 同时是 prompt、接口契约和测试用例。模型输出 {"needs_human": "yes"} 时，校验器会拒绝；修复循环会把 “needs_human must be a boolean” 发回去。这比在 prompt 里写十遍“请返回布尔值”可靠。

Java 对照

Schema ≈ DTO + OpenAPI + Bean Validation；校验失败重试 ≈ 带错误码的 4xx 响应 + 客户端修正； 不要把“解析成功”当成“业务合法”。

05一次调用的消息协议¶

无论你用哪家 SDK，Chat Completions 的形状基本一致。理解消息角色，比背 SDK 方法重要：

角色谁产生作用
system你的代码角色、约束、输出契约、工具使用规则
user用户 / 上游系统任务与输入
assistant模型自然语言回答，或 tool_calls 请求
tool你的代码工具执行结果，必须用 tool_call_id 配对

一次带工具的调用，响应里可能出现： 

{
  "choices": [{
    "message": {
      "role": "assistant",
      "content": null,
      "tool_calls": [{
        "id": "call_abc",
        "type": "function",
        "function": {"name": "query_logs", "arguments": "{\"service\":\"order-service\"}"}
      }]
    },
    "finish_reason": "tool_calls"
  }],
  "usage": {"prompt_tokens": 412, "completion_tokens": 38, "total_tokens": 450}
}

finish_reason 告诉你这次调用为什么结束：stop（正常）、 length（被 max_tokens 截断）、tool_calls（要执行工具）、 content_filter（被安全策略拦截）。不处理它，你会把截断当成完整答案。

流式响应则把文本拆成多个 delta，最后再给一个 done / usage。 流式改善的是首 token 延迟与用户体验，不改变 token 总量；不要以为“流式就不占预算”。

tool_calls 不是执行结果

模型返回 tool_calls 后，循环必须暂停：执行工具、把结果作为 tool 消息 追加、再用 tool_call_id 配对，发下一次请求。少了配对，API 会直接报错； 把“模型说它查了日志”当成证据，则是更隐蔽的错误。

07Lab：流式 client + 修复循环¶

代码在 labs/0001-llm-client/。 它只有两个文件要读：llm_client.py 与 structured.py。

Step 1 · 跑测试（5 分钟）

cd labs/0001-llm-client
python3 -m unittest -v

20 个测试覆盖消息构建、流式 delta/done、usage、JSON 解析、schema 校验与修复循环。 不需要 API key。

Step 2 · 看流式事件（5 分钟）

python3 llm_client.py --demo

观察每个 delta 只是增量；最后 done 才带完整文本与 usage。 把 usage 与 estimate_tokens 对比，理解“估算”与“账单”的差别。

Step 3 · 看修复循环（10 分钟）

python3 structured.py --demo

第一次输出把 needs_human 写成字符串，校验失败；错误被反馈给模型； 第二次输出合法。这个循环就是生产里处理结构化输出的最小闭环。

Step 4 · 接真实模型（15 分钟，可选）

cp .env.example .env
# 填写 LLM_API_KEY / LLM_BASE_URL / LLM_MODEL

python3 llm_client.py --live --prompt "用一句话解释 token 预算。"
python3 structured.py --live --ticket "生产环境订单服务大量 500，用户无法下单。"

不同 OpenAI-compatible 端点对 stream_options 与 response_format 的支持不同；如果报错，先确认端点能力，再决定是否降级。

Step 5 · 改 schema（10 分钟）

给 TICKET_SCHEMA 增加 confidence: number， 同步更新校验与测试；再把 max_repairs 改成 0，观察非法输出如何直接失败。

08和 Java 后端对照¶

LLM 概念Java 后端对应
token budget请求体 / 响应体大小上限
max_tokens响应缓冲区上限
temperature / top_p重试抖动 / 负载均衡随机性
JSON schemaDTO + OpenAPI + Bean Validation
tool_callsRPC 请求（不是执行结果）
修复循环带错误码的 4xx + 客户端修正 + 有限重试
流式响应SSE / chunked response
usagemetrics / 成本账本
finish_reason=length响应被截断 / 413 类错误

最大的认知转变是：模型是一个纯函数式的概率组件，不是一个服务。 它没有副作用、没有记忆、不会执行；所有可靠性都来自你包在它外面的协议、校验与循环。
