01请求不是 run¶

notebook 里的 Agent 是一个函数：传 prompt，等答案。服务里的 Agent 是一个 长生命周期对象：一次执行可能跑几十秒、调十几次模型和工具、 中途要审批、客户端可能断线、进程可能被 SIGTERM。把这些都塞进一个 HTTP 请求， 就会得到最难运维的形态：

Demo 写法

@app.post("/ask")
async def ask(q: str):
    # 一次请求里跑完整 Agent
    return await agent.run(q)
  • 网关 60s 超时，run 被腰斩
  • 客户端重试 → 重复副作用
  • 断线后没有结果可查
  • 无法取消、无法恢复、无法限流到 run 粒度

服务写法

POST /v1/runs
  Idempotency-Key: ...
→ 202 {run_id, events_url}

GET /v1/runs/{id}/events   # SSE
GET /v1/runs/{id}          # 最终结果
POST /v1/runs/{id}/cancel  # 取消
  • 202 立即返回，执行与请求解耦
  • 结果落 store，断线可查
  • 事件可重放、可恢复
  • 准入、超时、取消、关停都有明确位置

202 不是“偷懒不返回答案”，而是把执行的所有权从连接转移到服务。 返回的 run id 是后续所有操作的句柄： 

HTTP/1.1 202 Accepted
Location: /v1/runs/run-0001

{
  "run_id": "run-0001",
  "status": "accepted",
  "events": "/v1/runs/run-0001/events"
}
client │ POST /v1/runs (Idempotency-Key, tenant) ▼ API / admission │ 认证 → 幂等 → 租户配额 → 有界队列 ├─ 429 / 503 ──────────────────────────────► client（带 Retry-After） └─ 202 + run_id │ ▼ queue ──► worker ──► agent phases ──► checkpoint │ │ │ ├─ emit event ──► event log ──► SSE subscribers │ └─ write result ─► result store ▼ terminal: succeeded / failed / cancelled

这张图里有四个独立的存储/通道：run 状态、事件日志、 最终结果、订阅者队列。把它们混成一个“内存里的字符串” 是服务化最常见的起点，也是多 worker 部署时第一个爆炸的地方。

概念生命周期失败时谁拥有
HTTP 请求秒级客户端重试/断开连接
run分钟级，可跨重启checkpoint / resumerun store
SSE 连接与客户端在线时间一致Last-Event-ID 重连订阅者
副作用永久effect ledger 去重目标系统 + 账本
Java 锚点

这就是 Servlet 3 的 DeferredResult / @Async 所做的事： 请求线程只负责接收和返回句柄，执行交给有界线程池；区别是 Agent 的 run 更长、 更贵，所以还需要 checkpoint、幂等和取消。不要把 @Async 当成队列： JVM 一停，内存里的任务就没了。

02入口：认证、配额、并发、排队¶

一个 run 进入系统之前要过四道门。顺序很重要，因为每道门的价格和语义不同：

门问题拒绝状态放在这里的原因
认证 / 授权你是谁？这个 run 允许做什么？401 / 403后面的配额与审计都依赖可信身份
幂等这是重试，还是新请求？200 / 409 / 422重试不应重复扣配额、创建第二个 run
配额这个租户还有预算吗？429 + Retry-After租户问题，不应占用系统容量
容量全局 worker 和队列还有位置吗？503系统问题，所有人都受影响
不要相信 X-Tenant

lab 里用 X-Tenant 头只是为了演示；生产里 tenant 必须来自认证主体 （JWT claim、mTLS 证书、API key 映射）。如果客户端可以随便声明租户， 配额、审计和隔离全都是摆设。

令牌桶：允许突发，限制均值

Stripe 的限流实践把 “请求速率限制”和“并发限制”分开：前者按租户限速、允许短时突发；后者限制同时 进行的工作量。对 Agent 来说，两者都需要，但并发限制通常更重要， 因为一次 run 会长时间占用 worker、连接和模型配额。

tokens = min(capacity, tokens + elapsed × refill_rate) allow if tokens ≥ 1；否则 Retry-After = ceil((1 − tokens) / refill_rate)

capacity 决定能突发多少，refill_rate 决定长期均值。 lab 的配额场景里，每个租户 capacity=3、refill=0：12 个请求里 9 个被接纳， 3 个 429。429 的响应必须带 Retry-After，告诉客户端 多久以后再来；不带这个头，客户端只能猜，通常会立刻重试，把限流变成重试风暴。

429 与 503 不是一回事

状态含义客户端应该谁的问题
429租户配额用完按 Retry-After 等待，或升级配额这个租户
503队列/worker 饱和，或正在关停退避重试；不要立刻打满整个系统

lab 的饱和场景把 workers=3、max_queue=4 固定住： 12 个请求只有 7 个进入系统（3 个在跑、4 个排队），其余 5 个拿到 503。 max_inflight=3 证明并发上限生效；queue_depth=4 证明 队列有界。注意 queue full 时 lab 会把刚扣掉的配额 token 退回去—— 客户端没有做错，是共享资源忙，不应该再罚它一次。

速率限制保护什么

  • 滥用与意外循环
  • 按租户的公平性
  • 模型供应商的 RPM/TPM 配额

并发限制保护什么

  • worker、连接池、内存
  • 长 run 占用的模型配额
  • 过载时的尾延迟与级联失败

过载时还可以在客户端做自适应拒绝。Google SRE 的公式是： 

P(reject) = max(0, (requests − K × accepts) / (requests + 1))

# requests 包含本地拒绝的请求；accepts 是后端真正接受的
# K 通常取 2：允许尝试次数达到成功数的两倍，再开始本地 shed

这个公式的价值在于“按整个系统的状态”而不是“按单个用户”做决定。Stripe 的 load shedder 也是同一思路：过载时牺牲低优先级流量，保住高优先级流量。 SRE Book 明确指出 本地拒绝也要计入 requests，否则负载越高、拒绝率反而上不去。

限流器自己坏了怎么办

限流器是保护层，不是业务逻辑。Redis 挂了时，默认策略通常是 fail open（放行）并告警，而不是让所有请求 500；但要有 kill switch、暗发布和指标，确认它没有悄悄把正常流量全部拒掉。 Stripe 的做法是先观察将被拒绝的请求，再逐步 enforcement。

03执行：异步、超时、取消¶

FastAPI 的并发模型有两个关键事实，来自 官方文档：

路由写法FastAPI 行为适用
async def直接在事件循环里 await异步库；或不阻塞的轻计算
def放进外部线程池再 await阻塞库（多数数据库驱动、同步 SDK）

官方原文：“When you declare a path operation function with normal def instead of async def, it is run in an external threadpool that is then awaited, instead of being called directly (as it would block the server).” 反过来，在 async def 里调用阻塞 SDK， 会把整个事件循环卡住，所有并发请求一起排队。

阻塞事件循环

@app.get("/slow")
async def slow():
    # requests 是同步库
    return requests.get(url).json()

一个慢请求卡住所有连接；超时也无法取消。

交给线程池

@app.get("/slow")
def slow():
    # FastAPI 自动放进线程池
    return requests.get(url).json()

阻塞发生在 worker 线程；事件循环仍可处理其他请求。

另一个常见误区是用 BackgroundTasks 跑 Agent。 FastAPI 文档 把它定位为“响应之后的小任务”，并且它和 web 进程同生共死：没有持久队列、 没有重试、没有可见性，SIGTERM 一来就一起没。重活要用外部 job queue （Celery / Arq / 云队列），或者像本 lab 一样，把 run 放进自己的 store + worker。

Deadline 是绝对的，不是每层重新计时

deadline = now() + 25          # 整个 run 的总预算

async def call_tool():
    remaining = deadline - now()
    if remaining <= 0:
        raise DeadlineExceeded()
    # 每一步只拿剩余预算，不再重新起算
    return await tool(timeout=min(step_budget, remaining))

如果每一层都写自己的 30 秒超时，五层叠起来最坏要 150 秒，客户端的 30 秒早就 放弃了。正确的做法是把绝对截止时间传下去，每层只拿 remaining()。lab 的 Deadline 就是这个小对象， 每次 phase 开始前检查一次。

取消只在 await 点发生

FastAPI 文档对 StreamingResponse 的提醒同样适用于所有异步任务： “An async task can only be cancelled when it reaches an await. If there is no await, the generator can not be cancelled properly and may keep running even after cancellation is requested.” 所以 lab 的每个 phase 开头都有一个 clock.sleep() 作为 yield point； Agent 在 phase 边界检查 should_stop()。

取消分两种，语义完全不同：

用户取消

  • POST /runs/{id}/cancel
  • 状态 → cancelled，写 done
  • 不再继续花费 token
  • 已产生的副作用保留

服务端关停

  • readiness → false，拒绝新 run
  • 在飞 run 尽量完成
  • 超时则写 checkpoint，状态回 queued
  • 下一进程从 phase_index 继续

lab 的 R03 场景让 hypothesize 卡 10 秒，而 run deadline 是 1 秒。 结果是 failed、error.code=deadline_exceeded、 checkpoint.phase_index=3，并保留前三个 phase 的 partial evidence。 这不是“模型答错了”，而是执行边界在正确的时间切断了它。

不要用 disconnect 取消昂贵工作

客户端关闭 SSE，只说明它不想看了，不说明这个 run 没有价值——它可能正在 写报告、开 PR，或者另一个客户端正在等结果。lab 的 run 由 service 的 worker 拥有，SSE 生成器只是订阅者；断线只触发 unsubscribe，不触发 cancel。

04重试：预算，而不是勇气¶

重试的第一步不是“退避几秒”，而是判断这个错误是否值得重试。 错误分类错了，后面所有策略都是白费：

类别例子动作
可重试timeout、429、503、连接重置退避 + jitter，受预算约束
不可重试400、401、403、404、422、策略拒绝、校验失败立即失败，记录清晰错误
预算耗尽重试 token 用完立即失败，不再放大负载
超时run deadline 到期失败并保留 partial evidence

AWS Builders' Library 说得最直白：重试是自私的——每次重试都在为某一个调用者多花服务端资源； 在下游已经过载时，重试会让情况更糟、恢复更慢。正确的退避是 capped exponential backoff + full jitter：

delay = uniform(0, min(max_delay, base × 2retry_index)) full jitter：把重试波峰摊平，避免所有客户端同一时刻再次打满下游。

lab 的 R02 让日志工具前两次返回 503。两次重试的延迟分别是 22ms 和 45ms： base 50ms、cap 400ms，full jitter 后落在 [0, bound]。两条延迟不同 不是噪声，而是防止“失败的一批客户端”在同一毫秒一起重试。

重试预算：让重试成为有限资源

AWS SDK 用 token bucket 做 retry quota：重试消耗 token，成功回补 token； 桶空了就直接失败，不再重试。lab 的 RetryBudget 是同一个模型： capacity=8，两次重试后剩 6，五个 phase 成功各回补 0.25，最终 7.00。 如果把 capacity 改成 0，同一个 R02 会立即以 retry_budget_exhausted 失败——这不是“运气不好”，而是系统在保护下游。

3 attempts × 5 layers = 35 = 243 次下游调用 每一层都觉得自己只重试 3 次；叠起来是另一回事。只让一层拥有重试权。

“只让一层重试”是架构决策：如果网关重试、服务重试、Agent 重试、工具客户端也重试， 一次用户请求会被放大成 3^4 甚至 3^5。选定一层（通常是离失败最近、最懂错误的 那一层），其他层只做 fail fast 和错误翻译。

幂等：让重试可以安全发生

重试的前提是“重复执行不会产生第二个副作用”。创建 run 的 POST 必须带 Idempotency-Key： 客户端生成唯一值，服务端把它和 payload 的 fingerprint 绑定。IETF draft （注意：目前仍是 Active Internet-Draft，不是 RFC）定义了这些语义：

情况响应服务端行为
同 key，同 payload，run 已完成200返回原 run，不新建
同 key，同 payload，run 进行中409返回 Location，让客户端 attach
同 key，不同 payload422拒绝，不返回原结果
缺 key400拒绝，提示文档

注意 409 不是失败，而是“你的第一次请求还在跑”。客户端应该拿 Location 去 订阅事件或查状态，而不是再创建一个 run。key 还要有 TTL：太长会占内存， 太短会让仍在重试的客户端创建出第二个 run；TTL 必须覆盖客户端可能的最长重试窗口。

对于 run 内部的副作用（发评论、开 PR），lab 用 (run_id, phase) 作为 effect ledger 的键：先写 effect，再写 checkpoint。如果进程在两者之间崩溃， 重启后会重放这个 phase，但 ledger 发现 effect 已存在，就跳过实际动作。 这叫 at-least-once execution, exactly-once effect——不是靠“应该不会重跑”。

本课最重要的一句话

重试不是本地决定。它花的是下游容量，可能把一次小故障放大成一次雪崩。 先分类、再退避、加 jitter、扣预算，并且只让一层重试。

05流式：SSE 是视图，不是数据库¶

Agent 的首个 token 可能要等几秒，完整 run 可能要几十秒。SSE 的价值是让用户 立刻看到进度，而不是盯着一个转圈。但它不是结果存储，也不是可靠消息队列。

方案方向重连适合
轮询 GET /runs/{id}客户端拉天然可重试低频进度、极简客户端
SSE服务器推浏览器自动 + Last-Event-ID单向进度流、LLM token
WebSocket双向自己实现需要客户端持续发消息

SSE 的线格式很简单，但每个字段都有语义（ WHATWG / MDN）： 

Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no

retry: 2000

id: 7
event: phase_started
data: {"phase":"retrieve_logs","index":1}

: ping

id: 8
event: done
data: {"status":"succeeded"}
  • id: 单调递增；浏览器重连时把它放进 Last-Event-ID 请求头。
  • event: 事件类型；不写就是 message。
  • data: UTF-8 文本；多行会拼接，JSON 保持单行最省心。
  • retry: 浏览器重连等待毫秒数。
  • : 开头是注释，可做 keep-alive ping；它不能改变 Last-Event-ID。

FastAPI 0.135+ 提供了 EventSourceResponse 与 ServerSentEvent： 用 yield 返回事件，框架自动设 text/event-stream、 Cache-Control: no-cache、X-Accel-Buffering: no， 并在 15 秒没有消息时发一个 ping 注释。lab 手写 SSE 是为了控制 replay / snapshot / overflow 的语义，并兼容更老的 FastAPI；生产里可以直接用框架助手。

Last-Event-ID 与 ring buffer

事件日志是有界的。如果客户端断开一小时再回来，它请求的 id 可能已经被淘汰。 这时不能假装什么都没发生，也不能从中间开始发——客户端会缺一段。 lab 的做法是：

  • 订阅时先注册队列，再复制 replay 快照；两者之间的事件会重复一次，按 seq 去重。
  • 如果 last_event_id < first_retained_seq − 1，先发一个 snapshot，包含当前状态、最终结果、最后 id。
  • snapshot 的 id 设为第一个保留事件之前，保证客户端看到的 id 仍然单调。
  • 然后从第一个保留事件继续；如果 run 已 terminal，重放完就关闭。

lab 的 resume 场景里，客户端读完 4 条断开，用 Last-Event-ID=4 重连：从 #05 继续，重叠 0 条，最后一条是 done。 把 retention 改成 4 后，从 id=1 请求会先收到 #10 snapshot， 再收到 11–14；snapshot 里仍然有完整结果，因为结果在 store 里，不在流里。

顺序与错误

两条硬不变量

① 先把结果写进 store，再发 done；客户端收到 done 后仍应 GET 一次确认。② done 是最后一个事件；terminal 之后不再发 phase 事件。SSE 已经开始发送后 HTTP 状态码锁定为 200，运行中失败只能发 event: error，再发 event: done。

背压：慢客户端不能拖垮服务

SSE 没有应用层流控。如果服务端为每个慢客户端无限缓冲事件，一个打开后不读的 浏览器就能吃掉内存。lab 给每个订阅者一个有界队列（默认 16）：满了就丢弃最旧 事件、投递 overflow、断开订阅；客户端用最后真正收到的 id 重连。 overflow 事件携带的是 最后送达的 id，不是 run 的 last id， 否则客户端会跳过中间事件。

代理也会“帮倒忙”：Nginx 默认会缓冲响应，SSE 看起来像一次性到达。 必须设 X-Accel-Buffering: no；FastAPI 的 SSE 助手已经帮你设了。 另外，MDN 提醒：HTTP/1.1 下每个浏览器对每个域最多约 6 条连接，多个标签页同时开 SSE 会互相挤占； HTTP/2 的多路复用可以缓解。

多 worker 的陷阱

Uvicorn 的 --workers 4 是四个独立进程（spawn），不是四个线程。 进程内的 asyncio.Queue、事件日志、幂等表、订阅者字典都不共享。 SSE 连接可能落到 worker A，而 run 在 worker B 执行：必须用外部 store + pub/sub， 或者把 SSE 与执行放在同一进程（单 worker），并接受容量限制。

06关停：SIGTERM 不是断电¶

Kubernetes 的终止流程不是“立刻杀进程”。官方文档描述的默认路径是： 删除 Pod 后开始 grace period 倒计时（默认 30 秒），kubelet 先跑 preStop，再给容器 PID 1 发 SIGTERM，同时控制面开始把 Pod 从 Service endpoints 摘除；grace period 到期后仍在运行的进程收到 SIGKILL。

“The kubelet triggers the container runtime to send a TERM signal to process 1 inside each container.” · “When the grace period expires, if there is still any container running in the Pod, the kubelet triggers forcible shutdown.” Kubernetes — Pod termination

这意味着服务要主动配合，而不是等 SIGKILL：

1. readiness → false （LB 停止导流；liveness 保持 200） 2. 拒绝新 run （503 draining） 3. grace period 内等待在飞 run 4. 超时：取消 worker，写 checkpoint · effect 先落盘，ledger 去重 · checkpoint 记录最后完成的 phase 5. 进程退出 6. 新进程启动：扫描 queued run，从 phase_index 继续

lab 的 shutdown 场景：2 个 run 在跑、4 个排队；drain(0) 立即超时， 2 个在飞 run 各写一次 checkpointed，6 个 run 全部进入 queued_for_restart。新进程用同一个 store 启动，6 个 run 全部成功， effects 恰好 6 次，attempts 是跨重启累计的 [5, 5, 5, 5, 5, 5]。这说明 checkpoint 恢复了进度，而 effect ledger 阻止了重复副作用。

readiness

  • “我现在能接新流量吗？”
  • 关停一开始就返回 503
  • 依赖的 DB/队列未就绪也应为 false

liveness

  • “这个进程还活着吗？”
  • 只有死锁/永久卡死才失败
  • 不要在 liveness 里检查下游依赖

多 worker / 多副本时，下面这些状态必须外置，否则关停与恢复只是 单进程的幻觉：

状态单进程替身生产选择
run 状态与结果Store.runsPostgres / Redis
事件日志与 replayrun.events ring bufferKafka / Redis Streams / 对象存储
幂等键Store.idempotency带 TTL 的 Redis / DB 唯一索引
副作用账本EffectLedger目标系统的幂等键 + DB 表
订阅广播asyncio.QueueRedis pub/sub / NATS / SSE 网关
Uvicorn 相关开关

--timeout-graceful-shutdown 控制等待优雅退出的秒数； --limit-concurrency 在超过并发时直接返回 503； --proxy-headers 只应配合可信的 --forwarded-allow-ips 使用，否则 X-Forwarded-For 可被伪造。Uvicorn 的 workers 使用 spawn，不是 pre-fork；每个 worker 有独立内存。

配额场景：9 个 202、3 个 429；饱和场景：7 个 202、5 个 503， max_inflight=3、queue_depth=4。把 per_tenant_capacity 改小，观察 429 是否先出现；把 workers 改成 1、max_queue 改成 1，观察 503 是否更早。

Step 4 · 重试预算（10 分钟）

Step 5 · SSE 恢复（10 分钟）

先看客户端 A 读 4 条断开、客户端 B 从 Last-Event-ID=4 继续， overlap=0；再把 retention 改成 4，观察 snapshot 如何压缩丢失的前缀。 改 subscriber_queue 为 1，观察 overflow 事件与慢消费者计数。

Step 6 · 关停与恢复（10 分钟）

python3 service_cli.py shutdown

2 个 running、4 个 queued → readiness false → drain 超时 → checkpoint 2 个 → 新进程 6 个全部 succeeded、effects=6。把 drain_timeout_s 改成 10， 观察在飞 run 是否有机会自己完成；把 effect ledger 的检查去掉（改代码）， 观察 effects 是否变成 7——这就是重复副作用。

Step 7 · 拆掉一层，看回归（10 分钟）

  • 把幂等检查移到配额之后：重试会消耗 token，429 提前出现。
  • 把 queue.full() 检查去掉：内存无界增长，延迟飙升。
  • 把 done 事件发在写结果之前：客户端可能在结果落盘前就 GET 到旧状态。
  • 把 worker 取消时的 checkpoint 去掉：重启后 run 从 phase 0 重跑，attempts 翻倍。
  • 把 SSE 的 seq <= last_yielded 去重去掉：重连后出现重复事件。
