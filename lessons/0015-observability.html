01三个问题：为什么、多少钱、慢在哪¶

第 14 课把“任务是否成功”变成了可执行的契约。这一课要回答的是运维层面的三个问题：

问题需要的数据典型回答
这次 run 为什么失败？trace：span 树、工具参数、错误、审批第三次 query_logs 超时后用了相同参数重试，证据没拿到
钱花在哪？token 账本：叶子 inference 的 usage × 价格46.5% 的成本来自 R06 的 8 轮长上下文，历史被重复计费
慢在哪？延迟：wall / active / stage union / critical path墙钟 95 秒，其中 88 秒在等人审批；模型只有 6 秒

这三件事不能靠“日志多打一点”解决。日志是离散事件，缺少父子关系与统一的时间线； trace 把一次 run 组织成有起止时间的树，metrics 把大量 run 聚合成 可告警的时间序列。日志仍然有用，但它是细节，不是骨架。

一句话

日志告诉你“发生了什么”；trace 告诉你“为什么、花了多少、慢在哪”。 没有 trace 的成本数字，只是账单上的一个总数，无法优化。

02Trace 是一棵树¶

在 OpenAI Agents SDK 的模型里，trace 表示一次端到端 workflow， span 表示一个有起止时间的 operation；span 有 trace_id、parent_id、started_at、 ended_at 和 span_data。默认会生成 task、turn、agent、 generation、function tool、guardrail、handoff 等 span；也可以用 custom_span() 加业务 span。 OpenAI Agents SDK — Tracing

把 R04 画成 waterfall，会更直观：

root 95.0s
chat #1 3.0s
tool 1.0s
approval 88.0s
chat #2 3.0s

墙钟 95 秒，但 active 只有 7 秒。审批等待是黄色段；优化模型或工具不会让这条 run 变快。

在 OTel 的 GenAI 约定里，agent 与工具 span 也有标准名字： invoke_agent {agent.name}、execute_tool {tool.name}， 推理 span 的 gen_ai.operation.name 是 chat / text_completion / generate_content。 这些名字不是为了好看，而是为了让聚合查询有稳定的维度。 OpenTelemetry — GenAI semantic conventions

先别急着加字段

span 的属性不是越多越好。高基数属性（用户输入、完整 URL、工单号）会撑爆指标存储； 敏感内容（prompt、工具参数、输出）默认不应采集。先保证 trace_id / span_id / parent_id / 起止 / operation / status / usage 这七类骨架字段正确，再谈业务维度。

03Span 契约与 OTel GenAI¶

这一课的数据模型尽量贴近 OpenTelemetry GenAI semantic conventions。 2026-11 核验：这套约定仍在独立的 semantic-conventions-genai 仓库，状态是 Development，不是 Stable。实现要 pin 版本， 因为属性名会改；例如旧的 gen_ai.system 已被 gen_ai.provider.name 取代。

属性级别用途 / 坑
gen_ai.operation.nameRequiredchat / invoke_agent / execute_tool；汇总 token 前先按它过滤。
gen_ai.provider.nameRequiredprovider 判别维度；不要与 model 混在一起。
gen_ai.request.modelConditional价格表按它匹配；别名/路由会让 request 与 response model 不同。
gen_ai.usage.input_tokensRecommended包含 cache read / cache write / 各模态；不是“未缓存输入”。
gen_ai.usage.output_tokensRecommended包含 reasoning 与各模态输出。
gen_ai.usage.cache_read.input_tokensRecommendedinput 的子集；按 cache 价计费。
gen_ai.usage.cache_write.input_tokensRecommendedinput 的子集；部分供应商收写入溢价。
gen_ai.usage.reasoning.output_tokensRecommendedoutput 的子集；通常按 output 价计费，不要额外再加一次。
gen_ai.agent.nameConditional低基数；不要用框架类型名 StateGraph 当 agent 名。
gen_ai.tool.name / gen_ai.tool.call.idConditional定位一次工具调用；把 tool span 与消息里的 tool_call 对上。

metrics 与 spans 的分工也要清楚。OTel 定义了 gen_ai.client.operation.duration 直方图与 gen_ai.client.inference.usage.input_tokens / output_tokens 等计数器；总量、成本、SLO 应该用 metrics， 因为 metrics 不受 trace sampling 影响。单次为什么贵、为什么慢， 才用 trace。官方文档明确提醒：不要把 gen_ai.usage.* 在所有 span 上直接求和——同一批 token 可能同时出现在 agent span、 gateway span 与 inference span 上。 OTel — Token metrics

在 OpenAI Agents SDK 里，run 结束后可以从 result.context_wrapper.usage 拿到聚合 usage：requests、 input/output tokens、cached tokens、reasoning tokens，以及 request_usage_entries 的逐请求明细。这个聚合值适合做 “这次 run 总共多少”的展示，但做成本归因时仍然要回到每个模型调用。 OpenAI Agents SDK — Usage

04Token 账本：账单不是 token 总数¶

最容易被忽略的一点：agent span 上的 usage 是汇总。 本课把这套记账方式叫 token ledger。 如果你把所有带 usage 的 span 相加，同一批 token 会被算两遍。 lab 里的 R01 就是一个例子：叶子 inference 的 input 是 9,000， 但加上根 agent 的汇总后，naive sum 变成 18,000。

billed_input = input_tokens = uncached_input + cache_read + cache_write uncached_input = input_tokens - cache_read - cache_write input_cost = uncached_input × input_rate + cache_read × cache_read_rate + cache_write × cache_write_rate output_cost = output_tokens × output_rate total = input_cost + output_cost

为什么是“减”而不是“加”？因为 OTel 定义 gen_ai.usage.input_tokens 已经包含 cache read 与 cache write；output_tokens 也已经包含 reasoning。 cache / reasoning 是子集，不是额外项。把它们再加一次，是最常见的账本 bug。

账单要回答

  • cost per run：含失败 run，跑一次多少钱。
  • cost per success：分母只放成功 run，做成一件多少钱。
  • retry cost：失败调用 + 第 2 次及以后尝试。
  • cache savings：相对全部按 input 价省了多少。

不要回答

  • “总 token 数”本身。不同模型、不同缓存状态的价格不同。
  • “平均每次调用成本”。失败与长尾会被平均掉。
  • “按 tokenizer 估算的成本”。provider 的 usage 才是账单口径。
  • “用今天的价格回填历史”。价格会变，历史账不能用新价重算。

失败调用也计费

lab 的 R03 是一次超时 + 重试：第一次 chat 等了 15 秒后失败， 第二次才成功。失败的那次调用仍然消耗了 1,500 input token；重试又消耗了 1,500 input + 160 output。两条加起来是 $0.0091 的 “失败 + 重试”成本，占这条 run 总成本的 57%。 如果只统计成功调用，你会低估失败率高的版本的代价。

长上下文会把历史反复计费

agent 循环通常每轮都重发完整消息历史。第 1 轮输入 1,200 token，第 2 轮 1,800，……第 8 轮 5,400；累计输入是 26,400，约为最后一轮的 4.9 倍。R06 因此一条 run 就花了 $0.078，占总账单的 46.5%。 2026 年的测量研究把这类成本拆成固定前缀、回显的助手历史与工具结果历史； 同一段历史会在后续每一步被重新计费。 Where the Tokens Go (REaLM 2026)

成本优化的顺序

先看 cost per success，再看 top run，再看 context growth。 如果一条长上下文 run 占了近一半成本，先做 compaction / 摘要 / 工具输出裁剪， 比换一个更便宜的模型更有效；换模型可能同时降低能力，抵消收益。

05缓存、价格版本与缺失数据¶

缓存是成本账本里最容易被算错的部分。OpenAI 的 prompt caching 对相同前缀 自动生效，cached input 的价格显著低于未缓存输入；部分模型对 cache write 收溢价。usage 里用 cached_tokens 或 cache_read.input_tokens 报告命中量。 OpenAI — Prompt caching

因此价格表至少要四列：input、output、cache_read、cache_write。 lab 的 R04 命中 1,500 cache token，缓存节省 $0.003375；R07 四轮都命中 95% 的前缀，成本只有 $0.002208，是同等 token 量下最便宜的 run 之一。

价格要版本化

价格表必须有 effective_from。历史 trace 用发生当天生效的价格； 价格调整不能回溯已记录的账。LangSmith 的文档也明确：价格表的更新 不会回填已经记录的 trace。否则你会得到一个“昨天很贵、 今天突然变便宜”的假趋势。 LangSmith — Cost tracking

缺失 usage 时怎么办？答案不是估算，而是标记 unknown，并让面板阻断。 Langfuse 在 2026-11 停止自动 tokenization，理由正是：在 reasoning 与 cache 定价下，文本估算会算错，而且会掩盖损坏的 instrumentation。 Langfuse — Token & cost tracking

fail closed

R08 有一条 inference span 没有 usage。账本把这条 run 的成本标成 lower bound，审计输出 missing usage， 面板直接 BLOCK。先修 instrumentation，再谈成本优化；不要用一个 看起来合理的估算把问题藏起来。

06延迟：wall、active、critical path¶

延迟分析的第一步不是算平均值，而是把时间拆开。这里的关键概念是 critical path：

wall_ms = root span 的 end - start blocked_ms = approval span 区间的并集 active_ms = wall_ms - blocked_ms critical path = DAG 最长路径 - 节点权重：exclusive = duration - union(直接子 span) - 边：parent → child；顺序执行的兄弟：前一个子树的叶子 → 后一个 - 并行兄弟之间没有边，所以不会相加

R04 的 wall 是 95 秒，approval 是 88 秒，active 只有 7 秒。 如果你把 wall 当成“模型延迟”去优化，会改错地方。审批等待是 human latency， 应该单独设预算、单独告警；模型/工具的 p95 只统计 active 部分。

并行工具不能相加

R05 有两个并行工具，各 7 秒，从 2.5 秒同时跑到 9.5 秒。它们的 stage union 是 7 秒，不是 14 秒；critical path 仍然是 12 秒（llm 2.5s + 工具 7s + llm 2.5s）。如果你把每个 span 的 duration 直接相加，会得到一个不存在的 19 秒，然后去优化一个不存在的瓶颈。

critical path 的算法可以记成三句话： 独占时间（父 span 扣掉子 span 覆盖的区间）、 顺序边（前一个子树的叶子接到后一个兄弟）、 最长路径（并行兄弟之间没有边）。lab 的 latency.py 就是按这三个规则实现的，75 个测试里有专门覆盖并行工具与嵌套 agent 的 case。

预算怎么写

指标lab 预算为什么
active p9515.0s用户感知的“模型+工具”时间；不含审批等待。
单 run active 上限20.0s防止 p95 达标但个别 run 极慢。
tool p958.0s工具是常见的尾延迟来源；R10 一个 9 秒工具就把它拖爆。
approval p95120.0s人工审批的 SLO；单独设，避免和模型延迟混在一起。
TTFT p951.2s流式体验；首 token 慢会让用户觉得“卡住了”。

SLO 的写法也值得注意。Google SRE Workbook 建议把延迟 SLI 写成 “低于阈值的请求比例”，例如“95% 的请求 < 15s”，而不是“平均延迟 < 15s”。 平均值会让 5% 的慢请求消失；而用户感受到的往往正是那 5%。 Google SRE Workbook — Implementing SLOs

07尾延迟与 fan-out¶

agent 的一个特点是 fan-out：一次决策可能并行调用多个工具、检索多个分片、 查询多个服务。只要有一个叶子慢，整个 wait-for-all 的步骤就慢。 如果单个叶子慢的概率是 p，并行 n 个叶子时， 至少一个慢的概率是：

P(slow) = 1 − (1 − p)n

p=1%、n=100 时是 63.4%。 这就是为什么“每个工具 p99 都达标”不等于“端到端 p99 达标”。 Dean 与 Barroso 在《The Tail at Scale》里把这称为 tail-tolerant system： 用可预测的整体，去组合不可预测的部件；除了压缩单点延迟，还可以用 hedged requests、微分区、选择性复制等策略。 Dean & Barroso — The Tail at Scale

lab 的 R10 是一个小例子：五个并行工具里四个 0.5 秒、一个 9 秒。 平均值只有 2.2 秒，但 stage union 是 9 秒，tool p95 也是 9 秒。 如果只看平均，你会以为工具层很快；看 p95，才知道尾延迟在哪。

重试会放大尾延迟

超时重试不是免费的：它增加成本，也增加尾延迟。更糟的是“盲重试”—— 用相同参数重试一个已经超时的工具，往往只是把同样的慢路径再走一遍。 第 14 课的 blind_retry 评分器抓的就是这个行为；第 15 课的账本 则把它记成额外的 retry cost。两课要一起看。

08面板与门禁¶

一张可观测性面板至少要能回答四类问题：数据可信吗、钱花在哪、慢在哪、 哪些异常必须阻断。lab 的 dashboard.py 把它们组织成三层：

层检查默认级别
完整性schema / trace 树 / usage 缺失 / agent 汇总一致 / 未知价格BLOCK
延迟active p95、单 run active、tool p95、approval p95、TTFTBLOCK
成本cost per success、cache hit rate、retry shareWARN

lab 的默认数据故意不干净：R08 缺 usage、R09 汇总不一致、R03/R06 超 active 上限、 R10 超 tool p95。所以 dashboard 的结论是 BLOCK， 进程 exit 1，可以直接接 CI。这不是“lab 坏了”，而是 fail closed 的正常表现。

integrity [BLOCK] missing_usage 1 inference span(s) without usage: R08:R08-l2 [BLOCK] reconciliation agent aggregate != sum(inference spans): R09 (input +500, output +0) [PASS] unknown_model every billed model has a price latency [BLOCK] latency_budget global: active_p95_ms 22000.0 > 15000.0 [BLOCK] latency_budget global: tool_p95_ms 9000.0 > 8000.0 cost [WARN] cost_per_success $0.0210 per success > $0.0200 budget [WARN] retry_share 5.4% of cost is failure/retry > 5.0% active p95 22.0s · cost/success $0.020979 · cache 38.9% · retry share 5.4% verdict: BLOCK
面板不是仪表盘比赛

不要把所有指标都设成 BLOCK，那会让门禁变成噪声；也不要把所有指标都设成 WARN， 那等于没有门禁。完整性 fail closed；延迟 SLO 是硬约束；成本与抖动先观察， 有明确业务契约时再升级为 BLOCK。

09采样、隐私与成本治理¶

trace 可以采样，账单不能。OTel 的 token metrics 明确说明：总量指标不受 trace sampling 影响；如果你用采样后的 trace 求和当成本，会随采样率漂移。 正确做法是：metrics 算总账，trace 用来解释个别 run。

采样

  • 记录采样率，并随 trace 一起存储。
  • 错误、审批、高成本 run 优先保留（tail-based sampling）。
  • 不要用采样 trace 的总和做财务账单。
  • 采样策略变化要能解释指标跳变。

隐私

  • prompt / completion / 工具参数默认不采集。
  • 需要内容时单独授权、脱敏、限制保留期。
  • span name 与属性不要放用户输入。
  • ZDR / 合规环境要确认 tracing 是否可用。

成本治理也不只是“换便宜模型”。更有效的顺序通常是： 看 cost per success → 找 top run → 看 context growth → 做 compaction / 工具输出裁剪 / 缓存前缀 → 最后才考虑换模型。第 7 课的 compaction 与第 6 课的引用裁剪，都会在这里变成账单上的数字。

输出应显示 10 条 trace、74 个 span、8/10 成功，以及两个故意埋下的 instrumentation 问题：R08 缺 usage、R09 汇总比子调用多 500 input。 audit: FAILED 是预期结果；先理解为什么失败，再修。

Step 3 · 看一条审批 trace（10 分钟）

python3 obs_cli.py trace --id R04

回答三个问题：(1) wall、blocked、active 各是多少？(2) 为什么 critical path 是 95 秒，而 active critical path 是 7 秒？(3) 为什么 billed usage 只有 2,600 input，而不是 5,200？把答案写下来，再去看 latency.py 的 analyze_trace。

Step 4 · 读账本（10 分钟）

python3 obs_cli.py cost

重点看 R06、R03 与 R08。R06 为什么占总成本 46.5%？R03 的失败调用与重试 如何进入 retry cost？R08 为什么带 *？ 再跑一次： 

python3 -c "from pathlib import Path; from trace_schema import load_traces; from ledger import Ledger; from pricing import PriceBook; t=load_traces(Path('traces.jsonl')); l=Ledger(t, PriceBook.from_path(Path('pricing.json'))); print(l.context_growth([x for x in t if x.trace_id=='R06'][0]))"

你会看到 8 轮、first 1,200 → last 5,400、total input 26,400。 这正是长上下文“历史被反复计费”的账单形态。

Step 5 · 读延迟（10 分钟）

python3 obs_cli.py latency

重点比较 R05、R10 与 R04：R05 的两个 7 秒工具并行为什么不是 14 秒？ R10 的平均工具延迟不高，为什么 tool p95 是 9 秒？R04 的 approval p95 为什么是 88 秒，却不一定该阻断模型发布？

Step 6 · 跑门禁（10 分钟）

python3 obs_cli.py dashboard

输出 verdict: BLOCK，exit 1。把每条 BLOCK / WARN 归类： 哪条是数据完整性问题？哪条是延迟 SLO？哪条只是成本观察项？ 如果只允许你修一个，先修哪条？为什么？

Step 7 · 动手改一个假设（10 分钟）

三选一：

  • 给 R08 的缺失 span 补一个合理 usage，重新生成 fixtures，看 dashboard 的哪些告警消失、哪些还在。问自己：真实系统里应该改数据还是改 instrumentation？
  • 把 R09 的 root_input_delta 改成 0，重跑 audit，观察 reconciliation 从 BLOCK 变 PASS。
  • 把 budgets.json 的 active_p95_ms 放宽到 25,000，跑 dashboard。这是“达标了”，还是“把门禁调松了”？

Step 8 · 成功标准

12和 Java 后端对照¶

本课概念Java 后端对应
trace / span分布式链路追踪；traceId 贯穿请求，spanId / parentSpanId 建树
gen_ai.operation.name接口/操作名；指标聚合的维度
token 账本计费/成本中心；按 tenant、endpoint、model 分摊
cache read / write缓存命中价与回源价；命中率与回源成本
cost per success单位业务成功成本，而不是单次请求成本
wall / blocked / active服务处理时间 vs 等待下游/人工的时间
critical path关键路径法；并行调用不能简单相加
p95 / p99延迟 SLO；平均值会掩盖长尾
dashboard gate发布门禁；完整性 fail closed，SLO 硬约束，成本软信号
sampling链路采样；指标不能采样后再当总量

最大的认知转变是：可观测性不是 AI 特有的“看 prompt”，它就是软件工程里的 链路追踪、计费、SLO 与发布门禁。你在 Java 里做过的 traceId 传播、 Micrometer 指标、成本中心、p95 告警、灰度门禁，全都能直接迁移； 缺的只是把它们对准非确定性的模型调用与按 token 计价的成本。
