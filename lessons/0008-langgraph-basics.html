01为什么把循环画成图¶

第 3 课的循环大约是这样：messages 是局部变量，控制流藏在 for 与 if 里，trace 是手工 append 的列表。它能跑，但一旦要加“人工审批”、 “崩溃恢复”、“并行工具”、“按节点重试”，这些需求会同时改状态结构与控制流，循环会迅速变成一团。

LangGraph 的 StateGraph 把循环拆成三个显式概念： state（在节点之间传递的共享数据）、node（一步计算）、 edge（控制流）。你把图编译出来，框架负责按边推进、按 reducer 合并状态。 Thinking in LangGraph

关注点第 3 课的 while 循环StateGraph
状态局部变量，随手 append显式 schema + 每条通道的 reducer
控制流if / for 嵌在函数里节点 + 边，可渲染、可检查
持久化自己序列化整个对象checkpointer 按 super-step 持久化（下一课）
观测手工 print / tracestream_mode 推每个节点的增量
测试只能测整个循环节点、路由函数、reducer 可分别测
人工介入自己加暂停/恢复逻辑interrupt() + checkpointer（第 9 课）
Java 后端对照

这不是“把代码换个写法”，而是把过程式循环升级成显式状态机。 节点像 transition / command handler，边像 guard，reducer 像聚合根的 merge 函数， compile() 像启动时的图校验。你熟悉的状态机、幂等、事务日志， 都能在这张图上找到对应物。

不要为了图而图

如果流程就是“一次模型调用 + 一次工具调用 + 返回”，一个函数更清楚。 图适合的是有分支、有循环、需要持久化/暂停/观测的长任务。 Anthropic 的建议是：先用最简单的方案，复杂度只在它买到可靠性时才引入。 Building Effective Agents

02State 是通道，不是对象¶

在 LangGraph 里，state schema 的每个字段是一条通道（channel）。 节点不直接改整块 state，而是返回一个增量；通道的 reducer 决定增量怎么合并。 公式只有一行：

statet+1 = merge(statet, node_update)

没有 reducer 的通道使用 LastValue：新值直接覆盖旧值。带 Annotated[..., reducer] 的通道则调用你的合并函数。下面的 schema 把三种最常用的语义放在一起： 

from typing import Annotated, Any, Dict, List, TypedDict
from langchain_core.messages import AnyMessage
from langgraph.graph.message import add_messages
import operator

class AgentState(TypedDict):
    # append；同 id 的消息更新而不是重复追加
    messages: Annotated[List[AnyMessage], add_messages]
    # 每次模型调用 +1
    rounds: Annotated[int, operator.add]
    # 每次工具调用追加一条审计事件
    tool_events: Annotated[List[Dict[str, Any]], operator.add]
    # 默认 LastValue：后写覆盖先写
    max_rounds: int
    answer: str
    stop_reason: str
写法合并语义适合
field: intLastValue：新值覆盖旧值answer、phase、停止原因
Annotated[list, add_messages]追加；同 id 更新；支持删除标记messages
Annotated[int, operator.add]相加轮数、token 计数、重试次数
Annotated[dict, merge_facts]自定义：按 key 合并、冲突标记facts、决策、副作用记录

add_messages 不是简单的 list.append：新 id 会追加，已存在的 id 会 更新原消息，字典会被反序列化成消息对象。 add_messages reference 这正好对应第 7 课的要求：消息是事件流，不是可以随意拼接的字符串。

MessagesState 是预置捷径

LangGraph 提供预置的 MessagesState，其中 messages 已经用 add_messages 定义好，可以直接继承再加字段。本课手写 schema， 是为了让你看见每条通道的合并语义；理解之后再换预置类，不会失去控制。

节点只返回自己改动的字段： 

def model_node(state: AgentState) -> Dict[str, Any]:
    response = llm.invoke(state["messages"], registry.schemas())
    # 不返回完整 state，只返回增量
    return {"messages": [response], "rounds": 1}
reducer 写错，状态就会悄悄丢

把 messages 的注解拿掉，model 节点返回的一条 AIMessage 会 替换整个消息列表；下一轮 tools 节点就看不到之前的对话与工具结果。 把 rounds 的注解拿掉，它永远是 1，预算判断永远不触发。 这两件事都不会报错，只会让 Agent 行为变得“莫名其妙”。

03节点、边与路由¶

节点就是一个函数：接收 state（也可以接收 config / runtime）， 返回一个增量字典。固定边用 add_edge；需要根据状态选择下一步时，用 add_conditional_edges。 

from langgraph.graph import END, START, StateGraph

builder = StateGraph(AgentState)
builder.add_node("model", model_node)
builder.add_node("tools", tools_node)
builder.add_node("finalize", finalize_node)
builder.add_node("budget_exceeded", budget_exceeded_node)

builder.add_edge(START, "model")
builder.add_conditional_edges(
    "model",
    route_after_model,
    {
        "tools": "tools",
        "final": "finalize",
        "budget": "budget_exceeded",
    },
)
builder.add_edge("tools", "model")
builder.add_edge("finalize", END)
builder.add_edge("budget_exceeded", END)

graph = builder.compile()

路由函数只读取 state，返回一个 key；映射表把 key 翻成节点名。END 是特殊的终止节点， 也可以直接由路由函数返回。 

def route_after_model(state: AgentState) -> str:
    last = state["messages"][-1]
    calls = getattr(last, "tool_calls", None) or []

    if not calls:
        return "final"          # 模型给出最终答案
    if state["rounds"] >= state["max_rounds"]:
        return "budget"         # 应用层预算耗尽
    return "tools"              # 还有工具要执行

compile() 会校验图的连接与 schema，然后返回一个可执行的图； invoke() 驱动它跑完。图不是模型，也不是工具运行时——它只负责调度。

还有两种路由写法，先知道存在

Command(update={...}, goto="node") 把状态更新和下一步合并进节点返回值； Send 用于 map-reduce 式的并行 fan-out。它们会让控制流更内聚，但也更难一眼看全。 本课先把显式条件边用熟；需要时再读 Use the graph API。

04同一个 Agent，换一种表达¶

现在把第 3 课的 loop 原样搬进图。关键点是：模型仍然只输出 tool_calls，工具仍然由你的代码执行。 框架没有替你调用模型，也没有替你执行工具；它只是把“什么时候调用谁”显式化了。

对照第 3 课的代码，映射关系几乎是一一对应的：

第 3 课的 while 循环第 8 课的图
messages = [...]initial_state() 的 messages 通道
response = llm.complete(...)model 节点
for call in tool_calls: registry.execute(...)tools 节点
if not tool_calls: return answerroute_after_model → finalize
for step in range(max_steps)rounds 通道 + budget_exceeded
trace.append(...)tool_events 通道
raise AgentLoopError终止节点返回结构化 stop_reason
 
def tools_node(state: AgentState) -> Dict[str, Any]:
    last = state["messages"][-1]
    calls = getattr(last, "tool_calls", None) or []
    messages, events = [], []

    for call in calls:
        result = registry.execute(call["name"], call["args"])
        # 每个 tool_call 必须有一条带相同 id 的 ToolMessage
        messages.append(
            ToolMessage(
                content=result,
                tool_call_id=call["id"],
                name=call["name"],
            )
        )
        events.append({"tool": call["name"], "result": result})

    return {"messages": messages, "tool_events": events}
消息协议是硬约束

一个 tool_call 如果没有对应的 ToolMessage，下一次真实模型调用会直接报错。 预算终止时也一样：未执行的调用要补一条 SKIPPED 的 ToolMessage，而不是默默丢掉。 框架不会替你修消息协议。

05停止条件与失败路径¶

Agent 的停止条件要分三层，而不是只靠一个 max_steps：

层由谁负责典型机制失败时
任务层模型 + 你的路由没有 tool_calls，给出最终答案答非所问，但循环结束
应用层你的路由与预算轮数、token、时间、成本上限返回结构化 stop_reason
框架层LangGraphrecursion_limit（super-step 上限）GraphRecursionError

recursion_limit 是防止图失控的底线，不是业务预算。它统计的是 super-step 数， 默认值非常大；如果你把“最多 6 轮”寄托在它身上，报错时你拿不到结构化的失败原因。 正确做法是应用层先判断，框架层兜底。 Use the graph API — recursion limit 

def budget_exceeded_node(state: AgentState) -> Dict[str, Any]:
    last = state["messages"][-1]
    calls = getattr(last, "tool_calls", None) or []

    skipped = [
        ToolMessage(
            content="SKIPPED: max_rounds reached before this tool could run",
            tool_call_id=call["id"],
            name=call["name"],
        )
        for call in calls
    ]
    text = "达到最大轮数 %d，Agent 已停止。" % state["max_rounds"]
    return {
        "messages": skipped + [AIMessage(content=text)],
        "answer": text,
        "stop_reason": "max_rounds",
    }

失败路径也要分类：可预期的工具错误（参数不对、服务不存在）应该变成 observation， 让模型有机会换一种方法；不可预期的节点异常（代码 bug、依赖挂掉）应该暴露出来， 而不是被 except Exception 吞掉。LangGraph 提供 RetryPolicy、节点超时与 error_handler，但这些是第 9 课之后的工程化话题；本课先保证失败有结构、可观测。

Java 后端对照

应用预算像 SLA / 业务超时，recursion_limit 像熔断器的最大尝试次数： 前者决定“这笔任务还值不值得做”，后者只决定“进程别被拖死”。两者不能互相替代。

06框架给了什么，没给什么¶

框架给你框架不给你
显式 state schema 与 reducer正确的 state 设计（该记什么、冲突怎么裁决）
条件边、循环、并行分支的调度好的 prompt、工具描述与工具粒度
图的可视化与编译期校验任务是否值得用 Agent
checkpoint、interrupt、流式（后续课程）评测集、失败分析、成本与延迟预算
重试、超时、节点级错误处理副作用安全、幂等与权限边界

最容易犯的错误是“图洗白”（graph washing）：把一堆设计糟糕的工具和模糊的 prompt 画成一张图， 就以为系统变可靠了。图的形状不会提高答案质量；它只让你更容易看见问题在哪一步。 Anthropic 反复强调：先判断该不该用 Agent，再选择最简单的编排方式。 Building Effective Agents 12-Factor Agents 的第 8 条也是“own your control flow”：控制流可以借框架表达，但不能不理解。 12-Factor Agents

框架选型不是本课重点

LangGraph 用“显式图”表达控制流；OpenAI Agents SDK 用 Agent / Handoff / Guardrail 表达。 两者都能做出生产系统，差别主要在控制流的显式程度与生态。先把一种用透， 比在框架之间反复横跳更有价值。
