可恢复的 Agent

checkpoint 把状态变成日志，interrupt 把暂停变成协议，stream 把过程变成事件。

Lesson 0009 约 110 分钟 · 选修 +20′ 阅读 38′ · 测验 6′ · Lab 60′ · 选修 20′ 无需 API key · Python ≥ 3.10

第 8 课的图跑在一个进程里：invoke() 开始，END 结束，中间的状态只活在内存。 真实的排障 Agent 不是这样：诊断完可能要等人审批两小时，进程可能被发布、重启或 OOM 杀掉， 前端还想实时看到“现在走到哪一步”。这一课给图加上三样东西： checkpoint（跨进程的状态）、interrupt（持久化的暂停）、 stream（可观测的过程）。

术语以术语表为准： checkpoint、 interrupt、 resume、 durability、 stream_mode。

01一次运行，三个进程边界¶

设想 RepoMedic 接到一条告警：order-service 连接池 48/50，错误率上升。它查完健康数据与 runbook， 提出一个高风险动作：restart_service。接下来发生的事，决定了系统架构：

时刻发生了什么对状态的要求
20:10诊断完成，提出重启建议证据、建议、决策依据要留下来
20:11流程暂停，等待 on-call 审批暂停必须持久化，不能占着一个线程
22:30审批通过，执行重启不能重复执行；审批人要能审计
22:31进程在重启后、写报告前崩溃恢复时不能重跑诊断，也不能再重启一次

第 3 课的 while 循环把 messages 放在局部变量里；第 7 课你手工把 state 序列化成 JSON。 两者都能在“同一个进程内”恢复，但没有回答两个问题：从哪一步继续， 以及哪些步骤已经完成、不能重跑。LangGraph 的 checkpointer 把这两个问题产品化： 它在每个 super-step 边界保存一份状态快照，并用 thread_id 把快照串成一条时间线。 LangGraph — Checkpointers 

import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

conn = sqlite3.connect("checkpoints.db", check_same_thread=False)
graph = builder.compile(checkpointer=SqliteSaver(conn))

config = {"configurable": {"thread_id": "incident-42"}}
graph.invoke(initial_state(), config, durability="sync")

thread_id 不是用户 ID，也不是会话 cookie；它是恢复键。 同一个 thread_id 的每次调用都在同一条时间线上追加 checkpoint；换一个 ID， 就是一条全新的时间线，看不到旧状态。SqliteSaver 适合本地开发； 生产环境换成 PostgresSaver，让多个实例共享同一个 checkpoint 库。 LangGraph — Persistence

Checkpointer 与 Store 不是一回事

checkpointer 保存一条 thread 的图状态，是短期、会话作用域的记忆； store 保存跨 thread 的应用数据，是长期记忆（第 7 课）。 前者回答“这次任务做到哪了”，后者回答“这个用户/团队以前发生过什么”。 两者可以同时挂在一张图上：compile(checkpointer=..., store=...)。

Java 后端对照

thread_id ≈ 业务流水号 / 聚合根 ID；checkpointer ≈ 状态快照 + 事务日志； resume ≈ 从最后一条已提交日志重放。你熟悉的工作流引擎（Camunda、Temporal）里， 这对应“流程实例 + 历史表 + 任务表”。区别是 LangGraph 的图由代码定义，checkpoint 由框架写。

02checkpoint 的边界：super-step，不是代码行¶

这是本课最重要、也最容易误解的一点：checkpoint 发生在 super-step 边界，不发生在代码行之间。 一个 super-step 是一次调度轮次：当前可执行的节点一起运行，它们的增量按 reducer 合并， 然后框架决定下一轮跑谁。正常推进时，checkpoint 只在这轮结束后写。 interrupt() 是一个例外：它把“暂停”本身当作一个需要持久化的事件， 在节点中间额外保存一个 checkpoint。除此之外，节点内部的普通代码行不会触发 checkpoint。 Checkpointers — Super-steps

由此得到三条恢复规则：

对象resume 时的行为后果
已完成的 super-step跳过，不重新执行节点诊断、检索等昂贵步骤不会重跑
未完成的节点从函数第一行重新执行节点内的日志、外部调用、审计写入可能重复
同一 super-step 中已成功的并行任务已写入的 task writes 会保留失败任务重试时，成功兄弟节点不重跑
checkpoint 不是外部副作用的事务边界

execute 节点先调用外部 restart_service，再返回状态更新。如果进程在 “外部调用成功、节点返回之前”崩溃，checkpoint 仍然停在上一个 super-step。resume 时 execute 会整段重跑，外部系统就收到第二次重启请求。 外部写入和 checkpoint 是两个系统，没有分布式事务。 正确做法是给写操作一个幂等键（例如 restart:order-service:APR-7）， 由外部系统保证同一个键只生效一次；或者用 outbox / 唯一约束 / 状态机把重复请求挡住。 

# 危险：副作用在 interrupt 之前
def approval_node(state):
    audit_log.append("asked human")      # 外部写，resume 时再来一次
    decision = interrupt({"type": "approval_required"})
    return {"approval": decision}

# 更安全：把副作用放到 interrupt 之后，或让它带幂等键
def approval_node(state):
    decision = interrupt({"type": "approval_required"})
    return {"approval": decision, "audit": [{"event": "decided"}]}

这和第 7 课的结论是同一条，只是从“自己写 checkpoint”升级成了“框架写 checkpoint”： 可以重放的步骤要纯；不能重放的步骤要幂等。 12-Factor Agents 把这条总结为“own your control flow”，并强调把副作用与状态更新分开设计。

03interrupt：暂停是一个状态¶

interrupt() 不是 sleep，也不是阻塞队列。它抛出一个特殊异常， 让运行时把当前状态存成 checkpoint，然后把控制权还给调用方。 进程可以退出；两天后，只要用同一个 thread_id 调用 Command(resume=value)，节点就会重新进入，value 成为 interrupt() 的返回值。 LangGraph — Interrupts 

from langgraph.types import Command, interrupt

def approval_node(state):
    decision = interrupt({
        "type": "approval_required",
        "incident_id": state["incident_id"],
        "proposal": state["proposal"],
    })
    # resume 时，decision 就是 Command(resume=...) 传入的值
    return {"approval": normalize_decision(decision)}

config = {"configurable": {"thread_id": "incident-42"}}

result = graph.invoke(initial_state(), config, durability="sync")
pending = result["__interrupt__"][0]
print(pending.value)          # 展示给审批人的表单

result = graph.invoke(
    Command(resume={
        "approved": True,
        "approver": "alice",
        "approval_id": "APR-7",
    }),
    config,
    durability="sync",
)

暂停之后，状态可以通过两个入口检查： 

snapshot = graph.get_state(config)

snapshot.next                      # ('approval',) —— 下次会重跑的节点
snapshot.tasks[0].name             # 'approval'
snapshot.tasks[0].interrupts[0]    # Interrupt(value=..., id=...)
snapshot.values["diagnose_runs"]   # 已完成步骤的结果仍在

interrupt() 有六条规则；违反它们通常会得到“看起来能跑、其实会重复”的行为：

规则原因正确做法
必须有 checkpointer 和 thread_id暂停要落盘，恢复要定位compile(checkpointer=...) + 同一 ID
resume 必须用同一个 thread_id新 ID 是一条新时间线把 thread_id 存进你的任务表
节点会从第一行重跑checkpoint 在 super-step 边界interrupt 前的代码保持纯或幂等
一个节点每次调用尽量只放一个 interrupt()多次调用按顺序匹配；循环里每轮 resume 会重放之前的轮次用 state 保存当前问题，条件边回环
不要用 try/except 包住 interrupt()它靠异常暂停，捕获会破坏协议让异常穿透到运行时
并行多个 interrupt 要按 ID 配对每个暂停有独立 id传 {interrupt_id: value} 的 map
审批 payload 也是契约

审批返回值不要直接 bool() 就执行。至少校验三件事： 谁批准的（approver）、审批单号（approval_id）、 批的是哪个动作（incident_id / proposal）。缺少 approver 或 approval_id 的“批准” 无法审计，也无法做幂等键，应当判为无效。 LangGraph 1.2.12+ 支持给 interrupt(..., response_schema=...) 传 Pydantic / TypedDict， 让恢复值在进入节点前先过 schema 校验。 Interrupt response schema

Java 后端对照

这就像工作流引擎里的 user task：interrupt() 创建一个人工任务， payload 是任务表单；Command(resume=...) 是“完成任务”接口； approval_id 是业务主键兼幂等键。区别是 LangGraph 不需要独立的流程引擎和 BPMN， 图本身就是流程定义。你仍然需要自己的审批权限、审计表和唯一约束。

04流式：把过程变成事件¶

checkpoint 解决“能不能恢复”，stream 解决“恢复过程中看不看得见”。graph.stream() 按 stream_mode 把执行过程拆成不同粒度的事件；version="v2" 让每个事件 都有统一的 {type, ns, data} 形状。 LangGraph — Streaming

stream_mode每个事件是什么典型用途
values这一步之后的完整 state 快照调试面板、状态检查点
updates{node: 增量}进度条、审计、测试节点行为
messages(message_chunk, metadata)逐 token 输出、聊天 UI
custom节点通过 get_stream_writer() 发出的事件业务进度、阶段提示
debug运行时任务与 checkpoint 细节排查“为什么这一步没跑”
checkpoints与 get_state() 同形的 checkpoint 事件持久化审计、外部镜像
 
from langgraph.config import get_stream_writer

def diagnose_node(state):
    writer = get_stream_writer()
    writer({"node": "diagnose", "progress": 25})
    return {"evidence": collect_evidence()}

for part in graph.stream(
    initial_state(),
    config,
    stream_mode=["updates", "custom"],
    version="v2",
    durability="sync",
):
    if part["type"] == "custom":
        print("progress:", part["data"])
    elif part["type"] == "updates":
        for node, delta in part["data"].items():
            print(node, "->", delta)

两类流式经常被混为一谈：token 流（messages）解决“模型第一个字多快出现”； step 流（updates / custom）解决“这个任务走到哪一步”。 前者是用户体验，后者是运维与评测。两者可以同时开，事件消费者按 type 分流。

resume 会重放事件，消费者必须能去重

包含 interrupt() 的那个节点在 resume 时会从头重新执行，因此它的 custom 事件、 进度上报、外部日志都会再发一次。给事件带 event_id 或 (thread_id, checkpoint_id, node, seq)，消费端做幂等；不要假设“一条流里每个事件只出现一次”。 stream 是观察手段，不是控制流；不要根据“收到了某个事件”去推进业务状态。

Java 后端对照

values ≈ 快照读；updates ≈ 每个 command handler 发出的领域事件； custom ≈ 业务埋点 / SSE 进度；messages ≈ token 级流式响应。 你在后端熟悉的“事件总线 + 幂等消费 + trace id”，在这里一个都不能少。

05durability 与生产检查清单¶

“有 checkpointer”不等于“每次写盘”。LangGraph 允许你在每次执行时选择 durability 模式： Checkpointers — Durability modes

模式何时写 checkpoint崩溃窗口适合
sync下一步开始前同步写完最小审批、写操作、不可丢的任务
async下一步执行时异步写（1.2 默认）小：写盘途中崩溃可能丢大多数在线 Agent
exit只在正常结束、报错或 interrupt 时写最大：中途崩溃没有记录可整体重跑的批处理

还有一个容易忽略的边界：新 thread 的第一次运行。用 exit 时，崩溃可能让这条 thread 看起来“从未存在过”；get_tuple() 返回 None， invoke(None, config) 会抛 EmptyInputError。 如果你需要区分“没接收”和“接收了但丢了”，要在 checkpointer 之外先写一条 outbox / admission 记录。

Checkpointer适用场景注意
InMemorySaver测试、单次演示进程退出即丢，不能证明持久化
SqliteSaver本地开发、单机工具需要 langgraph-checkpoint-sqlite
PostgresSaver生产、多实例先 setup() 建表；thread_id < 255 字符

选修：把 SQLite 换成 Postgres

SQLite 证明了“状态能跨进程”，Postgres 证明“状态能跨实例”。生产环境通常有多个 API 副本， 它们必须看到同一条 thread；PostgresSaver 把 checkpoint 放进共享数据库， 也正是 LangSmith 使用的后端。图本身一行不用改，只换 checkpointer。 Checkpointer libraries 

import os
from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string(os.environ["DATABASE_URL"]) as saver:
    saver.setup()          # 建表；幂等，生产里作为一次 migration
    graph = builder.compile(checkpointer=saver)
    graph.invoke(initial_state(), config, durability="sync")

from_conn_string 适合脚本和单连接进程。多线程服务应该用连接池， 并在启动时只跑一次 setup()，而不是每个请求都建表： 

import os
from psycopg.rows import dict_row
from psycopg_pool import ConnectionPool
from langgraph.checkpoint.postgres import PostgresSaver

pool = ConnectionPool(
    conninfo=os.environ["DATABASE_URL"],
    min_size=1,
    max_size=10,
    kwargs={"autocommit": True, "prepare_threshold": 0, "row_factory": dict_row},
)
saver = PostgresSaver(pool)
saver.setup()              # 只在这里执行一次
Postgres 特有检查为什么
setup() 只跑一次它是 DDL migration；多实例并发建表会互相抢锁
用 ConnectionPool 共享连接每个请求新建连接会耗尽 Postgres 的 max_connections
thread_id < 255 字符官方对 Postgres checkpointer 的长度约束
一条事故一个 thread不同事故共享时间线后，get_state 会读到彼此的状态
删除前先导出审计delete_thread 会同时删 checkpoints / blobs / writes

Lab 的选修步骤会把同一套 start → resume → crash → continue 在 Postgres 上再跑一遍， 并用 5 个可选测试验证跨连接恢复、thread 隔离与删除语义。见 Lab README 的 Step 6。

生产检查清单

时间旅行：checkpoint 的副产品

graph.get_state_history(config) 按时间倒序列出所有 checkpoint； graph.update_state(checkpoint_config, values, as_node=...) 从旧 checkpoint 分叉出新的分支， 再 invoke(None, fork_config) 重放。replay 会重新执行后续节点（包括 LLM 调用和 interrupt）， 不会重新执行之前已完成的节点。它适合调试与审计，不是生产回滚工具。 LangGraph — Time travel

08和 Java 后端对照¶

Agent 概念Java 后端对应
thread_id业务流水号 / 流程实例 ID / 聚合根 ID
checkpointer状态快照 + 事务日志 / 工作流历史表
super-step一次状态机 tick / 一批 command handler 的执行轮次
interrupt()工作流 user task / 人工审批节点
Command(resume=...)完成人工任务 / 回调审批系统
stream_mode="updates"领域事件 / 每个 handler 的 state delta
stream_mode="messages"SSE / token 级流式响应
幂等键唯一约束 / 去重表 / outbox
get_state_history历史表回放 / 审计追踪

最大的认知转变是：Agent 的“暂停”不是一个阻塞的线程，而是一条持久化的状态。 一旦你接受这一点，审批可以等两天，服务可以滚动发布，消费者可以离线再上线； 恢复的正确性不再依赖进程活着，而依赖 checkpoint、幂等键和消息协议这三样东西。 这也是第 2 周从“会写循环”走向“能交付长任务系统”的分水岭。
