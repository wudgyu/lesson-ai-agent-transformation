01一条告警，三个证据域¶

先把场景具体化。RepoMedic 的可用证据有三类，每类的读取方式与输出量都不同：

证据域典型工具一次调查的原始输出真正要带回的结论
日志query_logs、check_health几十到上万行堆栈、指标时间序列3–5 条带时间戳的直接证据
代码search_code、git_log多个文件、调用链、提交差异可疑代码位置与变更点
Runbooksearch_runbook、search_incidents历史事故、处置步骤、风险说明一条可执行的缓解路径

单 Agent 的方案很自然：把三个工具都给一个循环，模型自己决定先查什么。 问题是，日志的 1000 行堆栈一旦进入主上下文，就会挤占后面读代码和 runbook 的注意力； 到生成最终答案时，最早读到的约束（例如“不要先调大连接池上限”）可能已经被淹掉。 这正是第 7 课讲的 context rot：上下文越长，模型对其中信息的利用越差。 Anthropic — Effective Context Engineering

多 Agent 的直觉是：让日志、代码、runbook 各自在一个独立上下文里调查，只把结论带回主线程。 这个直觉是对的，但它有一个前提：三条调查线可以独立决策，且结论可以用 schema 验收。 如果它们必须看到彼此的动作（例如改代码时必须知道日志里已经排除了什么）， 拆开就会制造冲突假设。这个前提，是后面所有取舍的起点。

先问一句

这条告警真的需要三个域吗？如果日志已经给出“连接池 48/50、30s 超时”， 单 Agent 查一个工具就够了。多 Agent 的第一条成本，是它会让简单任务也变贵。 先用评测确认“单 Agent 在哪些场景不够”，再决定拆谁。

02三种拓扑：控制权在哪¶

多 Agent 的讨论经常把三个概念混在一起：supervisor、handoff、sub-agent。 它们不是同一层的选项。先看一张图：

Supervisor：控制权留在 lead，worker 是受控调用

Supervisor（也叫 orchestrator-worker）是最常见的生产形态。Lead 负责规划、分派、汇总； worker 拿到的是一份委派契约，在独立上下文里调查，只返回摘要与证据。 Worker 不直接和用户对话，也不决定下一步派谁。Anthropic 的多 Agent 研究系统就是这个结构： lead 规划研究策略，并行启动 3–5 个 subagent，每个 subagent 用 3+ 个工具搜索， 返回精简结论，lead 再决定是否追加或收尾。 Anthropic — How We Built Our Multi-Agent Research System

在 LangGraph 里，worker 可以是一个独立的 StateGraph，被 lead 当普通函数调用； 在 OpenAI Agents SDK 里，对应的原语是 Agent.as_tool()：主 Agent 保持控制， 把 specialist 当作一个有 schema 的工具。 OpenAI Agents SDK — Handoffs vs agents-as-tools 

# Supervisor 的核心不是某个包，而是“子 Agent 是一个有契约的工具”
worker = create_agent(model="...", tools=[query_logs, check_health])

@tool("investigate_logs", description="在给定时间窗内查日志，返回 3 条证据")
def investigate_logs(query: str) -> dict:
    result = worker.invoke({"messages": [{"role": "user", "content": query}]})
    return {
        "finding": result["messages"][-1].content,
        "evidence": [],          # worker 必须回传证据
        "confidence": "medium",
        "open_questions": [],
    }

Handoff：控制权转移，上下文共享

Handoff 不是“调用一个工具再回来”，而是把控制权交给另一个 Agent。 接收方可以继续调用工具、直接回复用户，或者再 handoff 给下一个阶段。 OpenAI Agents SDK 的定义是“一个 Agent 把任务委托给另一个 Agent”，默认情况下 新 Agent 会接管整段对话历史；SDK 通过 input_filter 让你决定哪些历史随控制权过去。

在 LangGraph 里，handoff 通常表现为节点返回 Command(goto="code_agent", update={"active_agent": "code", ...})； 多图场景用 graph=Command.PARENT 在父图里导航。 LangChain — Handoffs 

def transfer_to_code(state):
    return Command(
        goto="code_agent",
        update={
            "active_agent": "code",
            # 显式决定哪些消息随控制权过去；不要默认把整个内部轨迹塞过去
            "messages": filter_handoff_messages(state["messages"]),
        },
    )

Sub-agent：一种实现单元，不是拓扑

Sub-agent 强调的是上下文隔离：它在自己的窗口里读大量原始材料， 只把压缩后的结论带回主线程。它既可以是 supervisor 的 worker，也可以由 handoff 的 specialist 内部再调用。LangChain 的文档说得很直接：subagent 默认是无状态的， 每次调用都在一个干净上下文里工作，记忆留在主 Agent。 LangChain — Subagents

问题SupervisorHandoff
谁控制下一步？Lead 决定派谁、何时收尾当前 specialist 决定是否转交
Worker 能直接回复用户吗？通常不能，结果回 lead可以，控制权已经在它手里
上下文如何流动？每 worker 新窗口；只回摘要共享会话；需要显式过滤

Router 与 network

还有两种常见变体：router 是一个无状态分类器，把请求分给一个或多个 specialist， 再把输出合并；它不做多跳委派。LangChain 文档的对比里，subagents 适合并发与上下文隔离， handoffs 适合有状态、需要直接面对用户的流程；router 适合“一次请求、并行分域、最后合并”。 network/swarm 则允许任意 agent 之间互相转交，灵活性最高、可控性最差， 生产里通常要额外加预算与去重。

03上下文经济学：省注意力，不省 token¶

多 Agent 最容易被误解的一点：它不减少总 token，反而增加。 Anthropic 的报告给出了三个量级：

  • 普通 chat 大约 1× token；一个 Agent 大约 4×；多 Agent 系统大约 15×。
  • 在 BrowseComp 上，token 使用量单独解释了 80% 的性能方差，工具调用数与模型选择解释其余部分。
  • 他们的内部研究评测里，Opus 4 lead + Sonnet 4 subagents 比单 Agent Opus 4 高 90.2%；代价是显著更高的 token 成本。

来源：Anthropic — How We Built Our Multi-Agent Research System。 这些数字来自“breadth-first 研究”这一类任务，不是所有任务的通用结论。

多 Agent 的成本 = 单 Agent token + 委派/汇总 + 重复探索
多 Agent 的收益 = 主上下文更小 + 并行 + 权限/工具隔离

所以问题不是“多 Agent 是否更强”，而是“主上下文的注意力压力，是否已经大到值得用额外 token 去换”。 LangChain 文档做过一个具体的成本对比：在多领域任务里，subagents 模式约 5 次模型调用、~9K token； handoffs 模式因为共享状态与历史，约 7+ 次调用、~14K+ token。前者的优势是上下文隔离与并行， 后者的优势是状态连续、可以直接多轮对话。 LangChain — Multi-agent

你想要的代价什么时候值得
主线程不被 1000 行日志淹没worker 的输入输出都要进总账；lead 要写清契约原始材料远超主窗口，结论却很短
三条调查线并行并发调度、超时、部分失败汇总子任务互相独立，墙钟时间重要
读代码与执行重启用不同权限多一套工具白名单、审批与审计高风险动作需要隔离
specialist 直接和用户多轮对话共享历史膨胀、历史过滤与角色配对流程是阶段化对话，而不是一次性调查
上下文隔离的另一面

Worker 拿不到主线程的全部历史，这既是收益，也是风险。它可能重复父级已经排除的调查， 也可能做出与父级约束冲突的假设。Cognition 把这一点总结为“actions carry implicit decisions”： 如果 worker 必须看到另一个 worker 的动作才能正确决策，那么这两个任务就不该被拆成独立上下文。

04反方观点：为什么 Cognition 说别拆¶

2025 年 6 月，Cognition 的 Walden Yan 写了一篇被广泛讨论的反方文章 Don't Build Multi-Agents。 核心论点不是“多 Agent 永远不行”，而是“在需要共享上下文的场景里，并行 subagent 非常脆弱”。 他给了两条原则：

  1. 共享上下文，而且要共享完整的 agent trace，不只是单条消息。 只把初始任务描述传给子 Agent 不够；生产对话是多轮的，工具调用会改变后续解释。
  2. 动作携带隐含决策，冲突的决策会带来坏结果。 两个子 Agent 即使拿到同一个任务，也可能基于各自看到的局部信息做出互相矛盾的假设， 最后由汇总方硬拼接。

他的例子很直观：让多个 Agent 并行实现一个 Flappy Bird，结果一个 Agent 画了马里奥风格的背景， 另一个画了不匹配的小鸟，拼在一起风格撕裂。问题不在单个 Agent 的能力，而在它们看不到彼此的动作。 他的建议是默认使用单线程线性 Agent，保持连续上下文；上下文不够时， 用模型把历史压缩成关键决策与事件，而不是把任务切片并行化。

适合拆

  • 日志、代码、runbook 三条独立调查线
  • 子任务只需返回证据，不需要改共享状态
  • 每个子任务有清晰的输出 schema
  • 并行能显著缩短墙钟时间
  • 工具/权限天然按域隔离

不适合拆

  • 大多数编码任务：后一步依赖前一步的全部动作
  • 子任务之间要不断同步中间决策
  • 任务本身很小，委派契约比任务还长
  • 只是想要“planner / researcher / writer”角色感
  • 没有评测，无法证明拆完更好

Anthropic 的结论与 Cognition 并不矛盾，只是适用边界不同。Anthropic 明确说多 Agent 适合 breadth-first、可独立并行的研究，不适合强耦合任务、大多数编码工作、 需要实时协调的场景；Cognition 说的正是后者。把这两篇放在一起读，你会得到一条更可靠的规则： 按“决策是否需要共享”来拆，而不是按“角色名称”来拆。

05委派契约、预算与失败模式¶

一旦决定拆，supervisor 与 worker 之间的接口就必须像后端 API 一样明确。 最危险的委派是“查一下日志”——范围、输出、约束、预算全缺失，worker 只能自由发挥。

坏委派

查一下 order-service 的日志。

  • 没有时间窗口与服务水平
  • 没有输出格式，无法验收
  • 父级“先别重启”的约束丢失
  • worker 可能查了 10 分钟还在翻日志

好委派

在 20:00–20:10 的 order-service 日志中，找出连接池耗尽的直接证据；只返回 3 条带时间戳的日志与错误码。不要提出修复动作；父级已决定暂不重启。

  • 范围、输出、边界、已知决策齐全
  • 返回可被 schema 校验
  • 父级可以据此审计证据

一份可执行的委派契约至少包含七项：

字段回答的问题
objective这次调查要回答什么？一句话。
inputs允许读哪些数据、文件、日志窗口、事故 ID？
must_consider父级已确认的约束与决策是什么？不要重新推翻。
tools只给完成这件事所需的最小工具集。
output_schema返回 {finding, evidence[], confidence, open_questions[]}。
budgetmax_steps / max_tokens / deadline。
stop什么条件下必须停下并返回 partial？

失败模式可以按 MAST（Multi-Agent System Failure Taxonomy）来系统检查。 这项研究标注了 1,600+ 条轨迹、7 个框架，归纳出 14 种失败模式，分属三类： system design、inter-agent misalignment、 task verification。 Why Do Multi-Agent LLM Systems Fail?

早期系统曾为简单查询创建 50 个 subagent、为不存在的来源无限搜索、 subagent 之间重复工作；还有 subagent 偏好 SEO 内容农场而不是高信任来源。 这些不是模型“笨”，而是委派、工具描述与验证设计的问题。多 Agent 把这些问题放大了 15 倍。

预算与去重

  • Agent 数：从 3–5 开始，不超过任务需要的领域数。Anthropic 的复杂研究场景也常用 3–5 个并行 subagent。
  • 每个 worker：有独立的 max_steps / max_tokens；失败两次即停止，返回 partial。
  • 整个 run：有总 token、deadline 与 max_handoffs；超限时返回“已覆盖什么、还缺什么”。
  • 去重：任务带稳定 key（如 logs:incident-42:20:00-20:10），已执行 key 写入 run state，避免并行 worker 重复调查。
  • 验证：worker 的返回值必须包含证据与置信度；lead 在汇总时做一次引用检查，而不是直接复述。

06评测：和单 Agent 基线比¶

多 Agent 的评测不能只看最终答案。你要回答的是“这次拆分买到了什么”， 所以至少要同时看结果、轨迹与成本：

指标回答的问题怎么测
Task success最终答案是否正确、完整？20 例起；rubric 或 LLM judge + 人工抽检
Evidence coverage该找的证据是否都找到了？期望证据清单 / 实际引用；按 agent 分域统计
Token / cost多花的 token 买到了什么？按 run 记账：lead + worker + 重试 + 汇总
Tool efficiency有没有重复调用、无效调用？tool_calls / task；重复 task key 比例
Latency并行是否真的降低了墙钟时间？p50 / p95；区分串行与并行
Coordination委派是否准确？handoff 是否必要？轨迹规则：agent 选择、handoff 次数、遗漏任务

Anthropic 的做法值得抄：先用约 20 条真实问题起步，定义一个覆盖事实准确性、引用准确性、 完整性、来源质量与工具效率的 rubric；用一个 0–1 分加 pass/fail 的 LLM judge， 再保留人工审查来处理异常与来源偏差。对会改变外部状态的 Agent，评测最终状态或离散检查点， 而不是要求一条固定的轨迹。

先有基线，再谈架构

没有单 Agent 基线的多 Agent 评测，只能证明“它能跑”，不能证明“它更好”。 正确顺序是：同一评测集 → 单 Agent → 加一个 specialist → 对比成功、证据覆盖、token、延迟； 没有可测收益就回退。这条规则能帮你挡掉 80% 的“为了多 Agent 而多 Agent”。

python3 multi_agent.py demo --pattern supervisor --scenario breadth
python3 multi_agent.py trace  --pattern supervisor --scenario breadth

在 trace 里找三个字段：worker_context_keys（worker 只看到自己的 agent / task / scenario，没有父级 findings 与 question）、 saw_other_findings（supervisor 每轮看到多少条已有摘要）、 worker_saw_parent_findings（应为 false）。 这是“上下文隔离”在代码里的样子。

Step 4 · 看 handoff 如何转移控制（10 分钟）

python3 multi_agent.py demo  --pattern handoff --scenario breadth
python3 multi_agent.py trace --pattern handoff --scenario breadth

Handoff 的 trace 会显示 triage → logs_agent → code_agent → runbook_agent → done； 每个 specialist 的 saw_history_len 与 saw_prior_findings 都大于 0， 说明它看到的是共享会话，而不是干净窗口。对比 supervisor 的 worker： 同样是 specialist，控制权与上下文边界完全不同。

Step 5 · 注入失败（10 分钟）

python3 multi_agent.py demo  --pattern supervisor --scenario retry
python3 multi_agent.py demo  --pattern supervisor --scenario dead_tool
python3 multi_agent.py demo  --pattern handoff    --scenario dead_tool

retry 场景里，日志工具第一次失败，worker 自动降级到健康指标； dead_tool 场景里，日志工具彻底不可用，supervisor 与 handoff 都返回 partial， 并在答案里明确标注缺失的证据域。注意：partial 不是失败，而是诚实的停止条件。

Step 6 · 选做：换一个委派契约（10 分钟）

打开 multi_agent.py，把 QUERIES["logs"] 改成一句模糊的 “查一下日志”，再跑 eval。观察 worker 的 task 与最终 coverage 是否发生变化。这个实验没有真实模型，所以不会自动变差； 它只是让你看到契约字段在代码里的位置。接真实模型时，模糊契约会直接体现在 worker 的搜索范围与返回质量上。

成功标准

09和 Java 后端对照¶

Agent 概念Java 后端对应
SupervisorOrchestrator / Facade / API Gateway：编排多个领域服务，自己不持有全部数据
Sub-agent worker有界上下文的领域服务调用；输入输出是 DTO，不是共享内存
委派契约接口契约 + 请求/响应 schema + SLA + 幂等键
上下文隔离不共享可变状态，只通过消息/事件传递已确认的事实
Handoff状态机转移 / 工作流任务改派：active_agent 就是当前状态
Context filtering出站消息裁剪 / 事件投影：只发接收方需要的事实
Task key 去重幂等键 / 去重表 / 唯一约束
Budget & stop超时、重试上限、熔断、deadline budget
Trace分布式追踪：parent span + worker span + 委派参数 + 返回摘要
MAST故障分类法 / postmortem 模板：按系统设计、协作、验证三层归因

最大的认知转变是：多 Agent 不是“把服务拆小”，而是“把上下文拆小”。 微服务拆分的目标是团队自治与独立部署；Agent 拆分的目标是让每个模型调用只看到它需要的证据。 如果你的拆分没有缩小任何一次模型调用的上下文，也没有隔离工具/权限，那它只是多了几层 RPC。
