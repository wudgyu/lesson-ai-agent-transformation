工具设计

Agent 聪明的一半，取决于你给它什么样的工具。

Lesson 0004 约 60 分钟 阅读 15′ · 测验 5′ · Lab 40′ 前半程可离线完成

同一个模型、同一个循环，换一套工具，表现可能差出一个数量级。 但问题通常不在模型：它看到的只有工具的名字、描述、参数 schema 和返回值—— 你的源码、Javadoc、内部 wiki，它一概看不见。今天我们不调模型，只改工具。

01工具是给谁设计的¶

先看一个熟悉的失败现场：用户问“过去 30 分钟有哪些 ERROR 日志”，模型却先调 list_logs， 再调 grep_logs，把整个日志文件捞回来；或者用户说“帮我重启服务”， 模型直接调了一个没有审批参数的重启工具。

直觉会说“模型不够聪明”。但更常见的原因是：工具没有把选择所需的信息暴露出来。 模型不知道 grep_logs 和 query_logs 的边界，因为描述里没写； 它不知道重启需要审批，因为 schema 里根本没有这个参数。

ACI：Agent–Computer Interface

Anthropic 把工具设计称为 ACI，类比人机接口 HCI。工具是确定性代码与 非确定性模型之间的契约：模型只通过 name、description、schema 和返回值来理解它。 Writing effective tools for agents

所以，工具设计不是“把后端 API 包一层”，而是为一个非确定性客户端设计 API。 你熟悉的接口设计原则仍然成立，但多了一个约束：客户端不会读文档，只会读你喂给它的那几百个 token。

02五个原则¶

原则 1 · 少而好：合并工作流，不要 1:1 包 API

Lab 里的 baseline 有 7 个工具：list_services、get_service、 get_metrics、get_deploys、list_logs、 grep_logs、restart_service。只回答“order-service 健康吗”， 模型就要组合三次调用。refactored 把它压成 4 个：

任务BaselineRefactored
健康检查get_service + get_metrics + get_deploysget_service_health
日志查询list_logs + grep_logsquery_logs
处置知识（没有）search_runbooks
重启restart_service（无审批）restart_service（审批 + 幂等）

每多一个工具，模型就多一个选择歧义，schema 也多占一段上下文。 Anthropic 的建议是：先问“删掉它、和别的工具合并，会不会更好？” 如果两个工具总是一起被调用，它们大概率应该是一个工具。

原则 2 · 命名与边界：让参数自己解释自己

Baseline

"grep_logs"
  svc: string
  p: string

p 是 pattern 还是 page？svc 能不能接受短名？没有级别、时间、条数，模型只能猜。

Refactored

"query_logs"
  service: string
  level: ERROR|WARN|INFO|ALL
  since_minutes: 1..1440
  limit: 1..50

参数名、枚举、范围本身就是说明。模型不需要读你的实现，也能把调用写对。

命名空间同样重要：工具名要能区分领域与动作。get_service_health 比 get 好， search_runbooks 比 search 好。工具多了以后，前缀是最便宜的消歧手段。

原则 3 · 返回语义化上下文，不要裸 ID

Baseline 风格

{
  "status": 2,
  "pool": 48,
  "deploy": "a1b2c3d"
}

2 是什么？48 的单位？a1b2c3d 是版本还是 commit？模型只能再查一次。

Refactored 风格

{
  "summary": "order-service 当前降级，连接池 48/50。",
  "status": "degraded",
  "db_pool": {"used": 48, "max": 50},
  "recent_deploy": {
    "version": "v2.14.1",
    "at": "2026-10-24T20:10:00+08:00"
  }
}

summary 不是装饰：它把模型下一步要做的推理，提前压缩成一句可直接引用的话。

裸 ID 还有一个隐性成本：模型为了理解它，会发起额外的查询。 每次额外查询都是一次往返、一次 token 账单、一次出错机会。

原则 4 · Token 效率：过滤、分页、截断

grep_logs 会把所有匹配行拼成一个大字符串，最多 8000 字符； query_logs 先按级别和时间窗口过滤，再用 limit 截断， 单行超过 500 字符也会截断，并在头部返回 matched / shown。 

service=order-service level=ERROR window=30m matched=13 shown=5
2026-10-24T20:12:03+08:00 ERROR [order-service] HikariPool-1 - Connection is not available...
2026-10-24T20:12:04+08:00 ERROR [order-service] GET /api/orders 500 30012ms
...

上下文窗口是预算，不是垃圾桶。工具返回的每一行，都在和系统提示词、对话历史、其他工具结果争夺模型注意力。 能返回 5 行时，不要返回 500 行。

原则 5 · Description 是 prompt，不是注释

Baseline

"Grep logs."

模型不知道：查哪个服务的日志？按什么过滤？返回多少条？什么时候不该用？

Refactored

按级别和时间窗口查询某个服务的日志，
返回带时间戳的匹配行，并附带
matched/shown 计数。用户问“过去 N 分钟
有哪些 ERROR/WARN”时使用。默认
level=ERROR、since_minutes=30、limit=20；
不要用 level=ALL 拉全量日志。

何时用、默认值、反例，都写进去了。这就是在“prompt 工程”工具调用行为。

Anthropic 的说法是：JSON Schema 只能表达结构，表达不了使用模式。 示例、边界、反例、失败时怎么办，都要写进 description。

03错误信息也是接口¶

工具报错时，模型会读错误文本，并决定下一步。错误信息写得好，模型能自己恢复； 写得差，它会重试同一个坏调用，或者干脆编一个答案。

坏错误

ERROR: KeyError: 'svc'
ERROR: failed
ERROR: 400

模型不知道是参数名错了、服务不存在，还是权限问题。只能瞎试。

好错误

ERROR: unknown service 'order-service'.
Available: inventory-service,
payment-service, order-service

ERROR: approval_id is required for
restart. Ask the on-call lead for a
valid approval; do not guess.

说清三件事：发生了什么、下一步能怎么做、什么不要做。

一个好错误信息应该回答：哪里错了？可选的合法值是什么？模型接下来该做什么？ 这和你写 4xx 响应时给客户端的信息是一样的，只是客户端从程序变成了模型。

04写操作：权限、审批、幂等¶

读工具出错，最多是答案不对；写工具出错，可能是生产事故。 Lab 里两个 restart_service 的差别，正好对应后端工程师熟悉的三层防线：

防线BaselineRefactored
最小权限任何调用都能重启必须提供 approval_id
审批校验无校验服务、动作、过期时间
幂等重复调用重复重启同一审批单第二次返回 noop
Prompt 不是安全边界

你可以在系统提示词里写一百遍“不要随便重启”，但模型仍然可能调用工具。 真正的边界在工具层：没有 approval_id 就拒绝执行，参数不合法就返回错误。 这与“前端校验不能替代后端鉴权”是同一个道理。 OWASP LLM Top 10 · Excessive Agency

还有一个容易被忽略的点：幂等键应该绑定审批单，而不是绑定调用次数。 同一张审批单重复到达（重试、断点恢复、模型重复调用），应该返回同一个结果，而不是再重启一次。

Lab 的系统提示词刻意只要求“遵守工具要求的审批流程”，没有写死“必须有 approval_id”。 这样 baseline 的缺陷才会暴露出来。如果你在提示词里写死“不许重启”，baseline 看起来也会很安全—— 但那只是模型这一次听话，不是系统保证。换一个模型、换一句更强势的用户指令，边界就消失了。

05怎么证明工具有效¶

“感觉模型变聪明了”不是证据。工具设计的效果，可以用同一组任务、同一套循环来测：

指标回答的问题
first-tool accuracy模型第一步有没有选对工具？
answer hit rate最终回答有没有包含关键事实？
safety写操作有没有被审批拦住？
steps / tokens同一任务要付多少步数与上下文成本？
failed trajectories失败是模型选错、参数写错，还是工具返回不可用？

这就是 Lab 里 eval.py 做的事。它不追求“排行榜分数”，只回答一个工程问题： 换一套工具，模型在同样的 10 个任务上，是否更少走弯路、更少花钱、更少闯祸？ 第 3 周我们会把这件事扩展成完整的评测体系。

07Lab：7 个薄包装 vs 4 个高层工具¶

代码在 labs/0004-tool-design/。 场景是一个小型 Java 微服务系统：order-service 正在连接池耗尽，payment-service 健康。

Step 1 · 离线校验（2 分钟）

cd labs/0004-tool-design
python3 eval.py --validate
python3 -m unittest -v

--validate 检查 10 个评测用例的期望工具是否都存在； 15 个契约测试覆盖健康快照、日志过滤、runbook 检索、审批与幂等。

Step 2 · 看两种工具设计的循环差异（3 分钟）

python3 agent.py --demo --tools baseline
python3 agent.py --demo --tools refactored

同一个问题，baseline 走 4 步（3 次工具 + 1 次回答），refactored 走 2 步（1 次工具 + 1 次回答）。 注意 refactored 的 observation 里包含 summary——模型可以直接引用，不需要自己拼。

打开 tools_baseline.py 与 tools_refactored.py，填出这张表：

08和 Java 后端对照¶

你已有的工程直觉，几乎可以原样迁移，只是“客户端”从程序变成了模型：

Agent 工具Java 后端
tool schemaOpenAPI / 接口契约
descriptionJavadoc + 使用指南，但它会被当作行为指令执行
ToolError 文本带 error_code 与 hint 的 4xx 响应
approval_id授权令牌 / 审批流 / 工单号
幂等键Idempotency-Key / 去重表
tool-selection eval契约测试 + 集成测试 + 生产演练

最大的认知转变是：模型是一个会犯错、会读错、会自作主张的客户端。 你不能假设它会按文档调用；你只能用更好的契约、更明确的错误、更硬的边界，让它“不容易错”。
